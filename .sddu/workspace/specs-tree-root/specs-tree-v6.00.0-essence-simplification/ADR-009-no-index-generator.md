# ADR-009: 聚合索引不引入生成器——ROADMAP.md 靠 zone/entry 合并机制，非并发问题

## 状态
PROPOSED（2026-11-24 用户拍板）

## 背景
跨视角评估（企业 monorepo 视角，严重度「高」）提出 A5：`TREE.md` / `ROADMAP.md` 是「手写单文件」，多团队并发写会 git 冲突 / 最后写入者胜出；`specs-tree-root/` 缺跨 Feature 进度索引。主张改为「脚本从目录 + state.md 生成，保留单文件可读」。其中 `TREE.md` 随 ADR-010 整体裁撤，本节结论仅覆盖 `ROADMAP.md`。

## 决策
**判为非问题，不引入生成器**。理由：

1. **ROADMAP.md 并非纯手写**——它内置 `sddu:zone` + `sddu:entry` 结构化合并标记（`mode="rewrite"` 整块替换 / `mode="preserve"` 按 entry 键控或行自然键合并），天然为增量更新设计，已是「结构化文档」而非「裸文本」。
2. **§3 特性清单本就是「specs-tree 实时投影」**——从 Feature 目录与 state.md 投影而来，不是人肉维护的副本。
3. **并发冲突只在「企业多团队同时改同一份」时存在**——产品尚未推广，当前为单机 / 单 Agent 场景，无并发；「最后写入者胜出」的风险在当前阶段不发生。
4. **不为「未发生的多团队并发」提前造生成器**——与「简化版本自身必须用最简机制实现简化，避免为简化先增重」自洽（承 ADR-001 理由①）。

## 后果
- 正面：不新增生成脚本，scripts/ 维持「复制器一对」的零代码形态；ROADMAP 的合并语义继续由 zone/entry 标记承担，单文件可读、可 git diff。
- 负面：若未来进入多团队并发维护场景，单文件合并冲突可能重现（届时按 ADR-001 演进路径评估是否引入生成器，无沉没成本）。
- 边界：本决策冻结「聚合索引生成化」于当前形态；重启条件 = 出现真实的多团队并发写冲突证据，而非理论推演。
