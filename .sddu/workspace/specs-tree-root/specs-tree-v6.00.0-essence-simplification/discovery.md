| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-001 | 方法论本质无单一权威表达。本质 = 7 阶段问题解决流程（发现→定义→设计→拆解→执行→核验→验证）+ 三原则（不跳步/不越界/文档即状态）+ 两字段状态模型（phase 8 / status 5），目前分散于 `src/templates/agents/*.md.hbs`（11 个）、README.md、docs/、.sddu/skills/dev-guide、dsh 侧 11 个 SKILL.md 等多处，无最小平台中立核心文档；新增平台即新增一份转写，副本间已出现口径分裂（P-037）。 | 全部平台、全部后续迭代的本质一致性 |
| Q-002 | 载体复杂度膨胀且与本质无隔离判定。45 个 .hbs 模板三层分发（src/templates → dist → .opencode//.dsh/ 落位）、ADR-001 要求同源表达五处同步、ROADMAP 1045 行（26 个修订版本）、问题台账 42 项（P-010 记技术债约 45 项）、.sddu/docs 30 文档中 26 个为迁移残留（P-018）、jest/tsconfig 残留重组前死路径（@pipeline/@discovery/@agents）、版本号三口径分裂（package.json 1.1.0 / README badge 1.4.1 / 项目版本 v4.0.0）——载体在无"本质 vs 附属品"判定约束下自由生长。 | 维护成本、贡献者上手、交付可靠性 |

| 竞品 | 是否处理过类似问题 | 处理方式 | 与我们场景的差异 |

## 5. 假设与风险
> 记录问题挖掘过程中识别的假设和风险，供后续阶段验证和关注

### 5.1 关键假设
> 记录我们对问题理解所基于的假设，标注待验证项

| # | 假设内容 | 验证方式 |
|---|---------|---------|
| A-001 | 方法论本质可被蒸馏为单一、最小、平台中立的核心表达，且 11 Agent / 45 模板 / Skill 可由它派生而不损失行为语义 | spec/plan 阶段做蒸馏可行性设计：抽取核心 → 与现有 Agent 模板逐项比对语义覆盖 |
| A-002 | 载体可删可换而不损害既有平台可用性（opencode/dsh 用户体验不降级） | 裁撤项逐一定义回归验证场景（复用 e2e basic/fullstack） |
| A-003 | 「本质 / 附属品」存在可判定标准（而非逐例争吵）——候选维度：删除后 7 阶段流程是否仍成立 / 是否平台相关 / 是否历史包袱 | plan 阶段定义判定标准并回放既有清单验证区分度 |
| A-004 | 用户对"附属品可删可换"的容忍边界：已交付能力（如 dsh 适配、模板系统）属"可换"而非"可弃"，裁撤需逐项显式确认 | spec 阶段列出裁撤候选清单交用户拍板（已由 roadmap 声明为类 HARD-GATE 语义） |

### 5.2 主要风险
> 识别可能影响问题判断或后续决策的风险因素

| # | 风险描述 | 影响程度 |
|---|---------|---------|
| R-001 | 裁撤既有能力引发回归或用户流失：45 模板 / 11 Agent / Skill 体系均有下游消费者，瘦身可能破坏已交付平台体验 | 高 |
| R-002 | 「本质 / 附属品」判定标准缺失导致误裁：把平台可用性必需品当附属品删掉（如安装链路、状态机） | 高 |
| R-003 | 与 v12.0.0（多平台二期 adapter 抽象）时序耦合：瘦身会重塑 adapters/ 与模板落位结构，先抽象后删减将产生重复劳动（ roadmap 已定本质先行，需保持该次序） | 中 |
| R-004 | 文档生态同步降位改动面大：README / dev-guide / docs/dsh / 30 个输出模板的叙事均以载体为主角，需随内核蒸馏同步改写 | 中 |
| R-005 | 既有 42 项问题台账中多数为载体债，简化后部分问题对象消失、台账需重整，存在登记悬空 | 低 |
