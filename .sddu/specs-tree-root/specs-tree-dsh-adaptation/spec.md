## 2. 上下文
> 回顾问题背景和目标用户

**背景**：SDDU 是一个以 OpenCode 为唯一宿主的软件开发流程框架——多阶段 Agent 编排（版本规划 roadmap + discovery → spec → plan → tasks → build → review → validate 的 Feature 阶段流程）、`state.json` 状态机（phase + status，硬强制阶段门禁）与模板体系。其全部交付物（`install.sh`、npm 包 `opencode-sddu-plugin`、`dist/sddu/*` → `.opencode/plugins/sddu/` 拷贝、Agent 提示词、`sddu_*` 插件工具）都只指向 OpenCode 一个平台，`src/adapters/opencode/` 是唯一适配器实现。

**v5 目标**：v5 大版本要「走出 OpenCode」，而本 Feature（v5.0.0「DSH 适配」）是该目标的**唯一落点**。它要回答：「SDDU 如何以 dsh Skill 包形态、经命令入口，在 dsh（DeepSeek Harness）这个只有 Web UI、无 CLI 的通用 agent harness 上被安装、触发并运行」。v5.1.0 通用多平台适配（FR-CROSSPLAT-001）以本 Feature 为第二平台样本。

**目标用户**（discovery §2）：

| 角色 | 典型场景 | 核心痛点 |
|------|---------|---------|
| SDDU 维护者（自用驱动） | 在自己的 dsh Web 会话里按 SDDU 阶段流程跑真实 Feature | dsh 上目前无任何接入路径，只能继续留在 OpenCode |
| dsh 生态开发者（生态驱动） | 用 dsh 做开发时只有通用 harness + 软引导 plan mode，缺阶段产物、状态可追溯与「不跳步」纪律 | 只能用 dsh 原生 plan + todo 手工替代，无统一产物与状态机 |
| SDDU 架构演进负责人（架构 + 竞争驱动） | 为 v5.1.0 准备第二个平台样本，对冲单平台锁定风险 | `adapters/` 仅一个样本，抽象正确性无法被第二个样本验证 |

**要解决的问题**（discovery 问题清单，本 spec 的追溯源）：

| 来源问题 | 摘要 | 本 spec 落点 |
|---------|------|-------------|
| Q-001 | 平台锁定：dsh 上无任何接入路径 | FR-001 / FR-008 / US-001 / US-002 |
| Q-002 | 形态承载缺口：Skill 包不携带执行能力（**最大不确定性**） | FR-003 / FR-004 / FR-005 / 开放问题 4 |
| Q-003 | 命令入口缺失：`/sddu` 路由与阶段命令在 dsh 无载体 | FR-002 / US-001 |
| Q-004 | 强制力退化：硬强制 vs 软引导 | FR-004 / EC-003 / 开放问题 6 |
| Q-005 | Skill 装配规则冲突：三层目录 vs 六级 rank | FR-001 / EC-002 / EC-007 |
| Q-006 | 验证路径缺失（无 CLI） | FR-006 / NFR-006 / EC-006 |
| Q-007 | 单平台样本的抽象泄漏 | FR-009 / NFR-004 / NG-001 |
| Q-008 | 分发与安装缺口 | FR-008 |
| Q-009 | 平台契约不稳定（Developer preview） | FR-007 / NFR-001 / EC-001 |

**平台事实口径与已知张力（重要）**：

- 用户口径（2026-09-27 访谈，权威）：**dsh 只支持 Web，没有 CLI 等**。本 spec 的接入面、验证方式、门禁约束均以该口径为前提。因此 `@sddu` 式的交互式终端入口与 CLI 驱动的自动化验证在 dsh 侧**不存在**，接入面只能对齐「命令入口（`/sddu` 路由与阶段命令）」，验证只能人工在 Web UI 观测。
- 已知张力：调研文档（2026-08-14 快照）§2 架构全景中记录了 `apps/cli (dsh CLI)`。该记录属**历史快照**，可能与用户口径冲突（假设 A-003）。本 spec **以用户口径为准**，不据此推翻「无 CLI」结论，但如实记录该张力，归入 R-001 时效风险与 §8 开放问题 3 待核实。
- 事实时效：本 Feature 的全部 dsh 契约事实（skill 提供方接口、rank 表、profile / bundle 装配）均来自 2026-08-14 单一调研快照。spec 阶段**尝试刷新契约快照失败**（联网搜索入口不可用），因此本 spec 的 dsh 事实一律标注为「快照态」，时效风险见 R-001 / NFR-007 / §8 开放问题 1。

## 3. 目标与非目标
> 明确需求范围，防止范围蔓延

### 3.1 目标 (Goals)
> 明确本次要达成的业务目标

| # | 目标描述 |
|---|---------|
| G-001 | **建立 dsh 接入路径**：SDDU 能以 dsh Skill 包形态被 dsh 的 skill 提供方注册表发现，并依据 rank 规则确定可辨识、可预期的落位（打开从「装不上」到「装得上」） |
| G-002 | **建立命令入口**：在 dsh Web 会话中提供命令入口（`/sddu` 路由与阶段命令），可启动 SDDU 并进入正确的阶段 Agent（打开从「装上」到「用得上」） |
| G-003 | **承载单阶段流程**：至少一个最小 Feature 可在 dsh 会话中走通单个 SDDU 阶段，产出合规的阶段产物并同步推进状态 |
| G-004 | **明确门禁承载的目标与约束**：为「不跳步」硬强制门禁在 dsh 侧定义可观测的承载目标，并在平台能力所限时要求显式、可见的降级（禁止静默丢失门禁语义） |
| G-005 | **状态与可追溯**：阶段推进与 `state.json` 保持一致，且与 dsh 侧可观测事实（会话日志 / 产物）的关系有明确约定 |
| G-006 | **可验证**：交付「如何验证 + 验证场景（V1~V5）」，使适配达成与否在无 CLI 条件下仍可被人工观测判定 |
| G-007 | **适配层隔离**：dsh 适配落在 `src/adapters/` 隔离边界内，最小侵入，不改动 SDDU 核心状态机语义与既有 OpenCode 链路行为 |
| G-008 | **可控的升级跟随**：在 dsh 频繁破坏性升级下提供可复现的「跟随升级」动作与破坏点记录机制 |
| G-009 | **定位清晰**：明确 SDDU 与 dsh 原生 plan mode / todo / workflow 的分工，避免双轨流程与产物混淆 |
| G-010 | **为 v5.1.0 提供第二平台样本**：沉淀一份可被 FR-CROSSPLAT-001 复用的 dsh 适配样本与契约依赖清单（不提前抽象为通用接口） |

### 3.2 非目标 (Non-Goals)
> 明确本次不涉及的范围，防止需求蔓延

| # | 明确不做 |
|---|---------|
| NG-001 | **通用多平台抽象**：不设计通用平台适配接口 / 抽象层重构 —— 由 v5.1.0 / FR-CROSSPLAT-001 承载（避免单一平台样本上过早抽象，R-003） |
| NG-002 | **端到端验证的执行**：端到端验证不在实施范围；本 Feature 只交付「如何验证 + 验证场景」，执行由用户配合 |
| NG-003 | **改造 dsh 本体**：不修改 / patch dsh 平台自身代码或提交上游改动 |
| NG-004 | **改动 SDDU 核心状态机语义**：phase 流转语义（registered → discovered → specified → planned → tasked → builded → reviewed → validated）保持不变 |
| NG-005 | **OpenCode 以外的其他平台适配**：仅 dsh；Pi / 其他 harness 不在本次范围 |
| NG-006 | **替换或深度集成 dsh 原生方法论插件**：plan / todo / workflow / goal / compaction 不为本 Feature 改造对象，仅需分工定位（FR-010） |
| NG-007 | **生态需求规模验证**：外部 dsh 用户需求规模（A-004）在 v5.0.0 交付后结合反馈评估，不阻塞立项 |
| NG-008 | **Feature 拆分**：本 Feature 保持单一 Feature，不拆分子特性（discovery §6.2 结论） |

## 5. 功能需求 (FR)
> 每个需求必须有唯一标识符且可测试

| ID | 需求描述 | 验收标准 | 优先级 |
|----|---------|---------|--------|
| FR-001 | **Skill 包装配与落位**：SDDU 必须以 dsh Skill 包形态交付，并依据 dsh skill 提供方注册表的 rank 规则（Rank 100 `<projectRoot>/.dsh/skills`、200 `.agents/skills`、300 `customSkillDirs`、400 `<dshHome>/skills`、500 `<agentsHome>/skills`、600 `bundled`；重名最近层优先、单层内按 rank 裁决）确定安装落位与命名约定，使 SDDU 条目来源可辨识、遮蔽行为可预期 | ① dsh Web UI 的 skill 列表可辨识 SDDU 条目及其来源/优先级；② 存在同名 / 近义 skill 时按既定约定裁决、无静默遮蔽；③ 产出「SDDU 三层目录 ↔ dsh rank」落位推演结论（对应 A-005） | P0 |
| FR-002 | **命令入口与阶段路由**：在 dsh Web 会话中提供命令入口（`/sddu` 路由语义 + 阶段命令），用于启动 SDDU 并路由到正确的阶段 Agent；入口不可用或阶段标识非法时，须给出明确、可观测的提示且不进入错误阶段 | ① 在 dsh Web 会话触发入口后进入正确的 SDDU 阶段 Agent 行为；② 非法阶段输入被明确拒绝/提示且流程不误推进；③ 入口清单（命令名 → 目标阶段）成文 | P0 |
| FR-003 | **单阶段流程承载与产物落盘**：至少一个最小 Feature 可在 dsh 会话中走通单个 SDDU 阶段（建议 discovery），产出该阶段规定的产物文件（如 `discovery.md`），产物格式与 SDDU 现有规范一致；阶段 Agent 指令文本须能被 dsh Skill 机制按需加载并正确执行其阶段职责（对应 A-001） | ① 走通后 Feature 目录存在格式合法、可被 SDDU 后续阶段读取的阶段产物；② 产物缺失 / 格式不合法时给出可观测错误而非静默通过；③ 至少 2 个不同阶段 Agent 的指令被加载后行为符合其阶段职责 | P0 |
| FR-004 | **阶段门禁承载的目标与约束**：SDDU 的「不跳步」门禁在 dsh 侧必须满足下列目标之一并如实声明：(a) 保留**可观测的拒绝行为**（非法跃迁被拒绝且不推进状态）；或 (b) 平台能力所限时降级为**显式、可观测、对用户可见**的软引导。**禁止在用户不可见的情况下静默丢失门禁语义**。本条只定义目标与约束，具体承载机制由 plan 决策 | ① 在 dsh 会话中尝试非法跃迁（如 registered 直接进入 build），可观测到明确结果（拒绝 or 显式软引导声明）；② 文档如实标注采用 (a) 还是 (b) 及其边界；③ 不得出现「门禁声称存在但实际不生效且无任何提示」的情形 | P0 |
| FR-005 | **状态推进与 state.json 一致性**：阶段推进必须同步更新 `state.json`（phase / status / phaseHistory），且 `state.json` 与 dsh 侧可观测事实（会话观测 / 产物文件 / 会话事件日志）之间不得出现单向不一致；须定义两者的一致性关系（谁是权威、如何对账、不一致时如何报告） | ① 任一阶段推进后 `state.json` 的 phase 与产物文件一致；② 提供对账规则，可发现并报告「阶段已推进但无记录」或反向不一致；③ 不一致时报告而非静默覆盖（对应 Q-012） | P0 |
| FR-006 | **验证方法与验证场景**：交付物必须包含「如何验证」说明与最小人工验证清单，覆盖 V1 装配可见 / V2 入口可用 / V3 单阶段走通 / V4 门禁行为观测 / V5 升级跟随，并明确观测依据（dsh Web UI 会话 + `.sddu/` 产物文件 + dsh 会话事件日志 / `SessionEvent` 可回放） | ① 验证说明逐项覆盖 V1~V5，写明步骤、观测方式、通过判据、配合方；② 显式声明「无 CLI → 无法自动化断言」的缺口；③ 明确 V1~V5 为**验证方法**而非端到端验收标准 | P0 |
| FR-007 | **升级跟随机制**：针对 dsh Developer preview 的频繁破坏性变更，提供可复现的「跟随升级」动作清单与破坏点记录机制，使适配成果在 dsh 升级后可被重新验证 | ① 提供升级跟随步骤清单 + 破坏点记录模板；② 按清单可在 dsh 升级后重复 V1~V3 并记录破坏点与修复动作；③ 形成「跟随升级」成本基线（对应 V5） | P1 |
| FR-008 | **安装 / 卸载 / 升级路径**：提供在 dsh 上安装、卸载、升级 SDDU Skill 包的明确路径（含落位目录约定），使无 SDDU 背景的 dsh 用户可自助完成 | ① 安装 / 卸载 / 升级步骤可被外部 dsh 用户按文档完成；② 卸载后 skill 列表无 SDDU 残留条目；③ 升级后可重复 V1 装配可见 | P1 |
| FR-009 | **适配层隔离边界**：dsh 适配落在 `src/adapters/` 隔离边界内，采用最小侵入方式；不得修改 SDDU 核心状态机语义，不得改变既有 OpenCode 适配链路行为；dsh 专项概念（rank、目录约定等）不得渗透进核心域 | ① 适配变更后现有 OpenCode 链路行为不变（现有测试保持通过）；② dsh 专项概念不出现在核心域（state / templates 等）；③ 隔离边界与最小侵入范围成文 | P0 |
| FR-010 | **与 dsh 原生方法论的分工定位**：明确 SDDU 阶段方法论与 dsh 原生 plan mode / todo / workflow 的分工与共存方式，避免双轨流程与产物混淆 | ① 交付一份定位说明；② 给出至少 3 个判定示例（何时走 SDDU 阶段、何时用 dsh 原生能力、如何共存）；③ 用户可按说明做出选择（对应 Q-010） | P1 |

> 说明：FR-004 只定义「门禁在 dsh 侧的可观测承载目标与约束」；门禁的具体实现机制（工具 seam / 命令拦截 / guard 等）属 plan 阶段技术设计范围，不在本 spec 内决策。

## 6. 非功能需求 (NFR)
> 性能、安全、可用性等跨切面需求

| ID | 类别 | 需求描述 | 验收标准 |
|----|------|---------|---------|
| NFR-001 | 兼容性 | 适配必须能承受 dsh Developer preview 的契约变更：所有 dsh 契约依赖点（skill provider 接口、rank 表、profile / bundle 装配、目录约定）须集中列出并落在隔离层，变更时修复面可控 | ① 产出完整 dsh 契约依赖点清单（含快照日期）；② 变更影响面仅落在隔离层，不波及核心域 |
| NFR-002 | 可维护性 | 在 v5.1.0 收敛前，OpenCode 与 dsh 两条接入链路在模板、文档、Skill 编排、状态语义上不得出现两套漂移表述；单一维护者可维护 | ① 两平台差异仅存在于隔离层，核心文档单一来源；② 产出「双平台差异清单」并可随版本核对（对应 Q-011） |
| NFR-003 | 可追溯性 | 阶段推进与门禁行为必须留下可观测证据（产物文件 + 会话观测 / 会话日志），使过程可回溯 | 任一阶段推进均可通过产物 + 会话记录回溯「谁推进、依据何产物、门禁是否放行」 |
| NFR-004 | 隔离性 | 最小侵入：核心状态机语义不变，既有 OpenCode 链路行为不变，dsh 专项细节不渗透核心域 | 现有测试全部通过；核心域无 dsh 专项概念引用（对应 FR-009） |
| NFR-005 | 可用性 | 在无 CLI 前提下，人工完成一次 V1~V3 验证的操作成本可控 | 验证清单给出最小步骤序列与可接受的时间预算上限；不依赖命令行 |
| NFR-006 | 可验证性 | 所有验收标准必须可在「dsh Web UI 会话 + `.sddu/` 产物文件」下人工判定，不依赖 CLI 或自动化断言 | 逐条验收标准均标注观测方式；无法人工判定的条目不得进入验收 |
| NFR-007 | 时效性 | 全部 dsh 事实必须标注来源与快照日期；契约刷新失败必须显式记录为开放问题与风险，不得以过时快照冒充当前事实 | ① 文档中每条 dsh 事实可追溯至 2026-08-14 快照；② 刷新失败与时效风险在 §8 显式登记（对应 R-001 / A-008） |

## 7. 边界情况 (EC)
> 异常场景和边界条件的处理方式

| ID | 场景 | 处理方式 |
|----|------|---------|
| EC-001 | dsh 破坏性升级导致适配失效（契约变更 / 目录约定变更） | 按 FR-007 升级跟随清单定位破坏点并记录；若属契约级变更，更新 NFR-001 契约依赖清单并标注快照日期，必要时登记开放问题（对应 R-001 / Q-009） |
| EC-002 | rank 遮蔽冲突：SDDU skill 与 dsh 宿主或第三方同名 / 近义 skill 相遇 | 按 FR-001 命名与落位约定裁决；约定无法覆盖时**显式提示冲突**并给出落位建议，不得静默被遮蔽（对应 Q-005） |
| EC-003 | 门禁无法硬承载：dsh 侧不具备可执行的拒绝点 | 降级为 FR-004(b) 的显式软引导，并在 spec / 交付文档中如实声明为「已知降级」，禁止声称硬强制（对应 Q-004 / R-002） |
| EC-004 | Skill 未被注册表发现（落位错误 / scope 不匹配 / 发现缓存未失效） | 提供落位自检清单（目录层级 / scope 链 / `skills/change` 失效后重新快照），提示用户核对并重试；不得静默失败 |
| EC-005 | `state.json` 与 dsh 会话日志 / 产物不一致 | 按 FR-005 对账规则报告不一致并指出权威来源；禁止静默覆盖任一侧；必要时暂停推进等待人工确认（对应 Q-012） |
| EC-006 | 无 CLI 导致无法自动断言 | 使用 FR-006 最小人工验证清单；显式声明自动化缺口，不将「未观测」等同于「通过」（对应 Q-006 / R-004） |
| EC-007 | 命名 / 近义 skill 冲突（SDDU 自身多阶段 skill 之间或与生态 skill 之间） | 采用带 SDDU 前缀的命名约定 + 来源可辨识标识；冲突时按 rank 与最近层优先规则裁决并记录 |
| EC-008 | 阶段产物落盘失败 / 路径不可写 / 目录不存在 | 给出明确错误提示与回退指引，且**不推进** `state.json`；避免「状态已推进但产物缺失」 |
| EC-009 | 用户在同一会话混用 dsh 原生 plan mode 与 SDDU 阶段流程 | 按 FR-010 分工说明给出可观测提示与建议；避免生成两套互相矛盾的流程产物（对应 Q-010 / R-005） |

## 附：验证方法与验证场景（**非端到端验收标准**）
> 应用户要求补充。用户原话：「端到端验证不在你的实施范围，但是可以将如何验证，验证场景的设计写出来，我来配合你验证，因为 dsh 只支持 web，没有 cli 等。」

**性质声明（务必遵守）**：下列 V1~V5 是**验证方法与验证场景**，用于让「适配是否达成」可被观测；**不是端到端验收标准**。**端到端验证不在本 Feature 实施范围内**（既定约束），执行由用户配合人工完成；本 Feature 的验收以 §5 / §6 / §7 条款为准。

**观测依据**：① dsh Web UI 会话内容；② `.sddu/` 产物文件；③ dsh 侧会话事件日志（`SessionEvent` 可回放，是天然的过程证据）。
**已知缺口**：无 CLI → 无法做自动化断言，V1~V5 均需人工观测；因此 §5 FR-006 要求交付一份最小「人工验证清单」（对应 EC-006 / NFR-006）。

| 场景 | 验证内容 | 观测方式（Web UI 无 CLI） | 通过判据 | 配合方 |
|------|---------|--------------------------|---------|--------|
| V1 装配可见 | SDDU Skill 包被 dsh skill 注册表发现且落位正确（rank / source 可辨识） | 在 dsh Web UI 中列出可用 skill，确认 SDDU 条目的来源与优先级 | 列表中出现 SDDU 条目且来源可辨识、无遮蔽冲突（校验 FR-001） | 用户（截图 / 列表） |
| V2 入口可用 | 在 dsh Web 会话中触发 `/sddu` 路由或阶段命令，进入正确的 SDDU 阶段 | 会话中观测到阶段入口被识别并切换到对应阶段 Agent 行为 | 进入正确阶段；非法阶段输入被提示且不误推进（校验 FR-002） | 用户（对话观测） |
| V3 单阶段走通 | 以最小 Feature 走通一个阶段（建议 discovery）：产出 `discovery.md` 并生成 / 更新 `state.json` | 检查产物文件是否存在且格式合法（`state.json` 可被 SDDU 状态机读取，phase 与产物一致） | 产物存在且合法，`state.json` 与产物一致（校验 FR-003 / FR-005） | 用户 + 维护者 |
| V4 门禁行为观测 | 尝试非法阶段跃迁（如 `registered` 直接进入 build），观测是否有拒绝行为 | 会话中观测：被拒绝（硬强制保留，FR-004a）还是显式软引导声明后继续（FR-004b） | 出现明确可观测结果（拒绝 or 显式软引导声明），且文档如实标注采用哪种（校验 FR-004） | 用户 + 维护者 |
| V5 升级跟随 | dsh 版本更新后重复 V1~V3，观测是否仍可用 | 记录破坏点与修复动作，形成「跟随升级」的实际成本基线 | 能按 FR-007 清单定位破坏点并完成回归 / 修复（校验 FR-007 / NFR-001） | 用户 |
