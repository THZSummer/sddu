## 1. 问题定义

> 概括核心问题及其业务影响，回答"为什么需要关注"

| 核心问题 | 业务影响 | 不解决的成本 |
|---------|---------|------------|
| SDDU 当前**只能以 OpenCode 插件形态运行**，在 dsh 上不存在任何安装 / 加载 / 触发路径 → 想在 dsh 上用 SDDU 的人完全用不上（ROADMAP 称 v5 大版本要「走出 OpenCode」，本 Feature 是该目标的唯一落点） | v5「多平台适配」大版本无法启动；SDDU 价值被平台锁定封顶；v5.1.0 通用多平台适配（FR-CROSSPLAT-001）缺少第二平台输入 | 持续被单平台锁定；dsh 生态中的方法论需求被 dsh 原生软引导方案（plan/todo）吸收，SDDU 失去生态位 |
| 用户已拍板形态为「**dsh Skill 包**」，但 dsh 的 Skill 是**可选的指令而非会话事件、不携带执行能力**；而 SDDU 的 8 阶段 Agent、`PhaseSkipError` 硬强制、`state.json` 状态推进、模板渲染全部建立在 OpenCode 插件 / 工具原语之上 → 交付形态与流程承载能力之间存在结构性缺口 | 「不跳步」这一 SDDU 核心竞争力在 dsh 侧失去强制载体，方法论从硬强制退化为提示词纪律；阶段产物与状态推进可能无法生成 | 适配成果退化为「一份写给模型看的说明书」，用户无法确认流程被遵守，SDDU 与 dsh 原生 plan mode 的差异化消失 |
| dsh 侧**只有 Web UI（无 CLI）**，SDDU 现有入口是 OpenCode 内的 `@sddu` 智能路由 + 阶段命令；选定对齐面为「命令入口（`/sddu` 路由与阶段命令）」后，该入口在 dsh 的 Web 会话中没有对应触发载体 | 用户无法在 dsh 上启动任何一个 SDDU 阶段，适配即使「装上」也无法「用起来」 | 用户只能手工把 Agent 提示词粘进 Web 输入框，流程编排（阶段路由、自动触发下游 Agent）全部失效 |
| SDDU 现有的验证手段（npm 测试、CLI 驱动、文件产物断言）在 dsh 上**不可用**（仅 Web UI，用户明确说明无 CLI）；适配是否达成只能靠人工在 Web UI 中观测，且用户已表态「我来配合你验证」 | 适配缺少可复现、可回归的验证路径，后续每次 dsh 破坏性升级都只能人工回归 | 质量问题被延迟到用户侧暴露；v5.1.0 收敛通用接口时缺少可靠的适配基线 |

## 2. 用户画像

> 描述受影响用户角色及其场景，回答"谁遇到了什么问题"

| 用户角色 | 典型场景 | 关键痛点（用户原话） | 当前应对方式 |
|---------|---------|-------------------|------------|
| **SDDU 维护者**（本项目唯一维护者，自用驱动） | 想在自己的 dsh Web UI 会话里，按 SDDU 的 8 阶段流程跑完一个真实 Feature | "自用驱动：维护者自己想在 dsh 上用 SDDU"（用户访谈 2026-09-27） | **忍受** — 日常继续留在 OpenCode 走 SDDU；dsh 只当调研对象，不进真实工作流 |
| **dsh 生态开发者**（外部用户，生态驱动） | 用 dsh 做软件开发时，只有通用 harness + 软引导 plan mode，缺少阶段产物、状态可追溯与「不跳步」纪律 | "生态驱动：面向外部 dsh 用户推广 SDDU"（用户访谈 2026-09-27） | **放弃 / 手工模拟** — 用 dsh 原生 plan + todo 手工替代，无统一产物、无状态机、无阶段门禁 |
| **SDDU 架构演进负责人**（同一维护者，架构驱动 + 竞争驱动） | 为 v5.1.0 通用多平台适配（FR-CROSSPLAT-001）准备第二个平台样本，同时对冲 OpenCode 单平台锁定风险 | "架构驱动：为 v5.1.0 通用多平台积累第二平台样本"；"竞争驱动：对冲 OpenCode 单平台锁定风险"（用户访谈 2026-09-27） | **临时方案** — 仅凭 OpenCode 单平台样本推断 `adapters/` 通用接口，抽象正确性无第二个样本可证 |

> 备注：三个角色由同一维护者出发、面向不同受众；角色差异主要体现在「用得上（自用）」「装得上（生态）」「抽得对（架构）」三个不同痛点上，而非访谈对象不同。

## 3. 问题清单

> 按影响程度分级梳理所有识别到的问题，每项赋予唯一编号 Q-xxx

### 3.1 核心问题

> 影响面大、频率高、用户强烈感知

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-001 | **平台锁定：SDDU 在 dsh 上无任何接入路径。** SDDU 的全部交付物（`install.sh`、npm 包 `opencode-sddu-plugin`、`dist/sddu/*` → `.opencode/plugins/sddu/` 拷贝、12 个 Agent 提示词、`sddu_*` 插件工具）都指向 OpenCode 一个宿主；dsh 既不在安装脚本的落点、也不在包的分发形态内。想用 SDDU 的 dsh 用户第一步就卡死。<br>来源：现状代码（`src/adapters/opencode/` 为唯一适配器；`package.json` 名 `opencode-sddu-plugin`）+ 用户访谈 | 全部 dsh 侧潜在用户（画像 2 类）；阻塞 v5 大版本；影响安装 / 装配 / 运行三个环节 |
| Q-002 | **形态承载缺口：Skill 包形态不具备执行能力。** 用户已拍板 SDDU 在 dsh 上以「dsh Skill 包」形态交付（复用 dsh 的 skill 提供方注册表 + rank）。但 dsh 的 skill 按设计是「可选的指令而非会话事件」（调研文档 §3.4），不携带工具执行、状态写入与阶段门禁能力；而 SDDU 的流程纪律依赖运行时可执行部分：`sddu_update_state` 状态推进、`PhaseSkipError` / `PhaseReversalError` 拒绝跳步、模板渲染与产物落盘。二者叠加后，纯 Skill 包无法承载这些机制，缺口位置与补救边界目前无人能说清。<br>来源：用户访谈（形态=「dsh Skill 包」）+ 调研文档 §3.4 / §3.6 + 现状代码 `src/state/`、`src/adapters/opencode/plugin.ts` | 全部 dsh 侧使用者；决定 spec 的全部边界；是本 Feature 的最大不确定性 |
| Q-003 | **命令入口缺失：`/sddu` 路由与阶段命令在 dsh 无载体。** 用户选定唯一对齐面为「命令入口（`/sddu` 路由与阶段命令）」。而 dsh 侧只有 Web UI，无 CLI / TUI 交互形态（用户明确说明"因为 dsh 只支持 web，没有 cli 等"）；SDDU 现有入口是 OpenCode 的 `@sddu` 智能路由 + Agent 模式，两者机制不同。用户在 dsh 会话里如何触发「开始 / 阶段推进 / 自动触发下游 Agent」目前完全没有答案。<br>来源：用户访谈（接入面=命令入口；dsh 仅 web） | 全部 dsh 侧使用者；阻塞端到端可用性；影响 v5.1.0 的入口抽象 |
| Q-004 | **强制力退化：硬强制方法论在软引导平台上失效。** SDDU 的「不跳步」是其在调研中确认的核心竞争力（硬强制 vs 软引导，调研文档 §3.6 / §6），而 dsh 的 plan mode 只是日志里的 `plan/mode` 软引导，限制由沙箱与批准策略各自执行、不读写 plan 状态；skill 同样只是指令。适配到 dsh 后，若无承载机制，SDDU 的阶段门禁会退化为「提示词里写了但没人检查」，用户无法确认流程被遵守，可追溯性也从「阶段快照」进一步减弱。<br>来源：调研文档 §3.6 / §6 + 用户访谈（形态=Skill 包） | 方法论可信度；生态用户对 SDDU 的差异化认知；后续所有阶段的产物质量 |
| Q-005 | **Skill 装配规则冲突：SDDU 三层目录 vs dsh 六级 rank。** SDDU 的 Skill 体系按目录层级仲裁（用户级 `.sddu/skills/`、框架级 `.opencode/plugins/sddu/skills/`、实际运行 `.opencode/skills/`），而 dsh 按提供方 rank 数值仲裁（100 `<projectRoot>/.dsh/skills`、200 `<projectRoot>/.agents/skills`、300 `customSkillDirs`、400 `<dshHome>/skills`、500 `<agentsHome>/skills`、600 `bundled`），重名时最近层优先、单层内按 rank 裁决。SDDU 自身不携带 rank 概念，与 dsh 宿主或其它插件提供的同名/近义 skill 相遇时，**谁遮蔽谁、SDDU 应落在哪一级**尚无结论。<br>来源：调研文档 §3.4（rank 表）+ 现状（三层 Skill 目录 + 三元自举闭环：discovery/creator/sync） | Skill 的安装位置与发现可靠性；与 dsh 生态插件的共存；SDDU 自举闭环（sync）在 dsh 上的有效性 |

### 3.2 次要问题

> 影响面中等、或为核心问题的衍生问题

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-006 | **验证路径缺失：无 CLI 导致自动化与回归手段不可用。** dsh 只有 Web UI（用户原话："因为 dsh 只支持 web，没有 cli 等"），SDDU 现有的验证手段（`npm test` 分层测试、CLI 驱动的端到端脚本、对 `.sddu/` 产物做文件断言）在 dsh 侧都无法直接使用；用户已明确「端到端验证不在实施范围内，但可以写出如何验证与验证场景的设计，我来配合验证」。因此适配成果缺少可复现、可回归的验证路径，观测只能依赖 Web UI 会话与产物文件，且高度依赖人工。<br>来源：用户访谈（无 CLI + 配合验证表态）+ 现状 `scripts/`、`package.json` scripts | 适配质量与回归能力；v5.0.x 缺陷版本的可验证性；用户侧投入的验证成本 |
| Q-007 | **单平台样本的抽象泄漏：`adapters/` 只经历过 OpenCode。** v4.0.0（FR-FRAMEWORK-ARCH-001）完成三域分层与平台适配器隔离，但 `src/adapters/opencode/` 是唯一实现，接口是否已被 OpenCode 概念（agent / command / plugin / MCP / 三层 skill 目录）渗透无从判断；而用户选定的 dsh 形态（Skill 包 + 插件树 + scope + rank）与原语的对应关系完全不同。若直接照搬现有适配接口，第二次适配很可能触发适配层返工。<br>来源：FR-FRAMEWORK-ARCH-001（已就绪）+ 调研文档 §2 / §3 + 用户访谈（架构驱动） | v5.0.0 的实现路径与工作量；v5.1.0 通用接口的正确性；适配层的长期可维护性 |
| Q-008 | **分发与安装缺口：现有落点与 dsh 约定不匹配。** 现有分发为「npm 包 + `install.sh` + 拷进 `.opencode/plugins/sddu/`」，而 dsh 的 Skill 发现约定是 `.dsh/skills`、`.agents/skills`、`<dshHome>/skills` 等目录；用户不知道「怎么把它装到 dsh 上」，也没有卸载 / 升级路径（dsh 处于 Developer preview，升级频繁）。<br>来源：调研文档 §3.4 rank 表 + 现状 `install.sh` / `scripts/package.cjs` | 生态用户的采纳门槛（装不上就谈不上用）；升级跟随成本 |
| Q-009 | **平台契约不稳定：dsh 处于 Developer preview。** dsh 明确处于快速迭代、带兼容性破坏警告的阶段；本适配所依赖的契约（skill 提供方接口与 rank 规则、profile / bundle 装配方式、目录约定）随时可能变更。用户的风险姿态是「适配层隔离，允许跟随升级」，但**隔离边界画在哪里、什么算破坏性变更、跟随升级的动作是什么**目前没有被定义。<br>来源：调研文档 §1（Developer preview）+ 用户访谈（风险姿态） | 适配成果的有效期；v5.0.x 的维护成本；v5.1.0 抽象时机 |

### 3.3 潜在问题

> 目前影响小但可能恶化，或信息不足待验证

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-010 | **方法论双轨与认知混淆。** dsh 自带 plan mode / todo / workflow 等方法论插件，与 SDDU 的阶段方法论在语义上重叠（都要回答「先想清楚再动手」）。在 dsh 上同时存在两套方法论时，用户可能不清楚何时用 dsh 原生能力、何时走 SDDU 阶段，形成双轨流程与两套产物。当前无 dsh 用户反馈，属潜在问题。<br>来源：调研文档 §3.6 / §5 + 推断（待用户反馈验证） | 生态用户的采纳与留存；SDDU 在 dsh 上的定位清晰度 |
| Q-011 | **双平台维护成本与一致性漂移。** 本 Feature 交付后到 v5.1.0（FR-CROSSPLAT-001）收敛通用接口前，SDDU 需同时维护 OpenCode 与 dsh 两条接入链路；模板、文档、Skill 编排、状态语义存在出现两套表述并逐渐漂移的风险，而项目为单一维护者模式（历史上曾有 solo-team-flow 议题）。<br>来源：ROADMAP v5.1.0 / PR-007 + 项目维护结构 | 维护者精力；产物一致性；文档可信度 |
| Q-012 | **状态权威来源未明（信息不足）。** dsh 以 append-only 事件日志为唯一事实源（「Model-visible ⟺ logged」不变量），SDDU 以 `state.json` 可变状态机为事实源。两者在 dsh 上并存时，谁是权威、如何避免「阶段已推进但日志无记录」或反向的不一致，目前无任何记录；信息不足，需在 spec/plan 前澄清。<br>来源：调研文档 §3.2 + 现状 `src/state/` | 状态可追溯性；跨平台行为一致性；调试与恢复能力 |

## 4. 竞品参考

> 记录竞品对类似问题的处理方式，回答"别人怎么做的、我们有什么不同"

| 竞品 | 是否处理过类似问题 | 处理方式 | 与我们场景的差异 |
|------|-------------------|---------|----------------|
| **DSH**（本 Feature 的宿主平台，同时也是与 SDDU 重叠度最高的竞品） | 是 | 把方法论元素做成可插拔插件：plan mode 仅写入 `plan/mode` 日志事件作**软引导**，限制由沙箱与批准策略各自执行；todo / workflow / goal / compaction 提供任务与方法论视角；skill 走提供方注册表（本地 / 内嵌 / 远程 + rank 100~600）；工具执行走 waterfall + 单调 guard 审批流水线 | dsh 是通用 harness（方法论软引导、无阶段强制、插件即能力单元）；SDDU 是方法论框架（硬强制 8 阶段 + 固定 Agent 角色）。关键区别：**dsh 在本 Feature 中是宿主平台（被适配对象），不只是竞品**——调研文档 §7 的「借鉴建议」不属于本 Feature 问题域 |
| **Pi**（earendil-works） | 部分 | 明确不做子代理与 plan mode，只提供扩展五件套（极简 harness） | 方法论元素比 dsh 更薄，与本 Feature 的适配问题不构成对照（调研文档 §5 结论：对标价值低于 dsh） |
| **OpenCode**（SDDU 现状宿主平台） | 是 | 通过 agent / command / skill / plugin / MCP 五类原语承载 SDDU：12 个 Agent 提示词模板、`@sddu` 路由、三层 Skill 目录、`sddu_update_state` 等插件工具、硬强制状态机 | 这是 SDDU 当前唯一运行形态，也是 Q-001 平台锁定与 Q-007 抽象泄漏的成因；本 Feature 要把同一套方法论搬到形态差异很大的第二个平台上 |

## 5. 假设与风险

> 记录问题挖掘过程中识别的假设和风险，供后续阶段验证和关注

### 5.1 关键假设

> 记录我们对问题理解所基于的假设，标注待验证项

| # | 假设内容 | 验证方式 |
|---|---------|---------|
| A-001 | dsh 的 Skill 机制足以承载 SDDU 的 12 个阶段 Agent 指令文本（skill 作为可选指令可被模型按需加载） | **待验证** — 通读 dsh skill 提供方文档 / 实机在 dsh Web UI 中加载 SDDU Skill 包并观察模型是否可用（用户配合） |
| A-002 | dsh 侧存在与 Skill 包并存的承载手段（插件 / 工具 seam / 命令），可补齐 Q-002 的执行缺口 | **待验证** — dsh 实机验证 + 用户确认；若不存在，则「Skill 包」形态不足以支撑完整流程，须回炉重定形态 |
| A-003 | 「dsh 只支持 web，没有 CLI」的准确含义是「无交互式终端形态」，而调研文档 §2 中列出的 `apps/cli` 仅为启动器 / 装配入口 | **待验证** — 查 dsh 仓库 apps 实际形态 + 用户确认（此点直接决定 Q-003 / Q-006 的解法空间） |
| A-004 | 生态侧存在真实规模的 dsh 用户需求（愿意在 dsh 上用 SDDU 的外部用户数值得投入） | **待验证** — 用户调研 / 社区反馈计数；当前仅有维护者主观判断 |
| A-005 | SDDU 三层 Skill 目录可通过「安装位置映射 + 命名约定」与 dsh 的 rank 规则对齐，无需引入 rank 概念 | **待验证** — 针对 dsh rank 表做一次映射推演（spec 前完成） |
| A-006 | `adapters/` 隔离层能容纳「Skill 包」这一**非代码 / 配置形态**的第二平台实现 | **待验证** — 架构评审（对照 `src/adapters/opencode/` 现有接口） |
| A-007 | 用户愿意配合在 dsh Web UI 中做端到端验证，且以「会话观测 + 产物文件」作为观测依据 | 用户已表态愿意配合（2026-09-27 访谈，接近确认）；**待验证** — 具体验证场景与观测方式需在 spec 阶段敲定 |
| A-008 | 本阶段所有 dsh 事实均来自 2026-08-14 的单一调研快照，至今（2026-09-27）未发生影响结论的变化 | **待验证** — 刷新 dsh 当前版本的关键契约（skill provider 接口 / rank 表 / profile 装配） |

### 5.2 主要风险

> 识别可能影响问题判断或后续决策的风险因素

| # | 风险描述 | 影响程度 |
|---|---------|---------|
| R-001 | **问题理解偏差风险**：dsh 侧事实全部来自一份 1.5 个月前的调研快照，且调研深度为「方法论 + 关键源码级」而非实机运行；若 skill / 装配契约已变，问题清单的若干条会失真 | 高 |
| R-002 | **形态可行性风险**：「Skill 包」形态可能不足以承载流程强制与状态推进（Q-002），导致 v5.0.0 的目标与验收边界需要重定义，甚至退回形态决策 | 高 |
| R-003 | **抽象过早风险**：仅凭一个平台样本迁移，`adapters/` 通用接口可能被 dsh 专项细节污染，v5.1.0 收敛时返工（ROADMAP 已识别「避免在单平台样本上过早抽象」） | 中 |
| R-004 | **验证能力风险**：无 CLI / 无自动化，回归只能人工在 Web UI 观测，且依赖用户配合；dsh 每次破坏性升级都可能带来无法自动发现的行为回归 | 中 |
| R-005 | **用户采纳风险**：方法论双轨（Q-010）若不做定位澄清，生态用户可能优先使用 dsh 原生 plan/todo，SDDU 在 dsh 上形成「装了但不用」 | 中 |
| R-006 | **维护容量风险**：双平台并存期间的一致性与升级跟随成本落在单一维护者身上（Q-011），可能挤压 v5.1.0 及后续版本节奏 | 中 |
| R-007 | **市场/价值风险**：生态需求规模未验证（A-004），若外部 dsh 用户需求不足，本 Feature 可能只服务维护者自用场景 | 中 |

### 6.1 验证场景设计（应用户要求补充；**非验收标准**，供 spec / validate 阶段参考）

> 用户原话："端到端验证不在你的实施范围，但是可以将如何验证，验证场景的设计写出来，我来配合你验证，因为 dsh 只支持 web，没有 cli 等。"  
> 以下仅为**验证设想与观测方式**，用于让「适配是否达成」可被观测；验收标准由 spec 定义、验证执行由 `@sddu-validate` 承担。

| 场景 | 验证内容 | 观测方式（Web UI 无 CLI） | 配合方 |
|------|---------|--------------------------|--------|
| V1 装配可见 | SDDU Skill 包被 dsh 的 skill 注册表发现，且落位正确（rank / source 可辨识） | dsh Web UI 中列出可用 skill，确认 SDDU 条目的来源与优先级；无遮蔽冲突 | 用户（截图 / 列表） |
| V2 入口可用 | 在 dsh Web 会话中触发 `/sddu` 路由或阶段命令，进入正确的 SDDU 阶段 | 会话中观测到阶段入口被识别并切换到对应阶段 Agent 行为 | 用户（对话观测） |
| V3 单阶段走通 | 以最小 Feature 走通一个阶段（建议 discovery）：产出 `discovery.md`，并生成 / 更新 `state.json` | 检查产物文件是否存在且格式合法（`state.json` 可被 SDDU 状态机读取，phase 与产物一致） | 用户 + 维护者 |
| V4 门禁行为观测 | 尝试非法阶段跃迁（如 `registered` 直接进入 build），观测是否有拒绝行为 | 会话中观测：是被拒绝（硬强制保留）还是仅提示后继续（退化为软引导）——**该观测结果直接决定 Q-004 在 spec 中的结论** | 用户 + 维护者 |
| V5 升级跟随 | dsh 版本更新后重复 V1~V3，观测是否仍可用 | 记录破坏点与修复动作，形成「跟随升级」的实际成本基线 | 用户 |

**观测依据约定**：会话内容（Web UI）+ `.sddu/` 产物文件 + dsh 侧会话事件日志（`SessionEvent` 可回放，是天然的过程证据）。**缺口**：无命令行 → 无法做自动化断言，V1~V5 均需人工观测，建议在 spec 阶段约定一份最小「人工验证清单」。

### 6.2 Feature 拆分建议

> 按 §5.6 拆分模式扫描：本 Feature 的输入（形态 = 「dsh Skill 包」，对齐面 = 「命令入口」）**未命中**前后端分离 / 多端架构 / 管理后台+用户端等拆分特征。

- **结论**：**不建议拆分**，保持单一 Feature（`specs-tree-dsh-adaptation`）。
- 说明：「通用多平台抽象」不属于本 Feature，已由 v5.1.0 / FR-CROSSPLAT-001 承载，不应在本 Feature 内提前分裂。
