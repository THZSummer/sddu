## 2. 上下文
> 回顾问题背景和目标用户

本 Feature 源于对 Roadmap v19.0.0 中 FR-AUTONOMY-001 原提案的深度访谈修正。原提案描述的是「给所有 Agent 加决策边界 + 分级自主 L0/L1/L2 + 四维决策边界模型」，经逐轮访谈确认，用户的真实诉求与之有根本性差异——**不是改造现有 Agent 的提问行为，而是新增一个独立的调度 Agent `sddu-auto`**，在用户与 7 个子 Agent 之间插入一层代理决策层。

**要解决的问题**（discovery.md Q-001~Q-007）：
- 简单项目走完整 7 流程时每一步都依赖人机交互，效率大幅下降（Q-001）。
- 现有 `sddu-fast` 零产物，无法满足「需要完整流程产物」的场景（Q-002）。
- 缺少「启动问清诉求 → 后续全自主跑完 7 流程」的入口，形成能力空白（Q-003）。

**目标用户**：有经验的开发者（简单项目想快速拿到完整 7 流程产物）、团队/项目负责人（需要完整产物供团队协作与知识沉淀，但不愿被逐步打断）。

**三个调度入口的定位**（用户已确认）：

| 入口 | 定位 | 走 7 流程 | 交互 |
|------|------|:---:|------|
| `sddu` | 普通调度 | ✅ | 每步人机交互 |
| `sddu-fast` | 快速调度 | ❌ 零产物 | 轻量直接 |
| `sddu-auto`（新增） | 自动调度 | ✅ 完整 7 流程 | 启动问一次，之后全自主 |

## 3. 目标与非目标
> 明确需求范围，防止范围蔓延

### 3.1 目标 (Goals)
> 明确本次要达成的业务目标

| # | 目标描述 |
|---|---------|
| G-001 | 新增独立的调度 Agent `sddu-auto`，作为第三个调度入口，与 `sddu`、`sddu-fast` 并列 |
| G-002 | 实现「启动阶段问清诉求 → 执行阶段全自主跑完 7 流程 → 沉淀全套产物」的端到端自动调度体验 |
| G-003 | 在不改动既有 7 个子 Agent 执行流程的前提下，将其执行阶段的提问重定向给 `sddu-auto` 代答 |
| G-004 | 选择 `sddu-auto` 入口即默认进入自主决策模式，无需「简单与否」判定或额外配置 |

### 3.2 非目标 (Non-Goals)
> 明确本次不涉及的范围，防止需求蔓延

| # | 明确不做 |
|---|---------|
| NG-001 | 不改造既有 7 个子 Agent（discovery/spec/plan/tasks/build/review/validate）的执行流程 |
| NG-002 | 不引入 autonomyLevel（L0/L1/L2）分级配置，不实现四维决策边界模型 |
| NG-003 | 不提供产物质量不满意的修正、回退、迭代能力——效果不满意由用户自行改走 fast/普通 sddu/重跑 |
| NG-004 | 不改变 `sddu`（普通调度）与 `sddu-fast`（快速调度）的现有行为 |

## 4. 用户故事
> 以用户视角描述功能需求

| # | 作为… | 我想要… | 以便… |
|---|-------|---------|-------|
| US-001 | 有经验的开发者 | 在启动时一次说清我的简单项目诉求，之后让 `sddu-auto` 全自主跑完 7 流程 | 不必在每一步都拍板，大幅降低交互负担 |
| US-002 | 团队/项目负责人 | 让 `sddu-auto` 自主完成简单项目并沉淀完整的过程产物（discovery.md~validate.md） | 团队可基于完整产物协作与知识沉淀 |
| US-003 | 有经验的开发者 | 直接选择 `sddu-auto` 入口即进入自主决策模式 | 无需判断项目「简单与否」或额外开关 |
| US-004 | 有经验的开发者 | 在 `sddu-auto` 跑完后查看最终效果与全套产物 | 放手一次跑完、最后统一验收 |

## 5. 功能需求 (FR)
> 每个需求必须有唯一标识符且可测试

| ID | 需求描述 | 验收标准 | 优先级 |
|----|---------|---------|--------|
| FR-001 | 新增独立调度入口 `sddu-auto`，作为第三个调度入口，与 `sddu`、`sddu-fast` 并列可选 | 系统提供 `sddu-auto` 入口；用户可从 `sddu`/`sddu-fast`/`sddu-auto` 三者中任选其一启动 | P0 |
| FR-002 | `sddu-auto` 走完整 7 流程，按 discovery→spec→plan→tasks→build→review→validate 顺序依次执行全部 7 个阶段 | 一次运行中 7 个阶段全部被触发并产出对应阶段产物，无阶段被跳过 | P0 |
| FR-003 | 启动阶段为唯一人机交互点：`sddu-auto` 在启动时向用户提问，搞清楚用户的问题与诉求 | 启动阶段 `sddu-auto` 向用户发起提问以澄清诉求；该提问仅发生在启动阶段 | P0 |
| FR-004 | 执行阶段（spec 起至 validate 完成）所有问题由 `sddu-auto` 自行答复，绝不允许向人类提问；拿不准时也必须硬决策 | 在启动阶段结束后到 7 流程完成前，注入任意「原本需向用户提问」的场景，`sddu-auto` 均自行返回决策，全程不向用户提问 | P0 |
| FR-005 | 既有 7 个子 Agent 的执行流程保持完全不变（零改动），其既有提问行为照常发生 | 对比改动前后 7 个子 Agent 的流程定义，无任何行为级修改 | P0 |
| FR-006 | 子 Agent 在执行阶段发起的提问，其接收方由「用户」变为「sddu-auto」；`sddu-auto` 必须返回答复，而非将提问转发或透传给用户 | 子 Agent 提问时，答复由 `sddu-auto` 给出；提问内容不呈现给用户、不等待用户输入 | P0 |
| FR-007 | `sddu-auto` 跑完后沉淀全套过程产物（discovery.md ~ validate.md），与普通 `sddu` 完整流程的产物范围一致 | 运行结束后，Feature 目录下存在 discovery.md~validate.md 全套产物文件 | P0 |
| FR-008 | 选择 `sddu-auto` 入口即默认进入自主决策模式，无需任何「简单与否」判定或额外配置开关 | 用户直接选择 `sddu-auto` 即进入自主决策模式，无中间判定步骤或配置项 | P0 |
| FR-009 | 本 Feature 边界限定为「新增 sddu-auto 代理决策层」，不包含「改造现有 7 个子 Agent 的提问行为」，不包含 autonomyLevel（L0/L1/L2）分级配置与四维决策边界模型 | 需求范围内不存在任何对现有 Agent 提问行为的改造项，也不存在分级自主配置项 | P1 |
| FR-010 | 跑完完整 7 流程并沉淀全套产物即视为本模式完成；本模式不提供修正、回退、迭代能力 | 7 流程跑完 + 全套产物落地即判定完成；不存在「自动修正/回退/迭代」环节 | P1 |

## 6. 非功能需求 (NFR)
> 性能、安全、可用性等跨切面需求

| ID | 类别 | 需求描述 | 验收标准 |
|----|------|---------|---------|
| NFR-001 | 可用性 | 启动阶段提问应足以引导用户一次性完整表达问题与诉求（对应 A-001） | 启动提问至少覆盖问题背景、目标、范围、验收期望等必要信息维度；用户表达不完整时可在启动阶段内追问补全 |
| NFR-002 | 一致性 | `sddu-auto` 沉淀的全套过程产物在文件命名与结构上与普通 `sddu` 完整流程产物保持一致 | 产物文件清单、命名与普通 `sddu` 走完整流程时一致 |
| NFR-003 | 行为确定性 | 执行阶段面对「拿不准/信息不足」的提问，`sddu-auto` 必须返回一个确定的决策，不得因无法决断而中止、阻塞或反问用户 | 注入「启动诉求未覆盖、信息不足」的提问，`sddu-auto` 仍返回决策并继续推进后续阶段 |

## 7. 边界情况 (EC)
> 异常场景和边界条件的处理方式

| ID | 场景 | 处理方式 |
|----|------|---------|
| EC-001 | 启动阶段用户诉求表达不完整 | 在启动阶段内（唯一交互点）可多轮追问补全；一旦进入执行阶段，不再向用户提问 |
| EC-002 | 执行阶段子 Agent 提出启动诉求未覆盖的决策点 | `sddu-auto` 基于「启动诉求 + 项目上下文」硬决策（拿不准也决策），不反问用户 |
| EC-003 | 执行阶段遇到需外部信息（如 API 文档缺失）的情况 | 由 `sddu-auto` 记录为开放问题/假设并继续推进，不中断向用户询问 |
| EC-004 | 用户误将复杂项目交给 `sddu-auto` | 仍全程自主跑完 7 流程（进入即自主、无复杂度门槛）；跑偏风险由用户承担，不满意后自行改走其他入口 |
| EC-005 | 产物质量不满意 / 全程自主硬决策跑偏 | 本模式不负责修正/回退/迭代；用户自行改走 `sddu-fast`（轻量）或普通 `sddu`（交互）处理 |

## 9. 拆分建议
> 在需求定义过程中识别到的可独立交付模块

本 Feature 边界清晰、功能内聚——「新增 `sddu-auto` 代理决策层」是一个单一的调度 Agent 行为定义，不包含可独立交付的子模块。**无需拆分**，按单 Feature 模式创建完整规范。
