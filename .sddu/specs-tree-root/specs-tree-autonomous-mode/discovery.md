> **文档定位**: SDDU 问题挖掘报告 — 记录用户问题、痛点和场景，作为 spec 阶段的输入

> **版本**: v2.0
> **更新人**: SDDU Discovery Agent

## 1. 问题定义
> 概括核心问题及其业务影响，回答"为什么需要关注"

| 核心问题 | 业务影响 | 不解决的成本 |
|---------|---------|------------|
| 简单项目走完整 7 流程时「每一步都依赖人机交互」，效率大幅下降 | 用户被迫在每个阶段反复拍板，即使项目本身很简单 | 用户要么忍受啰嗦的逐步交互，要么放弃完整流程产物 |
| 现有 `sddu-fast` 不走 7 流程、零产物，无法满足「要完整流程产物」的需求 | 需要完整产物（团队协作、知识沉淀）的简单项目没有合适入口 | 简单项目被强行套用重交互流程，或退化为无产物的快速处理 |
| 缺少「启动问清诉求 → 之后全自主跑完 7 流程」的入口 | 用户想要「放手一次跑完、最后看效果」的体验无从获得 | 简单项目无法高效地拿到完整产物 |

> **用户痛点原话**（逐轮访谈确认）：*「属于特殊场景，对于那种简单的项目，用户想让 AI 完成自主决策，完成所有流程之后，用户再去看效果，而非每一步都依赖人机交互，这样会大幅降低效率。」*

### ⚠️ 关键澄清：与 Roadmap 原提案的差异

Roadmap v19.0.0 中 FR-AUTONOMY-001 原提案描述的是「给所有 Agent 加决策边界 + 分级自主级别 L0/L1/L2 + 四维决策边界模型」——即**改造现有 Agent 的提问行为**。

经深度访谈确认，用户的真实诉求与之有**根本性差异**：

> 用户要的是「**新增一个独立的调度 Agent `sddu-auto`**」，而非改造现有 Agent。

- 原提案 = 改造现有 7 个子 Agent 的「何时该问、何时不该问」行为
- 真实诉求 = 在用户与子 Agent 之间**插入一层 `sddu-auto` 代理决策层**，子 Agent 完全不动

此差异直接影响 spec 阶段的方向选择，需在 spec 阶段明确对齐。

## 2. 用户画像
> 描述受影响用户角色及其场景，回答"谁遇到了什么问题"

| 用户角色 | 典型场景 | 关键痛点（用户原话） | 当前应对方式 |
|---------|---------|-------------------|------------|
| 有经验的开发者 | 简单项目想快速拿到完整 7 流程产物，选择 sddu-auto 放手一次跑完 | *「简单项目每一步都依赖人机交互，大幅降低效率」*；*「用户自己定义，可选自主完成」* | 被迫走 `sddu` 逐步交互，或用 `sddu-fast` 但拿不到产物 |
| 团队/项目负责人 | 需要完整流程产物供团队协作与知识沉淀，但项目本身不复杂 | 想「放手一次跑完、最后看效果」，不愿被逐步打断 | 委托成员代跑，成员同样面临逐步交互的负担 |

> **进入方式**（用户原话）：*「用户自己定义，可选自主完成」*；*「选了 auto agent 默认就是自主决策模式」* —— 用户直接选择 `sddu-auto` 入口即默认进入自主决策模式，无需额外的「简单与否」判定；「简单项目」只是典型适用场景，而非进入门槛。

## 3. 问题清单
> 按影响程度分级梳理所有识别到的问题，每项赋予唯一编号 Q-xxx

### 3.1 核心问题
> 影响面大、频率高、用户强烈感知

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-001 | **简单项目走 7 流程逐步交互，效率低**。现有 `sddu` 普通调度在每个阶段都与用户交互，简单项目也需要反复拍板，交互负担与项目复杂度不匹配。 | 所有「简单项目」用户 |
| Q-002 | **`sddu-fast` 零产物，无法满足「完整流程产物」需求**。fast 不走 7 流程、不沉淀 discovery/spec/plan 等产物，用户需要完整产物的场景（团队协作、知识沉淀）得不到满足。 | 需要完整产物的简单项目 |
| Q-003 | **缺少「启动问清诉求 → 后续全自主跑完 7 流程」的入口**。用户想要的「放手一次跑完、最后看效果」体验，现有 `sddu`（太交互）和 `sddu-fast`（无产物）都无法提供，形成能力空白。 | 全部有经验的用户 |

### 3.2 次要问题
> 影响面中等、或为核心问题的衍生问题

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-004 | **启动后所有决策须由 `sddu-auto` 自主答复，但决策依据有限**。在「执行阶段不允许问人」的硬约束下，discovery/spec/plan 等阶段原本依赖人机交互填人的那部分决策（需求确认、技术选型），只能靠「启动时搞清楚的诉求 + 项目上下文」自主推断，决策质量高度依赖启动输入的充分性。 | sddu-auto 的决策质量 |
| Q-005 | **子 Agent 保持原有流程照常提问，但其提问需被拦截并重定向到 `sddu-auto`**。用户明确「不改变原有 agent 的执行流程」，故子 Agent 仍会提问；需要一种机制把这些提问从「面向用户」重定向为「面向 sddu-auto」，而非直接问人类。 | 全部 7 个子 Agent 的提问路径 |

### 3.3 潜在问题
> 目前影响小但可能恶化，或信息不足待验证

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-006 | **全程自主硬决策的跑偏风险**。执行阶段「拿不准也硬决策、绝不允许问人」，一旦启动诉求理解有偏差，后续 6 阶段可能连锁跑偏，7 流程产物质量下降甚至作废。 | 产物质量；用户信任 |
| Q-007 | **自主决策的可追溯性（衍生需求）**。用户最后才看效果，中间 `sddu-auto` 替用户做了哪些决策、依据是什么，若无记录则难以回溯与纠偏。 | 验收与纠偏效率 |

## 5. 假设与风险
> 记录问题挖掘过程中识别的假设和风险，供后续阶段验证和关注

### 5.1 关键假设
> 记录我们对问题理解所基于的假设，标注待验证项

| # | 假设内容 | 验证方式 |
|---|---------|---------|
| A-001 | 用户能在启动阶段一次性说清诉求（否则后续全自主会连锁跑偏） | 观察启动提问是否足以让用户完整表达问题/诉求 |
| A-002 | 简单项目的 spec/plan/tasks/build/review/validate 决策可由 `sddu-auto` 基于「启动诉求 + 项目上下文」安全自主答复 | 用「简单项目」样本实测自主决策的合理率 |
| A-003 | 用户接受「全程自主硬决策可能跑偏、产物质量下降」的风险（用户已明确选择 A：启动后绝不问人） | 已确认；后续若质量不满，用户会自行走 fast/auto/普通 sddu |

### 5.2 主要风险
> 识别可能影响问题判断或后续决策的风险因素

| # | 风险描述 | 影响程度 |
|---|---------|---------|
| R-001 | 全程自主硬决策跑偏 → 7 流程产物质量下降甚至作废 | 高 |
| R-002 | 与 Roadmap 原提案 FR-AUTONOMY-001（分级自主 L0/L1/L2 + 四维决策边界）方向不一致，需在 spec 阶段对齐：是替换、并存还是废弃原提案 | 中 |
| R-003 | 「拦截并重定向子 Agent 提问到 sddu-auto」在「不改变子 Agent 执行流程」约束下的实现可行性 | 中 |
| R-004 | 启动提问与执行全自主的边界切分（「启动」到「开始执行」的分界点如何定义） | 低 |
