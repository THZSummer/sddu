# ADR-019: 启动/执行边界切分点与启动提问充分性保障

## 状态

PROPOSED

## 背景

spec 的两个开放问题在此一并解决：

1. **开放问题 #4（R-004）**：「启动提问」与「执行全自主」的边界切分——从「启动」到「开始执行」的分界点如何定义。交互时序要求「启动阶段问清诉求（唯一人机交互点）→ 执行阶段所有问题由 sddu-auto 答复、绝不允许问人类」，因此需要一个**明确、可判定、无歧义**的切分点。
2. **开放问题 #1（A-001/NFR-001）**：启动提问的充分性如何保证——需覆盖哪些信息维度，才能支撑后续 6 阶段（spec→validate）的全自主决策。这直接决定执行阶段代答决策的质量上限（Q-004）。

## 决策

**1. 边界切分点定义**

| 阶段 | 起止 | 判据 |
|------|------|------|
| 启动阶段 | 用户调用 `@sddu-auto <feature>` 起 → 诉求采集完成 | sddu-auto 向用户提问（可多轮追问补全），用户答复 |
| 切分点 | 触发「进入执行」的明确信号 | 满足以下任一即切分：① 用户显式表态「开始执行 / 可以了 / 就这么做」；② sddu-auto 已采集到「最小充分信息集」（见下），且用户不再补充，静默超时即自动进入 |
| 执行阶段 | 切分点之后 → validate 完成 | sddu-auto 首次调度 discovery 子 Agent 起，全程自主，绝不问人 |

> 关键设计：**「最小充分信息集」自动触发进入执行**。即使用户不显式说「开始」，只要采满最小充分集，sddu-auto 也自动进入执行阶段——这符合「拿不准也硬决策、绝不问人」的整体精神，避免因等用户一句「开始」而卡在交互点。

**2. 启动提问充分性保障（结构化问卷 + 最小充分集）**

启动提问覆盖**六维信息**，其中前三项构成「最小充分信息集」（必采）：

| 维度 | 是否必采 | 内容 |
|------|:--:|------|
| ① 问题背景 | ✅ 必采 | 要解决什么问题、为什么需要、当前痛点 |
| ② 目标 | ✅ 必采 | 想要达成什么结果、成功标准 |
| ③ 范围 | ✅ 必采 | 做什么 / 明确不做什么（防止范围蔓延） |
| ④ 验收期望 | 尽量采 | 完成时如何判定满意、关键验收点 |
| ⑤ 技术偏好/约束 | 尽量采 | 技术栈、既定约束、外部依赖 |
| ⑥ 优先级/干系人 | 尽量采 | P0/P1/P2、目标用户 |

- 前三维必采：缺失任一项则启动阶段内追问补全（EC-001），补齐前不进入执行阶段。
- 后三维尽力采：用户表达不完整时，sddu-auto 在执行阶段基于项目上下文补全假设，不因缺项而反问。
- 采集结果固化为「自主执行上下文」，作为后续 6 阶段注入子 Agent 的决策依据。

## 后果

**正面**：
- 切分点明确可判定，消除「何时开始自主执行」的歧义（R-004 解决）。
- 六维结构化问卷 + 最小充分集，系统性保障 NFR-001「启动提问足以引导用户一次性完整表达诉求」，从源头提升执行阶段代答质量。
- 「最小充分集自动进入执行」避免交互卡点，契合「放手一次跑完」体验。

**负面**：
- 用户若敷衍填写必采维度，后续仍可能跑偏——属 NG-003 明确的 Non-Goal 范畴，由用户自行承担并改走其他入口。
- 「静默超时自动进入」需定义一个合理的等待窗口（如用户一轮答复后即判定采满与否），build 阶段需在 sddu-auto prompt 中明确该窗口规则。
