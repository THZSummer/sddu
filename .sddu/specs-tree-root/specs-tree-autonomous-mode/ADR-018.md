# ADR-018: 子 Agent 提问拦截重定向实现路径（Question 协议层拦截 + 代答）

## 状态

**ACCEPTED**（2026-08-15，由 TASK-001 spike 静态调研结论确认可行）

> **状态变更记录**：PROPOSED → ACCEPTED。TASK-001 spike（静态调研版）通过分析 `@opencode-ai/plugin`/`@opencode-ai/sdk` 1.16.2 类型声明、`.opencode/node_modules` 1.17.4 类型声明、以及 opencode 1.18.18 二进制（`opencode.exe`）strings 反编译，确认三项关键能力均存在（详见 §版本差异实测依据 与 spike 报告 `spike-decision-proxy.md`）。方案 D 落地通道判定为「插件 event hook 通道（首选）+ HTTP API 通道（备选）」，**无需降级方案 C**。

## 背景

本 Feature 的核心硬约束（用户已确认）：**子 Agent 零改动**（NG-001/FR-005），即在完全不修改 7 个子 Agent（discovery/spec/plan/tasks/build/review/validate）执行流程的前提下，让子 Agent 在执行阶段发起的提问，其「接收方」由用户变为 sddu-auto（FR-006），由 sddu-auto 代答而非透传给用户。且用户明确要求**可靠性必须 100% 保证**——「一定要实现 auto 代理决策」。

现有 7 个子 Agent 的 prompt 中，广泛存在「向用户提问 / 等待用户确认」的行为指令（discovery 访谈、spec 模糊点询问、plan 争议决策、build 方案确认、review/validate 策略确认）。这些提问行为「照常发生」是 spec 的明确要求（FR-005）。因此需要一种机制，在**不改动子 Agent prompt 文件**的前提下，把这些提问**确定性**地重定向给 sddu-auto 代答。

### 平台机制调研（opencode 1.18.18）

经官方文档（agents/tools/plugins 页）与二进制源码反编译调研，确认 opencode 的 question 工具是「事件驱动 + 异步等待 + 可代答」协议：

1. **Question.ask**（子 Agent 调用 question 工具时触发）：创建 deferred（未来值），登记 pending，发布 `question.asked` 事件（携带 `sessionID` + `requestID` + questions + tool 关联），然后**阻塞等待 deferred 被唤醒**。
2. **Question.reply(requestID, answers)**：唤醒 deferred，注入答案——子 Agent 的 question 工具拿到答案继续执行。
3. **Question.reject(requestID)**：唤醒 deferred 并抛 `QuestionRejectedError`（"The user dismissed this question"）。
4. 存在**代答通道**：`session.question.reply` / `session.question.reject` / `session.question.list` HTTP API；`@opencode/Question` service 导出 `ask/reply/reject/list` 方法。
5. 事件**可订阅**：源码存在 `B.event.on("question.asked", ...)` 订阅模式。

### 版本差异实测依据（TASK-001 spike，2026-08-15）

TASK-001 spike（静态调研）对比了三个版本环境，详见 `spike-decision-proxy.md`：

| 能力 | SDK 1.16.2（根 node_modules） | SDK 1.17.4（.opencode/node_modules） | opencode 1.18.18（运行时二进制） |
|------|:---:|:---:|:---:|
| v1 `Event` 联合含 question 事件 | ❌（grep 0 命中） | ❌（v1 仍不含；v2 含） | —（运行时事件流为 v2 形状 `{id,type,properties}`） |
| v2 `Event` 联合含 `question.asked/replied/rejected` | ❌ **v2 子路径损坏**（`v2/gen/` 缺 `types.gen.d.ts`/`sdk.gen.d.ts`/`index.d.ts`） | ✅ `EventQuestionAsked` 等完整声明（types.gen.d.ts L4482-4512，properties 含 `sessionID`） | ✅ 事件三件套存在（strings 14/14/13 命中） |
| `Question` 服务 client（list/reply/reject） | ❌（v1 sdk.gen.d.ts 0 命中） | ✅ v2 `Question`/`Question2`(session级) | ✅ `@opencode/Question` service + `get question()` 访问器 |

| 插件 `event` hook 收到 `question.asked` | **运行时可达**（1.18.18 把全部 server 事件派发给插件 `event` hook，仅按 location.directory 过滤） | 同左 | ✅ `V.event?.({event:{id,type,properties}})` 派发代码确认 |

**关键结论**：
- 运行时（1.18.18）插件 `event` hook 会收到 `question.asked`（含 `properties.sessionID`），**不依赖 SDK 类型是否声明**。
- 当前插件实际解析的是 `.opencode/node_modules` 的 **1.17.4**（Node 向上解析先命中），其 v2 子路径完整、Question 服务齐全；根 1.16.2 的 v2 已损坏。
- 落地需将依赖升级至 **≥1.17.4（推荐 1.18.x 对齐运行时）**，以获得 v2 类型与完整 `Question` 客户端方法；`Hooks.event` 的 v1 `Event` 类型仍不含 question，实现时用 v2 `Event` 类型或局部 cast 收窄。

## 决策

采用**方案 D：Question 协议层拦截 + 代答**。核心思路：**保留子 Agent 的提问行为，但在 question 工具的协议层确定性拦截，由 sddu-auto 代答**。

实现架构：
```
sddu-auto（主会话）
  ├── 启动阶段：结构化提问采集诉求（唯一人机交互点）
  └── 执行阶段：经 task 工具调度 7 个子 Agent
        子 Agent 调用 question 工具
          → question.asked 事件（sessionID 关联到子会话）
          → 决策代理层订阅 → 识别「这是 sddu-auto 调度的子会话提问」
          → LLM 自主决策答案
          → 调用 Question.reply(requestID, answers) 代答
          → 子 Agent 拿到答案继续执行（问题全程不到终端用户）
```

决策代理层的落地位置（按优先级，**已由 TASK-001 spike 证实**）：
1. **插件 event hook（首选）**：SDDU 本身是 opencode 插件，在返回的 Hooks 对象中注册 `event` 钩子，过滤 `event.type === "question.asked"`，识别 sddu-auto 调度的子会话提问（`event.properties.sessionID`），调用 `client.v2.session.question.reply({sessionID, requestID, questionV2Reply})` 代答。进程内实现，无需 server 模式。**已证实 1.18.18 运行时会把 question.asked 派发给插件 `event` hook。**
2. **HTTP API（备选）**：`POST /api/session/{sessionID}/question/{requestID}/reply` 路由在 1.18.18 二进制中确认存在（`session.question.reply`），需 opencode 运行在 server 模式，插件经 `serverUrl` 调用。**已证实路由存在。**

sessionID 关联机制：sddu-auto 经 task 工具调度子 Agent 时记录子会话 sessionID（task 返回的 task_id 或子会话标识），决策代理层据此匹配 question 事件的 `properties.sessionID`，精确识别「该代答哪个提问」。**已证实 `question.asked` 事件携带 sessionID（QuestionRequest = `{id, sessionID, questions, tool?}`）。**

**明确否决**：
- 方案 A（上下文指令注入）：靠 prompt 劝子 Agent「别问」，可靠性依赖 LLM 指令遵从度，非 100%，用户明确不同意。
- 方案 B（调度层后置拦截）：识别子 Agent 输出中的「提问」文本再代答，依赖提问语义识别精度，且无法覆盖「子 Agent 提问后阻塞等待」情形，可靠性不达标。
- 方案 C（双会话代理 resume）：作为备选保留，仅当方案 D 的插件通道实测不可行时启用。

## 后果

**正面**：
- **可靠性 100%**：拦截在 question 工具的协议层，子 Agent 无论怎么提问都被确定性路由到代理层，代理层不给答案它就走不下去——完全不依赖「子 Agent 听不听话」。
- **严格符合原始诉求**：保留子 Agent 的提问行为（它本来就需要在决策点发问），仅把「回答者」从用户换成 sddu-auto，语义精确对应「后面的 agent 的问题都由 auto agent 去决策」。
- **子 Agent 零改动**：7 个子 Agent 的 prompt 文件一个字符不改，其提问行为照常发生（FR-005）。
- **有源码依据**：question.asked 事件、reply 代答通道、session.question.reply API 均在 opencode 1.18.18 源码中确认存在。

**负面与需验证点**（TASK-001 spike 已静态证实，剩余为落地实现事项）：
- **插件 API 签名已确认**：1.18.18 运行时插件 `event` hook 接收 `{event: {id, type, properties}}`，question.asked 经此派发；代答可走 `client.v2.session.question.reply` 或 HTTP API `session.question.reply`。**落地前置**：SDK/插件依赖升级至 ≥1.17.4（推荐 1.18.x 对齐运行时）；`Hooks.event` 的 v1 `Event` 类型不含 question，需用 v2 `Event` 类型或局部 cast 收窄。具体签名以 TASK-003 实现时最小样本验证为准。
- **sessionID 关联方式已证实**：`question.asked` 事件 properties 含 `sessionID`，与 task 工具子会话 sessionID 匹配可行（必要时用 `Session.children` 辅助维护映射表）。具体映射实现留待 TASK-003。
- **决策质量依赖启动充分性**：代答答案的质量取决于启动采集的诉求上下文，由 ADR-019 的结构化问卷保障。

## TASK-001 spike 结论（2026-08-15）

三项调研结论（证据详见 `spike-decision-proxy.md`）：
1. **question.asked 可订阅**：✅ 1.18.18 运行时把全部 server 事件（含 question.asked）派发给插件 `event` hook（`V.event?.({event:{id,type,properties}})`，仅按 location.directory 过滤）；SDK 1.16.2 类型未声明，需升级 SDK ≥1.17.4 获得 v2 类型。
2. **reply 代答通道**：✅ `session.question.reply` HTTP 路由（`/api/session/{sessionID}/question/{requestID}/reply`）与 `@opencode/Question` service（reply/reject/list）在 1.18.18 二进制确认存在；v2 SDK（1.17.4）提供 `client.question.reply` 与 `client.v2.session.question.reply`。当前 1.16.2 无 client 级通道（v2 损坏），需升级。
3. **sessionID 关联**：✅ `question.asked` 事件携带 `sessionID`（QuestionRequest = `{id, sessionID, questions, tool?}`），与 task 子会话关联可行。

**落地路径判定**：插件 event hook 通道（首选，进程内、无需 server 模式）+ HTTP API 通道（备选，需 server 模式）。**方案 C 不触发**。
