# ADR-018: 子 Agent 提问拦截重定向实现路径（协议层拦截 + 插件内决策会话代答，方案 E）

## 背景

本 Feature 的核心硬约束（用户已确认）：**子 Agent 零改动**（NG-001/FR-005），即在完全不修改 7 个子 Agent（discovery/spec/plan/tasks/build/review/validate）执行流程的前提下，让子 Agent 在执行阶段发起的提问，其「接收方」由用户变为 sddu-auto（FR-006），由 sddu-auto 代答而非透传给用户。且用户明确要求**可靠性必须 100% 保证**——「一定要实现 auto 代理决策」。

现有 7 个子 Agent 的 prompt 中，广泛存在「向用户提问 / 等待用户确认」的行为指令（discovery 访谈、spec 模糊点询问、plan 争议决策、build 方案确认、review/validate 策略确认）。这些提问行为「照常发生」是 spec 的明确要求（FR-005）。因此需要一种机制，在**不改动子 Agent prompt 文件**的前提下，把这些提问**确定性**地重定向给 sddu-auto 代答。

**更关键的是「代答」的质量来源**：用户原始诉求是「后面的 agent 的问题都由 **auto agent 去决策**」——即答案应来自 sddu-auto 的 LLM 思考，而非某个协议层组件的规则匹配。这要求：拦截机制（协议层确定性）与决策机制（sddu-auto 真思考）解耦。

### 平台机制调研（opencode 1.18.18）

经官方文档（agents/tools/plugins 页）与二进制源码反编译调研，确认 opencode 的 question 工具是「事件驱动 + 异步等待 + 可代答」协议：

1. **Question.ask**（子 Agent 调用 question 工具时触发）：创建 deferred（未来值），登记 pending，发布 `question.asked` 事件（携带 `sessionID` + `requestID` + questions + tool 关联），然后**阻塞等待 deferred 被唤醒**。
2. **Question.reply(requestID, answers)**：唤醒 deferred，注入答案——子 Agent 的 question 工具拿到答案继续执行。
3. **Question.reject(requestID)**：唤醒 deferred 并抛 `QuestionRejectedError`（"The user dismissed this question"）。
4. 存在**代答通道**：`session.question.reply` / `session.question.reject` / `session.question.list` HTTP API；`@opencode/Question` service 导出 `ask/reply/reject/list` 方法。
5. 事件**可订阅**：源码存在 `B.event.on("question.asked", ...)` 订阅模式。

**关键运行实证结论（`verify-decision-proxy.md` 二轮）**：
- 拦截 → 识别 → 决策 → 代答四步闭环在真实 serve 运行时**已成立**（`decision_count=1`，子 Agent 拿到代答答案继续）。
- 运行时插件 `client` 为 **v1 形态**（成员 global/project/session/app/…，无 v2 / 无顶层 question 访问器）；真实可用代答通道是**全局端点 `POST /question/{requestID}/reply`**（body `{answers}`）。
- **「决策」环节当时用的是 `DecisionEngine` 规则匹配**（关键词 `haystack.includes(label)` / 选首项 / 保守默认），**答案未经 LLM 思考**——这正是本 ADR 要修正的偏离。

### 方案 B 反编译否决依据（`verify-prompt-interrupt.md`，v4.1 新增）

方案 B 的落地依赖「向阻塞等待 task 的 sddu-auto 主会话注入 `prompt_async` 消息并能打断、触发新一轮思考」。该先决条件经反编译 opencode 1.18.18 二进制**实证否决**：

1. **消息排队模型（不打断）**：Runner 状态机 `SessionRunState.ensureRunning` 在 `case"Running"` 分支返回 `y(m.run.done)` —— 会话 busy 时新消息仅 FIFO 排队，等待当前 run 完成，**不 interrupt 当前 fiber**（offset 96284855）。
2. **唯一打断路径是 `cancel`**：仅由 abort 通道（`SessionHttpApi.abort` / 用户 Esc）触发，语义为「取消整个当前 turn」（`handleSubtask` 的 `onInterrupt` 会 `L.abort()` 连带取消子任务），**不是**「插入新消息优先处理再恢复」。
3. **死锁闭环**：sddu-auto 主会话 turn 运行中（Runner=Running）→ `yield* handleSubtask → TaskTool.execute → s.raceFirst(e.wait)` 阻塞等待子 Agent → 子 Agent `Question.ask` 阻塞等待 reply → decision-proxy 注入的 `prompt_async` 消息排队等待主会话当前 turn 完成 → 当前 turn 完成前提是 task 返回（= 子 Agent 完成 = question 得到回答）→ 循环依赖。
4. **task 后台模式存在（B' 依赖）**：`TaskTool` 结构含 `background: optional(Boolean)`（offset 96579137），后台模式返回 `output:{state:"running"}` 并 forkIn 运行；`e.wait({id})` 支持提交后异步查询状态——这是变体 B' 的机制基础（现随 B' 一并降级为备选）。

### 方案 E 调研依据（`research-agent-reply.md`，v4.2 新增）

变体 B' 的全部复杂度源于一个被反编译定论的死锁事实：sddu-auto 主会话阻塞等待 task 时无法被打断，因此「让主会话亲自思考」只能通过「后台 task 提交 + 轮询 + 间隙响应」绕开。调研（`research-agent-reply.md`）进一步确认 opencode question 工具本质是「**事件 + deferred 异步等待 + 任意 actor 可代答**」的原生协议（`QuestionV2.ask → question.asked → QuestionV2.reply 解析 deferred → 子 Agent 拿到答案继续`），并据此发现**方案 E**：

- **无死锁**：决策会话是独立 session，`session.prompt` 走 `ensureRunning` 的 Idle 分支正常启动新 run（反编译确认 Idle 分支可用）；被阻塞等待的是子 Agent 会话，不是决策会话。方案 B 的死锁闭环被完全绕开。
- **无轮询、无队列**：决策是「事件驱动 + 同步等待一次 LLM」的单次往返，延迟 ≈ 一次 LLM 思考时长（数秒），远优于 B' 的「轮询间隔 + 思考时长」。
- **无需改写 sddu-auto 调度循环**：方案 E 对主会话 sddu-auto 模板**零改动**（照旧同步阻塞等待 task），子 Agent 也零改动（FR-005 保持）。
- **「答案来自 sddu-auto 的 LLM 思考」语义成立**：决策会话使用**同一 agent 定义（sddu-auto）+ 同一模型**，种子上下文与 B' 要素 ③ 要求注入的内容一致（启动诉求 + 项目上下文 + 上游产物）。唯一区别是会话实例不同——这是死锁约束下必然的取舍。
- **插件 client 具备机制基础**：插件 v1 client 有 `session` 命名空间（`list/create/get/prompt/message/...` 全量），且插件 `event` hook 派发是 fire-and-forget（`v.sync(...)` 不 await 插件 Promise），插件可在回调里 `await client.session.prompt(...)` 做同步 LLM 思考而不阻塞服务端事件派发。

## 决策

采用**方案 E：协议层拦截 + 插件内同步决策会话代答**。核心思路：**保留「拦截 + 识别」机制（方案 D 已被实证的部分），把「决策」职责回传给 sddu-auto（真 LLM 思考），但传递通道由「注入打断 / 队列中转」改为「插件内独立决策会话同步思考」**——用插件 v1 client 的 `client.session.create()` 开/复用独立「决策会话」（agent=sddu-auto，注入种子上下文），`client.session.prompt()` 同步等其 LLM 真思考（决策会话 idle、无死锁），答案经全局端点 `POST /question/{requestID}/reply` 代答，30s 超时降级规则匹配兜底。

> **命名说明**：历史上「方案 B」曾指「调度层后置拦截」（识别子 Agent 输出文本中的「提问」再代答，已否决）。v4.0 起「方案 B」重新定义为「协议层拦截 + 回传 sddu-auto 思考」（prompt_async 注入打断）。v4.1 起，方案 B 因 prompt_async 死锁被反编译否决，其设计意图由**变体 B'** 承接（「回传 sddu-auto 思考」不变，「注入打断」改为「后台 task + 轮询 + 间隙响应」）。v4.2 起，调研发现原生代答协议后确定**方案 E**——「换一个不阻塞的会话思考」（独立决策会话同步代答），变体 B' 降级为备选。方案 D 的「拦截 + 识别」机制被继承，方案 D 的「规则匹配决策」被否决（降级为 30s 超时兜底）。

实现架构：
```
sddu-auto（主会话，唯一调度者，照旧同步等待 task，零改动）
  ├── 启动阶段：结构化提问采集诉求（唯一人机交互点）
  └── 执行阶段：经 task 工具调度 7 个子 Agent（同步等待，零改动）
        子 Agent 调用 question 工具
          → question.asked 事件（sessionID 关联到子会话）
          → 决策代理层订阅 → 识别「这是 sddu-auto 调度的子会话提问」
          → ┌──── 决策代理层（插件 event hook 内，async）────────────┐
            │ ① client.session.create() 建/复用「决策会话」          │
            │    （agent=sddu-auto，注入种子上下文：                 │
            │     启动诉求 + 项目上下文 + 上游产物）                  │
            │ ② client.session.prompt() 同步等 LLM 真思考           │
            │    （决策会话 idle、无死锁）                           │
            │ ③ 解析答案 → 全局 reply 代答                          │
            └────────────────────────────────────────────┘
          → ④ POST /question/{requestID}/reply（body {answers}）
               （30s 超时 → 降级 DecisionEngine 规则匹配，NFR-003 不阻塞）
          → QuestionV2.reply 解析 deferred → 子 Agent 拿到答案继续执行
            （问题全程不到终端用户）
```

### 五要素可落地机制

**要素 ① —— 决策会话创建（session.create，缓存复用）**：decision-proxy 拦截 `question.asked` 后经 `SessionRegistry.getAutoParent(sessionID)` 确认是 sddu-auto 调度的子会话提问（`autoRoots` 已登记，识别机制不变）。用插件 v1 client 的 `client.session.create({ body: { agent: "sddu-auto", ... } })` 创建「决策会话」；**首次创建后缓存 sessionID，后续决策点复用同一长生命周期决策会话**（避免反复建会话的开销）。决策会话注入**种子上下文**：启动诉求（auto-context.json）+ 项目上下文 + 上游产物（等价 B' 要素 ③ 要求注入的内容）。

**要素 ② —— 思考（session.prompt，同步等待，Idle 分支无死锁）**：用 `client.session.prompt({ path: { id: 决策会话ID }, body: { agent: "sddu-auto", parts: [种子上下文 + 问题全文 + 选项] } })` 触发决策会话 LLM 真思考，**同步等待完整回答**（decision-proxy 在插件 event hook 内 async 处理，`event` hook 派发是 fire-and-forget，await 不阻塞服务端事件派发）。决策会话 idle（非阻塞中的主会话），`session.prompt` 走 Idle 分支正常启动新 run，无死锁。

**要素 ③ —— 答案回传（全局 reply 代答）**：从决策会话回答中解析答案（单题 → 选中 label；多选题 → label 数组；自由文本 → 保守默认）。代答走**全局端点 `POST /question/{requestID}/reply`**（body `{answers}`，运行实证可靠）；备选：插件自建完整 SDK client 后走 `client.question.reply`（需 `@opencode-ai/sdk` 依赖，见后果「新增 build 验证点」）。requestID 直接复用 `question.asked` 事件的 `properties.id`，天然唯一且与 reply 关联。

**要素 ④ —— 30s 超时兜底（NFR-003 不阻塞、不反问）**：decision-proxy 对每次「决策会话思考」设超时（**30s**）。超时未拿到决策会话回答 → 降级为**规则匹配兜底**（复用现有 `DecisionEngine`：有选项选关键词匹配项/首项，无选项返回保守默认答案），保证子 Agent 的 question 工具不被无限阻塞。兜底答案同样写入 `auto-decisions.md`，标注「⏱ 超时兜底（决策会话未在 30s 内响应）」。

**要素 ⑤ —— 决策追溯（标注「决策来源：sddu-auto 决策会话」）**：代答答案 + 依据仍由 decision-proxy 写入 `auto-decisions.md`（生产者 = decision-proxy，与 ADR-020 架构结论一致）。追溯字段标注「决策来源」：`sddu-auto 决策会话`（真 LLM 决策）vs `超时兜底（规则匹配）`，供用户区分决策质量。

### 落地位置（继承方案 D 已实证的通道）

1. **插件 event hook（拦截 + 识别，已实证）**：SDDU 插件在 Hooks 对象注册 `event` 钩子，过滤 `event.type === "question.asked"`，经 `SessionRegistry` 识别 sddu-auto 子会话（`event.properties.sessionID`）。
2. **决策会话（方案 E 新增）**：插件 v1 client 的 `client.session.create()` 建/复用独立「决策会话」（agent=sddu-auto，种子上下文），`client.session.prompt()` 同步 LLM 思考——替代 B' 的「队列 + 轮询」。
3. **代答通道（已实证）**：全局端点 `POST /question/{requestID}/reply`（body `{answers}`），保留插件自建完整 SDK client 走 `client.question.reply` 作为「进程内优先」的兼容探测（见后果「新增 build 验证点」③）。

**明确否决**：
- 方案 A（上下文指令注入）：靠 prompt 劝子 Agent「别问」，可靠性依赖 LLM 指令遵从度，非 100%，用户明确不同意。
- 旧「调度层后置拦截」（识别输出文本中的「提问」）：依赖提问语义识别精度，无法覆盖「提问后阻塞等待」，可靠性不达标。
- **方案 D 的「规则匹配决策」**：`DecisionEngine` 关键词匹配/选首项/保守默认，答案未经 LLM 思考，违背「LLM 自主决策」设计意图——**决策环节否决，但其「拦截 + 识别」机制被继承**。
- **方案 B（prompt_async 注入打断）**：经反编译实证否决——会话 busy 时注入消息仅排队、`cancel` 为取消整个 turn 语义，构成死锁（详见「背景」与 `verify-prompt-interrupt.md`）。其「回传 sddu-auto 思考」的设计意图由方案 E 承接。
- **变体 B'（后台 task + 轮询 + 间隙响应）**：降级为备选（仅当「决策必须发生在主会话同一实例」强约束时保留）。其全部复杂度源于被反编译定论的死锁事实（主会话阻塞等待 task 无法被打断），方案 E 用独立决策会话直接消解该问题。
- 方案 C（双会话代理 resume）：作为方案 E 不可行时的最终退路。

## 后果

**正面**：
- **恢复「LLM 自主决策」设计意图**：答案来自 sddu-auto 的 LLM 真思考（独立决策会话，同 agent 定义 + 同模型），而非协议层规则匹配，决策质量上限最高（对应 spec Q-004）。
- **决策者与上下文持有者语义合一**：决策会话使用 sddu-auto 的 agent 定义与种子上下文（启动诉求 + 项目上下文 + 上游产物），语义上等价「答案来自 sddu-auto 的 LLM 思考」。
- **决策代理层职责收敛**：decision-proxy 只做「拦截 + 识别 + 建决策会话 + prompt 思考 + reply 代答 + 超时兜底」的确定性管道，不持有模型、不重建推理上下文，职责清晰可测。
- **可靠性 100%**：拦截仍在 question 工具协议层，子 Agent 无论怎么问都被确定性路由；30s 超时兜底保证 NFR-003 不阻塞。
- **子 Agent 零改动 + 主会话零改动**：7 个子 Agent prompt 一个字符不改（FR-005）；sddu-auto 主会话照旧同步等待 task（无需调度循环改造）；**权限模型不变**（sddu-auto 保持 `edit: deny` / `bash: deny`）；**SessionRegistry 识别机制不变**（拦截职责保留）。
- **无队列、无轮询、无注入打断**：方案 E 相比变体 B' 少了一个完整的机制层（队列/轮询/调度循环改造），复杂度更低、延迟更低（≈ 一次 LLM 思考往返）、对现有模板侵入面更小。

**负面与需验证点（技术风险章节）**：

✅ **核心风险 1 —— opencode 打断能力依赖（方案 B 先决条件，已反编译否决）**：

`prompt_async` 在会话 busy（阻塞等待 task）时仅 FIFO 排队、不打断，唯一打断 `cancel` 为取消整个 turn 语义——方案 B 死锁不可行（反编译证据见 `verify-prompt-interrupt.md` §2.2/§3）。**已决定走方案 E**，该风险消除。

✅ **核心风险 2 —— 变体 B' 调度循环改造复杂度（已消解）**：B' 需把 sddu-auto 调度改为「后台 task + 轮询 + 间隙响应」，复杂度显著。方案 E 用独立决策会话消解该问题，主会话零改动，该风险消除。

⚠️ **风险 1（方案 E 新增）—— 决策会话生命周期管理**：新增「决策会话」的创建/复用/清理管理（首次创建缓存 sessionID，长生命周期复用）。缓解：决策会话与主会话同生命周期（主会话结束即清理）；创建失败降级超时兜底，绝不阻塞代答。

**风险 2 —— 延迟**：代答延迟从规则匹配的 ~26ms 升至 LLM 思考的**数秒级**。可接受——决策点非高频路径，子 Agent 处于阻塞等待，延迟不影响正确性；30s 超时兜底保证上限。

**风险 3 —— LLM 成本**：每个决策点消耗一次决策会话的 LLM 推理，长流程决策点多则 token 成本上升。属「真思考」的必然成本，换取决策质量；超时兜底为规则匹配（零额外 LLM 成本）作为降级下限。

**风险 4 —— 并发**：同一时刻多个子 Agent 提问时，多个决策会话 prompt 并发。按 requestID 的 pending map 去重（已答的 requestID 再 reply 会 404，天然幂等）；sddu-auto 调度本就「单任务单阶段串行」（模板 §5.2 规则 4），实际并发场景极低。

**新增 build 阶段验证点（✅ 已由 TASK-008 spike 实证解决，见 `spike-decision-session.md`）**：
1. ✅ **session.create / prompt body 形状**：TASK-008 spike 运行时实证——`session.create({ body: { agent, title } })` 的 `agent` 字段运行时**接受并存储**（SDK 类型未声明但透传接受）；`session.prompt({ path: {id}, body: { agent: "sddu-auto", parts: [{type:"text",text}] } })` 同步等待 10.5s 拿到完整回答（`data.parts` 含 text），决策会话 idle、无死锁、一次 LLM 往返成功；同一会话连续两次 prompt 复用无死锁。
2. ✅ **决策会话权限**：TASK-008 spike 实测——决策会话（agent=sddu-auto）read ✅ 可用、edit ❌ deny、bash ❌ deny（写入目标文件未生成，非仅口头汇报）；权限由 `session.prompt` 的 `body.agent: "sddu-auto"` frontmatter 决定，TASK-009 必须显式传 `agent`。
3. ✅ **插件依赖 @opencode-ai/sdk 可解析性**：TASK-008 spike 实测——`@opencode-ai/sdk`（v1）与 `@opencode-ai/sdk/v2` 均可在插件内 import；v2 `client.question.reply` 为 function（全局代答 SDK 通道），但插件注入 v1 client 无 question 命名空间、自建 v2 client 需声明依赖。**代答通道判定：HTTP 全局端点 `POST /question/{requestID}/reply` 为主通道（已实证 + 零依赖），SDK v2 client 仅作可选备选（收益低，不建议本期引入）**。

**已解决项**：插件 API 未暴露 question 代答能力（原方案 D 主要风险）已被 `verify-decision-proxy.md` 二轮实证缓解——拦截→识别→代答闭环成立，reply 走全局端点 `POST /question/{requestID}/reply`；方案 B 打断能力依赖已由 `verify-prompt-interrupt.md` 反编译否决并转方案 E；变体 B' 的调度循环改造复杂度已由方案 E 消解（`research-agent-reply.md` 调研）。
