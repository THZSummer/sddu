# ADR-012: 治理诉求不进内核——CODEOWNERS 与审计字段拒绝，治理走钩子扩展点（评估 B2 拒绝）

## 状态
PROPOSED（2026-11-24 用户拍板：拒绝）

## 背景
多视角评估（企业 monorepo 视角）对 v6 提出两项治理诉求：

1. **本体保护**：`.sddu/.sddu/`（本体）躺在 workspace 内，团队成员日常提交可能随手修改方法论内核，企业希望本体变更强制走 CODEOWNERS 审批。
2. **审计追溯**：`state.md` 的 phase 迁移（如 registered→speced）缺少 who/when 审计字段，企业合规希望内核记录审计轨迹。

## 决策
**两项诉求均拒绝，治理不进内核**。理由：

1. **CODEOWNERS 是平台特定治理机制**（GitHub/GitLab/Bitbucket 语法与路径各异）——将其纳入 SDDU 安装范围即引入平台指针，直接违反 ADR-006「平台中立」。且 CODEOWNERS 本质是**用户仓库的治理决策**，不是 SDDU 的分发物。
2. **审计字段膨胀机器状态契约**——在 `state.md` front-matter 增加 who/when 字段违反 ADR-005 的字段契约收敛方向；且 AI-Agent 场景下「who」往往是「某个会话」，语义稀薄。审计是业务治理需求，不是方法论本质（违反 D 判据：元数据不是状态）。
3. **钩子机制本身就是治理扩展点**——`.sddu-config/` 的 `sddu-<stage>-{before,after}.md` 钩子正是为此设计：企业若需审计，在 `sddu-<stage>-after.md` 钩子中写入记录动作即可；若需本体保护，在用户侧自行将 `.sddu/.sddu/` 纳入其平台的 CODEOWNERS（用户决策、零机制耦合）。

## 后果
- 正面：内核保持零治理假设；state.md 契约不膨胀；平台中立不被打破；企业治理诉求仍可经钩子满足（能力不缺失，只是不代劳）。
- 负面：企业用户需自行组装治理（CODEOWNERS 自己配、审计钩子自己写）——已判定为可接受：SDDU 的定位是方法论内核，不是治理框架。
- 不可逆性：无——本 ADR 仅固化「不纳入」的决策；未来若 v7（质量闭环）重新评估，钩子机制已留好接缝。
