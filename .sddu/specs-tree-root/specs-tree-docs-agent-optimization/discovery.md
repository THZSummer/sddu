## 1. 问题定义
> 概括核心问题及其业务影响，回答"为什么需要关注"

| 核心问题 | 业务影响 | 不解决的成本 |
|---------|---------|------------|
| @sddu-docs 是 SDDU 框架中唯一的半成品 Agent — 指令模板为占位骨架、§5 工作流程标注「待后续 Feature 定义」、无输出模板、无产物落盘机制 | @sddu-docs 无法在生产中使用，用户少了一个了解项目全貌的关键入口；SDDU 框架 11 个 Agent 的一致性承诺被破坏（10 个完整 vs 1 个半成品） | 用户入职新项目或接手已有项目时，无法通过 SDDU 工作流快速获取项目全景。每次需要人工翻阅代码建立心智模型，效率低且信息碎片化 |
| @sddu-docs 与其他辅助 Agent（@sddu-tree、@sddu-roadmap）的边界不清晰 — 三者都在扫描 `.sddu/` 并产出项目级文档，存在职责重叠风险 | 用户不知何时该 @sddu-docs vs @sddu-tree vs @sddu-roadmap，Agent 之间可能产生重复劳动或信息不一致 | 随着框架演进，三个 Agent 各自扩张职责范围，最终导致「一个项目全景三份文档」的信息冗余和碎片化问题 |

## 2. 用户画像
> 描述受影响用户角色及其场景，回答"谁遇到了什么问题"

| 用户角色 | 典型场景 | 关键痛点（用户原话） | 当前应对方式 |
|---------|---------|-------------------|------------|
| **SDDU 框架开发者**（当前维护者） | 需要补全 @sddu-docs 以补齐 11 Agent 体系闭环；运行 `@sddu-docs` 发现只能做对话级输出，无法落盘 | 「@sddu-docs 当前只能做对话级输出，无法被下游消费」 | 不调用，问题搁置 |
| **新项目入职者** | 接手一个已有 SDDU Feature 的项目，需要快速了解项目的业务模块、API 面、技术架构 | 「打开项目，面对多个 spec.md / plan.md，没有一个文档告诉我全局是怎样的」 | 逐个打开 Feature 目录的 spec.md / plan.md，手动拼接全貌，耗时且容易遗漏 |
| **架构决策者** | 需要做跨 Feature 的技术决策（如统一错误处理、全局状态管理），但没有一份文档描述当前系统的技术全貌 | 「ROADMAP.md 告诉我要做什么，TREE.md 告诉我文件在哪，但没人告诉我当前系统实际长什么样」 | 依赖 @sddu-roadmap 的 ROADMAP.md（侧重规划而非现状）和手动代码阅读 |
| **AI Agent（下游消费者）** | @sddu-tree 在每次 Agent 完成后被自动调用，「希望完成后也能自动同步项目全景文档」 | 同一触发机制未能延伸到项目全景文档的生产 | 无自动化，项目全景文档不会在每次变更后更新 |

## 3. 问题清单
> 按影响程度分级梳理所有识别到的问题，每项赋予唯一编号 Q-xxx

### 3.1 核心问题
> 影响面大、频率高、用户强烈感知

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-001 | **§5 工作流程缺失 — Agent 无执行指南**：`src/templates/agents/sddu-docs.md.hbs` 的 §5 工作流程节仅包含一行占位文字「待后续 Feature 定义（本模板仅为占位骨架）」。Agent 被调用时没有任何工作流步骤可供遵循 — 不知道应该扫描哪些目录、读取哪些文件、生成什么结构、以什么顺序执行。这意味着 Agent 注册了但不具备可执行能力。 | 所有调用 @sddu-docs 的场景；框架完整性 |
| Q-002 | **输出模板缺失 — 无产物格式定义**：`src/templates/outputs/` 目录下仅有 7 个核心流水线 Agent 的输出模板（discovery / spec / plan / tasks / build / review / validate），不存在 `sddu-docs.md.hbs`。当前 §6 虽然定义了用户自定义模板和插件内置模板的查找优先级，但两处都不存在该文件 — Agent 按规则会「显式报错，不要自行编造输出格式」。 | @sddu-docs 的输出生产链路中断 |
| Q-003 | **无产物落盘机制 — 只有对话级输出**：7 个核心流水线 Agent 都将产物写入 Feature 目录（discovery.md、spec.md 等）；@sddu-tree 写入各层级 TREE.md；@sddu-roadmap 写入 `.sddu/ROADMAP.md`。@sddu-docs 当前没有定义产物写入路径，只能输出到对话窗口，无法被下游 Agent 或用户引用。 | 下游消费（@sddu-tree 的自动触发引用、用户查看、其他 Agent 参考）全部不可行 |

### 3.2 次要问题
> 影响面中等、或为核心问题的衍生问题

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-004 | **产物定位模糊 — Feature 级 vs 项目级**：当前指令模板 §1 描述 @sddu-docs 输出「项目业务与技术全景视图」，暗示项目级产物。但 §6 的输出模板查找逻辑（`.sddu/templates/agents/output/` → `.opencode/plugins/sddu/templates/output/`）暗示与 Feature 级 Agent 共享同一模板查找路径。产物到底是落在特定 Feature 目录（如 `specs-tree-xxx/docs.md`）还是落在项目公共目录（如 `.sddu/docs/`、`.sddu/PROJECT_OVERVIEW.md`）？这一模糊性阻碍了输出模板和落盘路径的设计。 | 输出模板设计；落盘路径规划；@sddu-tree 的自动触发配置 |
| Q-005 | **与 @sddu-tree 的边界未显式声明**：两者都扫描 `.sddu/` 目录和 Feature 产物。@sddu-tree 负责「目录导航」— 每个目录生成 TREE.md、文件简介、phase 进度条。@sddu-docs 负责「项目全景」— 业务模块全景与技术架构全景。但目前两者的职责边界只是在各自的 §7 规则中用一句话提及（如 @sddu-tree §8：「不进行版本规划」），缺少精确的输入/输出/消费关系定义。例如：@sddu-tree 读取 state.json 生成 phase 进度条 → @sddu-docs 是否应该复用而非重新扫描？ | 两个 Agent 的调用者；框架指令维护者 |
| Q-006 | **与 @sddu-roadmap 的边界存在表述冲突**：@sddu-roadmap 在 §2 职责边界中声明「不输出版本路线图」（疑为笔误 — roadmap 本身就输出路线图），其 §1 描述为「协调多个功能特性的长期发展路线图」。@sddu-docs 描述为「项目业务与技术全景视图」。但 ROADMAP.md 实际输出包含大量「项目状态速览、Feature 全量扫描、文件覆盖率检查」等当前状态内容，与 @sddu-docs 的「业务全景」存在重叠。需要明确：ROADMAP.md 中的当前状态扫描是否应剥离给 @sddu-docs 负责。 | 用户不知道该看哪份文档获取项目当前状态；两份文档可能出现信息不一致 |
| Q-007 | **用户自定义模板覆盖路径已声明但未实现**：§6 声明了用户自定义模板路径 `.sddu/templates/agents/output/sddu-docs.md.hbs` 和兜底路径 `.opencode/plugins/sddu/templates/output/sddu-docs.md.hbs`，但标注为「当前预留，尚未实现」。7 个核心流水线 Agent 的模板覆盖机制已在 FR-TPL-001（模板质量统一）中标准化，@sddu-docs 是否能复用该机制，需要明确。 | 未来需要自定义 @sddu-docs 输出格式的用户 |

### 3.3 潜在问题
> 目前影响小但可能恶化，或信息不足待验证

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-008 | **§9 示例对话与实际能力不一致**：指令模板 §9 示例对话展示了 Agent 响应流程（确认范围 → 扫描代码 → 生成全景 → 完成报告），但该流程在当前骨架状态下无法执行。一旦 §5 工作流程和输出模板补全，需同步验证示例对话与实际工作流的一致性。 | 用户期望管理 |
| Q-009 | **与其他辅助 Agent 的自动触发协调**：@sddu-tree 已在 8 个主流程 Agent 执行完成后自动触发（§5：「8 个主流程 Agent 执行完成后自动调用」）。@sddu-docs 是否也需要类似的自动触发机制？如果两者都在同一时机触发，执行顺序是什么？会不会互相等待或产生竞态？ | 框架自动化完整性；主流程 Agent 的执行后等待时间 |
| Q-010 | **业务全景扫描的能力边界待定义**：§7 规则要求业务全景覆盖「模块、功能、API、页面、数据表、业务对象及关联」。对于当前 SDDU 插件项目（一个 CLI/Agent 框架，无页面、无数据表），这些维度中哪些适用、哪些不适用？不同项目类型（Web 应用 vs CLI 工具 vs 库）需要的全景维度不同，Agent 如何自适应？ | 不同类型项目的全景文档适用性 |

## 4. 竞品参考
> 记录竞品对类似问题的处理方式，回答"别人怎么做的、我们有什么不同"

| 竞品 | 是否处理过类似问题 | 处理方式 | 与我们场景的差异 |
|------|-------------------|---------|----------------|
| **Storybook** | 是 — 自动生成组件全景文档 | 扫描项目源码中的 components/ 目录，自动提取 Props/Events/Slots，生成交互式组件目录。通过 `stories` 文件描述组件状态，`DocsPage` 自动聚合为项目组件全景 | Storybook 高度专业化于 UI 组件，自动提取依赖 AST 解析和框架约定；SDDU @sddu-docs 面向更广泛的产物类型（不限于组件）|
| **Docusaurus / VuePress** | 是 — 从 Markdown 自动生成文档站点 | 基于文件系统路由，自动将 Markdown 文件组织为侧边栏导航和文档站点。插件机制支持从源码注释生成 API 文档 | 这些是通用文档框架，不关心「项目全景」的语义（业务模块 vs 技术架构）；SDDU @sddu-docs 需要做语义化的聚合和理解 |
| **Backstage (Spotify)** | 是 — 软件目录和技术文档一体化 | 通过 `catalog-info.yaml` 注册组件，自动聚合所有组件的技术文档、API 规范、依赖关系为一个统一的开发者门户 | Backstage 依赖手动注册（YAML 配置）；SDDU @sddu-docs 应从已有产物（spec/plan）自动推导，而非要求额外配置 |
| **Structurizr DSL** | 是 — 从代码结构生成架构图 | 通过解析代码的模块依赖关系，自动生成 C4 模型架构图（Context / Container / Component / Code） | Structurizr 专注架构可视化；SDDU @sddu-docs 需要更广泛的全景（业务 + 技术），架构图只是其中一部分 |
| **@sddu-tree（内部参考）** | 部分类似 — 扫描目录生成导航 | 扫描 `.sddu/` 目录结构，读取文件前 20 行生成简介，按层级生成 TREE.md | @sddu-tree 是「目录导航」— 告诉你有什么文件和它们的简介；@sddu-docs 需要「语义聚合」— 跨文件理解业务全景 |

> ⚠️ **注意**: 以上竞品信息仅描述事实，不做方案推荐。具体实现方式将在 spec 和 plan 阶段结合 SDDU 的实际约束（Handlebars 模板引擎、现有 Feature 目录结构、已有的 7 个输出模板模式）进行评估。

## 5. 假设与风险
> 记录问题挖掘过程中识别的假设和风险，供后续阶段验证和关注

### 5.1 关键假设
> 记录我们对问题理解所基于的假设，标注待验证项

| # | 假设内容 | 验证方式 |
|---|---------|---------|
| A-001 | @sddu-docs 输出的「项目业务全景」可以从现有 Feature 产物（spec.md / plan.md）中自动聚合，不需要用户额外提供配置或描述 | 在 spec 阶段选取 2-3 个不同类型的 Feature 目录进行试聚合，验证信息提取的可行性 |
| A-002 | 将所有 Feature 的 spec.md 和 plan.md 聚合为一篇项目全景文档是有价值的 — 用户确实需要这样一个聚合视图，而非在每个 Feature 目录下单独查看 | 询问当前维护者和潜在用户，确认「单篇聚合文档」的实际使用频率和场景 |
| A-003 | @sddu-docs 的产品定位是「项目级独立产物」（类似 ROADMAP.md），而非「Feature 级产物」（类似 spec.md）。落盘位置应为 `.sddu/` 根目录或专用子目录 | spec 阶段基于下游消费场景（谁读、何时读、怎么读）确定最佳落盘位置 |
| A-004 | @sddu-docs 的输出模板可以参照现有 7 个输出模板的共性结构（元数据头部 + 结构化章节 + 修订记录），使用 Handlebars 引擎生成 | 评估「项目全景」的特殊性 — 它需要聚合多 Feature 信息，模板结构可能与单 Feature 模板有本质不同 |
| A-005 | 现有 Handlebars 模板引擎和模板覆盖机制（用户 `.sddu/templates/` > 插件内置 `src/templates/`）可以直接扩展支持 @sddu-docs，无需修改引擎代码 | 检查 FR-TPL-001 的模板查找逻辑是否已覆盖所有 Agent 类型，确认 docs 类型无需特殊处理 |
| A-006 | @sddu-docs 的自动触发时机应当与 @sddu-tree 一致（在 7 个主流程 Agent 完成后），且两者无执行顺序依赖 | 分析 @sddu-tree 的触发机制，确认可以无冲突地加入第二个触发后 Agent |

### 5.2 主要风险
> 识别可能影响问题判断或后续决策的风险因素

| # | 风险描述 | 影响程度 |
|---|---------|---------|
| R-001 | **职责边界划定不当导致后期返工**：当前 @sddu-docs / @sddu-tree / @sddu-roadmap 三者的边界在 RD-002（边界模糊问题）中已暴露。如果 discovery/spec 阶段未能明确定义三者的输入/输出/消费关系，未来需要修改多个 Agent 的指令模板来重新划界 | 高 |
| R-002 | **全景文档的信息时效性问题**：@sddu-docs 从 Feature 产物（spec.md / plan.md 等）聚合信息。如果 Feature 更新后 docs 未同步刷新，全景文档将过时。需要设计一个刷新机制（手动触发 or 自动触发），否则文档可信度下降 | 中 |
| R-003 | **模板复杂度膨胀**：项目全景需要聚合多 Feature 信息，输出模板可能需要引入循环遍历（Handlebars `#each`）、条件渲染等高级模板特性。如果模板过于复杂，维护门槛会高于其他 Agent 的线性模板 | 中 |
| R-004 | **首次生成性能 vs 增量更新**：对于已有 17 个 Feature 的项目，首次全量扫描所有 spec.md / plan.md 可能耗时长（需读取 30+ 文件并做语义理解）。需要权衡「全量重建」和「增量更新」两种策略 | 中 |
| R-005 | **与 v3.2.0 FR-KB-002「项目知识自动沉淀」的定位冲突**：ROADMAP.md 中规划了 FR-KB-002「聚合 Feature 产出物为项目总览文档」，这与当前 @sddu-docs 的目标高度一致。如果 FR-KB-002 是 @sddu-docs 的上游规划描述，则本次 Feature 本质上是 FR-KB-002 的执行者；如果不是，则需解释两者的区别 | 高 |

## 6. 下一步建议
> 给出后续工作的优先级建议，回答"接下来优先做什么"

| 优先级 | 事项 | 说明 |
|--------|------|------|
| 高 | 聚焦 **Q-001 §5 工作流程**：定义 Agent 的完整执行步骤 — 扫描哪些目录、读取哪些文件、按照什么逻辑聚合、输出到哪个路径。这是 Agent 从「占位骨架」变为「可执行 Agent」的基础 | 没有工作流程，其他改进都无从落地 |
| 高 | 聚焦 **Q-002 输出模板**：需要配套设计 `sddu-docs.md.hbs`，定义产物格式。明确哪些信息来自聚合（从多 Feature spec/plan 提取）、哪些信息来自直接扫描（代码/配置/Schema） | 与 Q-001 同步推进 — 工作流程定义「如何产出」，输出模板定义「产出什么」 |
| 高 | 聚焦 **Q-003 + Q-004 产物落盘**：需在 spec 阶段决策产物定位（项目级 vs Feature 级）和落盘路径，解决 Q-004 的定位模糊问题 | 落盘路径决定了自动触发机制的设计和 @sddu-tree 的扫描范围 |
| 中 | 澄清 **Q-005 + Q-006 边界**：与 @sddu-tree / @sddu-roadmap 的职责划分。需在 spec 阶段定义三角色的输入/输出/消费关系，消除职责重叠风险 | 防止后期职责重叠导致返工 |
| 中 | 评估 **R-005 与 FR-KB-002 的关系**：确认本 Feature 是否是 v3.2.0 FR-KB-002 的前置或替代。如果是前置，标注为 FR-KB-002 的 blocker 依赖 | 影响版本归属和 Roadmap 更新 |
| 低 | 评估 **Q-009 自动触发**：在 spec 阶段定义 @sddu-docs 的触发时机和与 @sddu-tree 的协调关系 | 自动化增强，可在核心功能完成后追加 |
