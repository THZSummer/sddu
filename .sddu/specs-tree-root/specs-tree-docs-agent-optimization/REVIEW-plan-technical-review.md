> **文档定位**: 技术方案评审 — 聚焦核心争议：产物形态（单文件 vs 目录树）  
> **评审人**: 第三方技术方案评审专家  
> **评审日期**: 2026-07-05

## P0-1：产物形态 — 单文件 vs 目录树

### 问题描述

@sddu-docs 的输出产物是什么？现有文件给出了三种互不兼容的描述：

| 来源 | 产物形态 | 关键措辞 |
|------|---------|---------|
| spec.md FR-004 | **单文件** | 「主产物的文件名为 `PROJECT.overview.md`」 |
| plan.md §2.4 步骤 6 | **单文件** | 「写入 `PROJECT.overview.md`」 |
| plan.md §2.7.1 | **目录树** | 「每个 docs-tree-xxx 目录由 `docs-overview.md` + 可选文件」 |
| plan.md §2.8.2 | **目录树** | 三级电商目录树示例（`用户域/docs-overview.md` → `认证模块/` → `登录认证.md`） |
| plan.md §5.1 | **目录树** | 「运行时创建目录树（含逐级 `docs-overview.md` + 业务对象）」 |
| ADR-001/002 | **单文件** | 「`PROJECT.overview.md`（业务全景 + 技术全景）」 |

根源：plan v1.2 是单文件，v1.3 重构为目录树，但 spec.md 和 ADR 未同步更新。

### 原始评审意见（已撤回）

**路径 A（推荐）**：回归单文件 `PROJECT.overview.md`。删除 plan §2.7/§2.8 的目录树设计。

理由：与 spec 一致，增量更新简单，sddu-tree 干扰最小，scope 可控。

### 设计者回复

**方案**：分两期交付。本期单文件（先可执行），后期目录树（再优化）。

| 阶段 | 产物 | 范围 |
|------|------|------|
| 本期 | 单文件 `PROJECT.overview.md` | 补全 Agent 指令模板 + 输出模板，4-6h |
| 后期 | 目录树 `docs-tree-root/` | 聚类算法、增量更新、build-agents 递归复制 |

### 最终裁定

**❌ 撤回路径 A，也撤回两期方案。最终裁定：一期完成目录树。**

**理由**：

1. **两期方案用户体验不可接受**。单文件 → 目录树是破坏性迁移：输出格式、模板体系、阅读习惯、增量策略全部要变。用户刚学会读单文件，下一期就要全部推倒重来。迁移成本远大于开发侧的「先交付再优化」收益。

2. **两期不是迭代，是重做**。SDDU 的分阶段原则是「一个 Feature 一个边界」，不是「一个 Feature 拆成两个版本」。目录树方案的各环节（聚类算法、递归构建、增量更新、性能目标）是一个整体因果链，拆成两期意味着后期 Feature 要重新走 discovery→spec→plan→tasks 流程。

3. **真实项目规模验证**：大型 Feature 的 plan.md 单文件可达 160KB+，且存在多版本并行（v1/v2/v3）场景。目录树是唯一能在「全貌可浏览 + 细节可钻取」间取得平衡的方案。单文件要么全量臃肿不可读，要么牺牲细节。

4. **spec.md 的约束是纸面的**。spec FR-004 写的是单文件，但 spec 是服务于真实需求的。当真实需求证明单文件不成立时，应该更新 spec 而不是让 plan 屈就于 spec。

**结论**：保留 plan §2.7/§2.8 的目录树设计，一期实现。spec.md FR-004/FR-002/EC-002 同步更新为目录树描述。

## P0-2：业务层级推导算法

### 问题描述

plan §2.8.2 展示了三级业务目录树示例：

```
docs-tree-root/
├── docs-overview.md       ← 根级：描述子系统间关系
├── 用户域/
│   ├── docs-overview.md   ← 子系统级：描述模块间关系
│   ├── 认证模块/
│   │   ├── docs-overview.md
│   │   ├── 登录认证.md
│   │   └── Token签发.md
│   └── 权限管理/
│       └── ...
├── 订单域/
└── 商品域/
```

但 plan 从未定义 LLM **如何从输入的扁 Feature 目录列表推导出这个层级**。

### 输入 vs 输出

**输入**是 `.sddu/specs-tree-root/` 下若干扁平的 Feature 目录（名称各异，无统一命名规范）：

```
specs-tree-{feature-a}          specs-tree-{feature-b}
specs-tree-{feature-c}          specs-tree-{feature-d}
specs-tree-{feature-e}          specs-tree-{feature-f}
...
```

**期望输出**是 `用户域/认证模块/登录认证.md` 这样的业务组织树。

**缺失的映射**：输入 → 输出的转换算法完全没有定义。

### 为什么必须定义

| 不定义会怎样 | 原因 |
|------------|------|
| **输出非确定性** | 每次运行 `@sddu-docs`，LLM 可能产生不同的业务域划分，无法审计 |
| **增量更新找不到文件** | 当某 Feature 变更时，LLM 需要知道它的 docs-tree 文件在哪个域哪个模块下——但域划分是每次重新计算的 |
| **ADR 归属漂移** | plan §2.7.3.2 定义 ADR 按「本级范围」归属——但「本级范围」每次可能不同 |
| **review 无法验证** | 审查清单 C1-C12 没有一条验证「业务层级是否合理」|
| **P6 自相矛盾** | plan §2.8.1 P6「不反向要求 specs-tree-root 如何组织」与「期望输出稳定业务层级」互相矛盾 |

### 需要设计者回复的问题

**Q1：聚类策略如何确定？**

从 plan 目前的设计看，聚类方式有三种可能：

- **名前缀截取**：取 `specs-tree-` 后第一个 `-` 前的字段做域标识。确定性高，但依赖目录命名规范
- **LLM 语义聚类**：LLM 读取各 Feature 的 spec.md 目标后按语义分组。灵活性高，但每次运行结果可能不同
- **人工映射文件**：在 `.sddu/` 下维护一份 Feature → 业务域的映射表。确定性最高，但有维护成本

你的倾向是哪一种？或者有第四种方案？

**Q2：`-v2`/`-v3` 后缀的目录如何聚类？**

同名多版本目录（如 `feature-aaa`、`feature-aaa-v2`、`feature-aaa-v3`），是归入同一域以版本元数据区分，还是作为三个独立域处理？

**Q3：无法归类的 Feature 如何处理？**

总会有些 Feature 无法落入已定义的业务域。剩余 Feature 是统一放入「其他」域，还是留在根级 docs-overview.md 的 Feature 索引表中不做层级展开？

---

**▶ 答复（SDDU Plan Agent, 2026-07-05）**

**Q1 — 聚类策略**：名前缀截取。取 `specs-tree-` 后第一个 `-` 前的字段做域标识。确定性最高，每次运行结果一致。不用 LLM 语义聚类（不可重复）、不用人工映射文件（有维护成本）。以 SDDU 自身为例：按目录名前缀将 Feature 分组为若干业务域。

**Q2 — 版本后缀**：先去 `-vN` 后缀再截取前缀。如 `feature-aaa-v3` → 截掉 `-v3` → `feature-aaa` → 与 `feature-aaa` 归入同域。版本号写入该域 `docs-overview.md` 元数据行，不在目录名中出现。

**Q3 — 未归类 Feature**：留在根级 `docs-overview.md` 的 Feature 索引表中，不入子目录，不强行聚类。读者可见其存在但无层级展开。通常这类 Feature 是工具类或跨域组件，强行塞入某域反而误导。

**▶ 评审裁定（技术方案评审专家, 2026-07-05）**：

| 问题 | 答复内容 | 裁定 |
|:----:|---------|:----:|
| Q1 聚类策略 | 名前缀截取 | **❌ 不赞同** — 目录名服务于文件组织，不服务于业务语义。名前缀截取将小规模 Feature（2 文件）与大规模 Feature（50+ 文件）压平同级，全景变形。LLM 应阅读 spec.md 理解 Feature 实际内容后按语义分组，才反映真实业务结构 |
| Q2 版本后缀 | 先去 `-vN` 再聚类 | **❌ 不赞同** — 硬编码的字符串截取和 Q1 名前缀是同一个问题：目录名不可靠。用户命名可能不规范或写错。LLM 应通过阅读各 Feature 的 spec.md，从内容语义判断同名多版本目录是否属于同一业务域——而非依赖目录名的字符串规则 |
| Q3 未归类处理 | 留在根级索引表 | **❌ 不赞同** — 不强行塞入不合适的域是对的，但不应留在根级索引表中。它们本身就是单独的业务域/模块，应和其他域一样在根级有自己的一级目录，只不过该域下只有一个 Feature 无需进一步拆分子模块 |

> **注**：Q1 的确定性问题可通过「首次聚类结果持久化到根级 docs-overview.md，后续增量仅调整变更 Feature」解决，无需走名前缀截取。

**▶ 答复（SDDU Plan Agent, 2026-07-05）**：

Q1/Q2 接受专家裁定，已改为 LLM 语义聚类 + 首次持久化（见 plan §2.4 步骤 3、§2.8.4 D7）。

Q3 接受专家纠正：不留在根级索引表，自成一级目录，只是目录下无子模块拆分。

## P0-3：单次 Agent 调用的上下文窗口承载能力

### 问题描述

plan §2.4 定义了 7 步工作流，全部在一次 `@sddu-docs` 调用中完成：

1. 工作空间验证
2. Feature 扫描（读 state.json）
3. 业务层级推导（逐 Feature 读 spec.md，语义聚类）
4. 产物内容提取（逐 Feature 读 spec.md + plan.md）
5. 输出模板选择（读 17 个模板的定位声明）
6. 增量生成（对比 mtime，决定重写范围）
7. 产物落盘（按业务层级创建目录树，写 20+ 文件）

**输入量预估**（以中等规模项目为例）：

| 输入项 | 数量 | 单文件大小 | 总量 |
|--------|------|-----------|------|
| Feature 的 spec.md | ~7 个 | ~30~100KB | ~300KB |
| Feature 的 plan.md | ~7 个 | ~20~160KB+ | ~500KB |
| 模板库 | ~17 个 | ~60 行 | ~1000 行 |
| Agent 指令模板 | 1 个 | ~300 行 | ~300 行 |
| **合计** | | | **~1MB+** |

大型 Feature 的 plan.md 单文件可达 160KB+，约占 40K+ token。7 个 Feature 的 spec+plan 总量可能超过 200K token，接近或超过主流 LLM 的上下文窗口上限。

### plan 当前的处理

plan §4.1 缺点②提到「首次全量扫描 17 个 Feature 需读取 30+ 文件，受 LLM 上下文窗口限制」，但未给出应对方案。R4 风险提到「远期方案：分批扫描 + 流式聚合（纳入未来 Feature）」——即当前不处理。

### 需要设计者回复的问题

**Q1：当前方案是否接受「大项目不可用」的限制？**

如果中等项目规模（~7 个 Feature、1MB+ 输入）就超限，那 @sddu-docs 对真实项目的可用性存疑。是接受这个限制（标注「适用规模上限」），还是在 plan 中定义分批处理机制？

**Q2：如果需要分批，怎么分？**

候选方向：
- 按业务域分批：先聚类（只读 spec.md §3 目标，量小），再逐域提取（只读该域 Feature 的完整 spec+plan）
- 按 Feature 分批：逐 Feature 提取后写入，不一次性全部读入

设计者的倾向是？

---

**▶ 答复（SDDU Plan Agent, 2026-07-05）**：

**Q1**：不接受「大项目不可用」的限制。分批处理是必须的。当前 plan R4 的「远期方案」应该提升为当期方案的一部分——不在本期实现代码，但必须在 plan 中明确分批策略，否则验证场景 V2 无法通过。

**Q2**：倾向**按业务域分批**。具体做法：
1. 步骤 1-3 合并为轻量预扫描：只读 state.json + spec.md §3 目标，完成聚类并持久化，输入量远小于 200K token
2. 后续逐域处理：每个域开始新的 Agent 调用，只读该域 Feature 的完整 spec+plan，生成该域的目录树
3. 增量时：变更 Feature 对应的域重新处理，未变更域跳过

这样做的好处：每次调用的输入是可控的（单域规模），同时步骤 3 的聚类结果在第一次就固化下来，后续增量不会漂移。

**▶ 评审裁定（技术方案评审专家, 2026-07-05）**：

| 问题 | 答复内容 | 裁定 |
|:----:|---------|:----:|
| Q1 大项目限制 | 不接受，分批处理提升为当期方案，但不在本期实现代码 | **❌ 不赞同** — 「不在本期实现代码」意味着 Agent 仍然单次调用读取全部文件，中等项目规模下 V2 验证场景必然失败。plan 中写了分批策略但不实现，等于没做。分批策略的复杂度并不高——指令模板中写明「逐域读取→处理→写入→下一域」的迭代流程即可，不需要额外脚本或基础设施。应在本期落地 |
| Q2 分批策略 | 按业务域分批：轻量预扫描聚类 → 逐域处理 | **✅ 赞同** — 预扫描只读 state.json + spec.md §3，输入量小；逐域处理时每次只持有一个域的完整 spec+plan，前一个域处理完即可释放上下文。聚类结果首次固化，增量只碰变更域，与 P0-2 的持久化机制一致 |

> **注意**：plan 落地时需明确「逐域处理」是在同一 Agent 会话内迭代执行（LLM 用工具逐域读取→生成→写入→下一个域），而非多次独立调用。SDDU Agent 是单会话工具使用者，不是自调用编排器。

## P0-4：聚类结果持久化机制未定义

### 问题描述

plan §2.4 步骤 3 写了：

```
│ 步骤 3: 业务层级推导（轻量预扫描）                         │
│   - 只读 state.json + spec.md 目标章节，输入量可控         │
│   - 按语义相似度将 Feature 分组为业务域和模块               │
│   - 首次运行时将聚类结果持久化                              │
│   - 后续增量运行时仅变更 Feature 重新评估归属               │
```

步骤 4~7 写了：

```
│ 步骤 4~7: 逐域迭代处理                                    │
│   增量时：仅处理变更 Feature 所在的域，其余域跳过。          │
```

**「持久化」和「增量仅处理变更域」是整个分批架构的地基**，但 plan 没有定义这个地基的具体形态：

| 未定义项 | 影响 |
|---------|------|
| 持久化到哪个文件？ | 根级 `docs-overview.md` 里的表格？独立文件 `.sddu/docs-tree-root/.clustering.json`？ |
| 什么格式？ | Markdown 表格 LLM 可读但解析不可靠；JSON 可靠但 LLM 写入易出错 |
| LLM 下次运行时怎么读回来？ | 指令模板需要明确告诉 LLM「先读 X 文件获取上次聚类结果」 |
| 域划分变化时怎么更新？ | 某 Feature 从域 A 移到域 B，持久化文件怎么同步？旧域 A 下的文件要不要删？ |

### 为什么必须定义

P0-2（LLM 语义聚类）和 P0-3（逐域分批处理）都依赖这个持久化机制：

- **没有持久化** → 步骤 3 每次运行都从头重新聚类 → 所有域划分可能变化 → 步骤 4~7 无法「仅处理变更域」，因为不知道哪些域变了
- **持久化不可读** → LLM 下次运行读不回上次的结果 → 增量模式退化为全量
- **持久化不可写** → LLM 写入格式错误 → 下次读取失败 → 增量链路断裂

### 需要设计者回复的问题

**Q1：持久化到哪个文件、什么格式？**

考虑到 SDDU 体系中 LLM 既是写入者也是读取者，格式需要同时满足「LLM 可靠写入」和「LLM 可靠读取」。设计者的倾向是？

**Q2：增量时域划分变化怎么处理？**

某 Feature 重新评估后从一个域移到另一个域，它的文件路径变了（`域A/xxx.md` → `域B/xxx.md`）。持久化文件怎么记录这个变化？旧路径下的文件是删除还是保留？

---

**▶ 答复（SDDU Plan Agent, 2026-07-05）**：

**Q1**：持久化到根级 `docs-overview.md` 的 Feature 索引表中。直接用 Markdown 表格，在现有的 Feature 索引表上增加一列「所属域」。LLM 对 Markdown 表格的读写是成熟能力，无需引入 JSON 中间文件。

**Q2**：Feature 域归属变化时，删除旧域下的文件子树，在新域下重建，同时更新根级索引表中的「所属域」列。操作顺序：① 读上次持久化的映射表 → ② 对比新聚类结果 → ③ 对每个变更 Feature：删旧域路径 → 写新域路径 → 更新映射表。

**▶ 评审裁定（技术方案评审专家, 2026-07-05）**：

| 问题 | 答复内容 | 裁定 |
|:----:|---------|:----:|
| Q1 持久化位置/格式 | 根级 docs-overview.md 的 Feature 索引表增加「所属域」列，Markdown 表格 | **✅ 赞同** — LLM 对 Markdown 表格的读写是成熟能力，不引入 JSON 中间文件，与 SDDU 体系中其他 Agent 的产物风格一致。索引表本身就是 docs-overview.md 的既有内容，增加一列不改变文档结构 |
| Q2 域归属变化处理 | 删旧域路径 → 写新域路径 → 更新映射表 | **✅ 赞同** — 三步操作顺序清晰，删-写-更新的顺序保证了不会出现「新文件已写但旧文件未删」的不一致状态。人工编辑会随旧域子树一起删除——这与 plan §2.4 步骤 4~7「保留未变更 Feature 的已有目录和文件（含人工编辑）」的语义一致：只有域归属变化时才删，未变更的保留 |

## P0-5：技术全景无归属 — 目录树按业务域组织无法承载横切视图

### 问题描述

spec.md FR-002 要求产物提供「业务全景 + 技术全景」两个维度的视图。plan 的目录树设计（§2.7/§2.8）完全按业务域组织层级：

```
docs-tree-root/
├── docs-overview.md       ← 根级：子系统间关系
├── 用户域/
├── 订单域/
└── 商品域/
```

**业务全景**有自然归宿——按业务域逐级展开目录树即可。但**技术全景**（系统架构、技术栈选型、部署拓扑、跨域中间件、数据流、外部依赖）是**横切**多个业务域的：

| 技术全景内容 | 性质 | 在业务域目录树中的归属 |
|------------|------|---------------------|
| 整体分层架构（前端/网关/服务/存储） | 横切所有域 | 无自然归属 |
| 技术栈选型（语言/框架/中间件） | 横切多个域 | 无自然归属 |
| 部署拓扑（集群/region/网络） | 跨域基础设施 | 无自然归属 |
| 跨域数据流（订单→库存→物流） | 跨域流转 | 强行归入某域会割裂链路 |
| 共享中间件（MQ/缓存/网关） | 跨域共享 | 无自然归属 |

plan §2.8.1 P6 明确「不反向要求 specs-tree-root 如何组织」，意味着 LLM 只能从 Feature 内容推导——而 Feature 本身是按业务划分的，技术信息分散在各 Feature 的 spec/plan 中，没有任何一个业务域能完整承载技术全景。

### 为什么必须定义

1. **spec FR-002 是硬约束**：产物必须同时包含业务全景和技术全景。当前 plan 只交付了业务全景，技术全景维度缺失，FR-002 不满足。
2. **根级 docs-overview.md 承载不了**：plan §2.7.1 说根级 docs-overview.md「描述子系统间关系」，这是业务关系不是技术架构。把技术全景塞进根级 overview 会让该文件变成杂物间。
3. **读者预期落空**：用户运行 `@sddu-docs` 期望得到「看懂这个项目」的全景，技术全景是核心诉求之一。只给业务域划分，读者仍不知道「这项目用什么技术、怎么部署、数据怎么流转」。

### 需要设计者回复的问题

**Q1：技术全景放在目录树的什么位置？**

候选方向：

- **方案 A — 根级独立目录**：在 `docs-tree-root/` 下增设 `_technical/`（或 `_architecture/`）目录，专门承载技术全景。与业务域目录平级，下含 `architecture.md`、`tech-stack.md`、`deployment.md`、`data-flow.md` 等。LLM 在逐域处理前/后单独生成技术全景文件。
- **方案 B — 根级 docs-overview.md 扩展**：在根级 overview 中增加「技术全景」章节，与「业务全景」章节并列。不新增目录，但根级文件会膨胀。
- **方案 C — 每个域内含技术章节**：各域 docs-overview.md 中增加该域的技术栈/部署信息。能反映域内技术细节，但跨域技术全景（整体架构、跨域数据流）仍无归属。

设计者的倾向是？或者有第四种方案？

**Q2：技术全景的内容从哪里提取？**

业务全景的输入是各 Feature 的 spec.md §3 目标。技术全景的输入分散在：

- spec.md 中的技术约束/非功能需求章节
- plan.md 中的 ADR（技术决策记录）
- plan.md 中的技术选型描述
- 代码结构本身（框架、依赖、目录布局）

plan 当前的工作流（§2.4 步骤 3-4）只读了 spec.md 目标章节和 spec+plan 主体。技术全景是否需要额外定义提取步骤、提取哪些章节？还是复用已有步骤的输入做二次归纳？

**Q3：技术全景与业务全景的生成顺序？**

如果技术全景独立成目录（方案 A），它的生成依赖对多个域 Feature 的技术信息归纳。是在逐域处理前先扫一遍生成技术全景（此时对各域技术细节了解不充分），还是逐域处理完后再生成技术全景（此时上下文已被业务全景占满）？还是穿插进行？

---

**▶ 答复（SDDU Plan Agent, 2026-07-05）**：

**Q1**：方案 A — 根级独立目录。在 `docs-tree-root/` 下增设 `_technical/` 目录，包含架构总览、技术栈、部署拓扑、跨域数据流等文件。这些文件使用现有模板库（T2~T10）即可——技术全景不是新类型的文档，只是放在不同目录下、内容聚焦技术维度而已。模板库不需要为此新增模板。

**Q2**：复用已有步骤的输入。同一份 spec.md 和 plan.md，LLM 提取业务信息时取 FR/用户故事/目标章节，提取技术信息时取 NFR/ADR/技术选型/架构分析章节。Plan 的工作流不需要新增提取步骤，只需在生成技术全景文件时调整提取聚焦点。

**Q3**：逐域处理完成后再生成技术全景。此时 LLM 已遍历所有域的 Feature 产物，掌握全局技术信息，可以归纳出跨域架构、共享中间件、整体数据流等横切视图。技术全景作为最后一步，放在根级 `_technical/` 目录下。

**▶ 评审裁定（技术方案评审专家, 2026-07-05）**：

| 问题 | 答复内容 | 裁定 |
|:----:|---------|:----:|
| Q1 技术全景位置 | 方案 A — 根级独立目录 `_technical/`，复用现有模板 T2~T10，不新增模板 | **❌ 不赞同方案 A，改定方案 B — 根级 docs-overview.md 扩展技术全景章节** — 方案 A 增设 `_technical/` 特例目录，破坏了目录树的简洁模型：根级 docs-overview.md 是唯一入口，其余皆为 LLM 从模板库选择的业务域子树。多一个非业务域的特例目录，用户心智模型变复杂——要理解两类顶层条目（业务域目录 + 技术目录）。方案 B 将技术全景作为根级 overview 的章节与业务全景并列，单一入口原则不变。根级技术全景是**概要级综合**（整体架构/技术栈/部署拓扑/跨域数据流），不无限膨胀；技术细节仍落在各域 docs-overview.md 技术章节（见 Q2 修正） |
| Q2 内容提取来源 | 复用已有步骤输入，不新增提取步骤，生成技术全景时调整提取聚焦点 | **❌ 不赞同** — 与 P0-3 分批架构直接矛盾。逐域处理时各域 Feature 的 spec+plan 读入生成业务文档后即释放上下文，技术全景作为最后一步生成时，上下文中已无原始 spec/plan 输入，「复用已有输入」在物理上不成立。正确做法：**逐域处理时顺带提取技术信息**（NFR/ADR/技术选型），缓存在各域 docs-overview.md 的技术章节中；技术全景最后从各域技术章节归纳跨域视图，写入根级 docs-overview.md 的技术全景章节 |
| Q3 生成顺序 | 逐域处理完成后生成技术全景 | **✅ 赞同方向，需与 Q2 修正对齐** — 「最后生成」方向正确，此时各域已处理完毕。但技术全景的输入不是「复用已有输入二次提取」，而是从各域 docs-overview.md 技术章节归纳。最终生成顺序应为：轻量预扫描（业务聚类）→ 逐域处理（同时产出业务文档 + 域级技术章节）→ 生成技术全景（从各域技术章节归纳跨域视图，写入根级 docs-overview.md 技术全景章节） |

> **核心修正**：设计者 Q2/Q3 的本意是避免增加复杂度，但在 P0-3 分批架构下，「复用已有输入」不成立。技术信息必须在逐域处理时顺带提取并缓存在域级文档中——这不是「新增提取步骤」，而是「在已有步骤中增加技术维度的输出」。各域 docs-overview.md 需增加技术章节（技术栈/关键 ADR/部署信息），既服务于域内技术视角，又作为根级技术全景的归纳素材。Q1 采用方案 B 后，根级 docs-overview.md 承载「业务全景 + 技术全景」双章节，单一入口，与 spec FR-002 完全对齐。
