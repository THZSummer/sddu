# ADR-003: @sddu-docs 双模式架构 — specs-tree 主扫描 + 用户指令代码扫描

## 状态
PROPOSED（替代 v3.0 ADR-003「适用范围限定」）

## 背景

### 前置决策（v3.0，已驳回）

v3.0 ADR-003 做出决定：`@sddu-docs` 不覆盖场景 B（非 SDDU 项目），适用范围限定为「仅服务于已通过 SDDU 工作流维护的项目」。核心理由包括：
1. Agent 命名即范围声明（SDDU 专属）
2. 降级策略产出质量低
3. 职责边界不可模糊
4. 非 SDDU 项目全景需求另有解决路径（@sddu-tree）

**驳回理由**：该决策被驳回。驳回方认为——
- `@sddu-docs` 不应直接拒绝非 SDDU 项目的用户。用户可能正在评估是否引入 SDDU，或项目正在从其他工作流迁移
- 提供一个「有限但有价值的」代码扫描能力，比直接说「你没有 specs-tree，我什么都做不了」对用户更友好
- 关键是**不自动降级**——让用户明确知道自己在请求什么，产物标注清楚「这不是完整全景」

### 矛盾根源

`@sddu-docs` Agent 模板存在 YAML 描述与实际规则的自相矛盾：

| 位置 | 原文 |
|------|------|
| **YAML description** | 「扫描代码、配置、Schema 等实际产物，生成项目业务与技术全景视图」 |
| **§8 规则 1** | 「仅扫描 `.sddu/specs-tree-root/`...**不扫描**实际源代码」 |

YAML 描述承诺了代码扫描能力，但规则禁止了代码扫描。v3.0 的解决方式是「修正 YAML 描述以匹配规则」，本 ADR 的解决方式是「扩展规则以匹配 YAML 描述中的合理部分，但限制触发方式和产出质量」。

## 决策

我们决定采用**双模式架构**：

### 模式 1：specs-tree 主模式（默认）

- **触发**：用户直接调用 `@sddu-docs`（无代码扫描触发短语）
- **行为**：与 v3.0 方案完全一致——扫描 `.sddu/specs-tree-root/` 下 Feature 的 spec.md / plan.md / state.json / ADR，聚合为项目业务与技术全景
- **前置条件**：`.sddu/specs-tree-root/` 存在且含至少一个 Feature。不满足时提示并终止（EC-001）
- **产物**：写入 `.sddu/docs-tree-root/`

### 模式 2：代码扫描模式（用户指令触发）

- **触发**：用户说出明确触发短语（如「扫描代码生成全景」「分析项目代码」「代码模式」）
- **行为**：跳过 specs-tree-root 验证，直接扫描项目源代码、配置、Schema 文件
- **能力边界**：5 个维度（目录结构 → 模块划分、依赖文件 → 技术栈、路由文件 → API 面、配置文件 → 部署信息、Schema 文件 → 数据模型）
- **能力天花板**：无法还原设计意图、业务语义和技术决策
- **产物标注**：每个文件头部醒目标注「基于代码扫描生成，未经 SDDU 工作流验证」
- **产物隔离**：写入 `.sddu/docs-tree-root-code/`（与 `docs-tree-root/` 物理隔离）
- **不会自动触发**：无 specs-tree-root 时不会自动降级为代码扫描。用户必须明确说出触发短语

### 关键设计约束

1. **不耦合**：两个模式在 Agent 指令模板中实现为独立分支（§5.1 vs §5.2），不共享异常处理逻辑（EC-001~EC-011 仅适用主模式）
2. **不降级**：缺失 specs-tree-root 不会自动切换到代码扫描——防止用户误以为获得了完整全景
3. **可识别**：产物目录名（`docs-tree-root-code`）和文件头标注确保读者始终知道自己在看什么
4. **无新模板**：代码扫描模式复用现有模板库（T1/T3/T4/T7/T9），不新增 Handlebars 模板文件

## 后果

### 正面影响
- ✅ **消除 YAML 描述矛盾**：描述诚实地反映两种能力，不再有「承诺了但没做」的问题
- ✅ **服务非 SDDU 项目用户**：为正在评估 SDDU 或从其他工作流迁移的用户提供入口
- ✅ **不损害主模式质量**：代码扫描模式独立分支，不污染 specs-tree 主模式的数据流和异常处理
- ✅ **用户知情**：产物标注和物理隔离确保用户清楚代码快照 ≠ 全景视图
- ✅ **零模板膨胀**：不新增 Handlebars 文件，仅 Agent 指令模板中增加分支

### 负面/风险
- ⚠️ **Agent 指令模板复杂度增加**：从单一模式变为双模式，模板行数从 ~300 增至 ~350 行
- ⚠️ **用户可能期待代码扫描能替代 specs-tree**：风险在于用户看到「代码扫描」产物后误以为这是完整全景，不再推进 spec/plan 阶段
  - **缓解**：产物标注 + Agent 完成报告提示 + EC-001 提示引导用户理解完整全景需要 spec/plan
- ⚠️ **触发短语依赖自然语言匹配**：用户可能用不同的措辞表达相同意图，存在未匹配风险
  - **缓解**：定义 6 个常见触发短语，覆盖主流表达方式。短语集可在后续迭代中扩展

### 与旧版决策（v3.0）的对比

| 维度 | v3.0 ADR-003 | v3.1 ADR-003（本版） |
|------|-------------|---------------------|
| 场景 B 支持 | ❌ 不支持 | ✅ 支持（用户指令触发） |
| 自动降级 | 不适用 | ❌ 不自动降级（关键约束） |
| YAML 描述 | 仅描述 specs-tree | 诚实描述双能力 |
| 产物目录 | `docs-tree-root/` | + `docs-tree-root-code/` |
| Agent 模板行数 | ~300 | ~350（+50 行代码扫描分支） |
| 用户犯错风险 | 低（直接拒绝） | 中（可能误以为代码快照=全景）→ 标注缓解 |
