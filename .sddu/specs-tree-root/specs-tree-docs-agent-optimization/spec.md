## 2. 上下文
> 回顾问题背景和目标用户

### 2.1 问题背景

`@sddu-docs` 是 SDDU 框架中的「项目全景专家」Agent，负责聚合各 Feature 的流程产物（spec.md / plan.md）生成项目业务全景和技术全景视图。在 SDDU 体系中定位为侧向辅助 Agent，与 `@sddu-tree`（目录导航）、`@sddu-roadmap`（版本规划）共同构成辅助 Agent 矩阵。

**当前状态**：指令模板（`src/templates/agents/sddu-docs.md.hbs`）为占位骨架 —— §5 工作流程仅一行「待后续 Feature 定义」、无输出模板、无产物落盘机制。Agent 在 opencode.json 中已注册（描述为「项目全景文档生成器」），在 `build-agents.cjs` 中已列入 `specialAgents` 数组，框架侧已准备就绪，但指令模板本身不具备可执行能力。

**业务影响**：
- 用户入职新项目或接手已有 SDDU Feature 的项目时，缺少一份聚合全局信息的文档来快速建立心智模型
- 10 个完整 Agent vs 1 个半成品 —— 框架一致性承诺被破坏
- `@sddu-docs` 与 `@sddu-tree` / `@sddu-roadmap` 的职责边界模糊，存在信息冗余和碎片化风险

### 2.2 目标用户

| 用户角色 | 典型场景 |
|---------|---------|
| **SDDU 框架维护者** | 运行 `@sddu-docs` 生成项目全景文档；期望 Agent 能从占位骨架变为可执行 |
| **新项目入职者** | 接手已有 SDDU Feature 的项目，需要快速了解业务模块、API 面、技术架构 |
| **架构决策者** | 需要做跨 Feature 技术决策，依赖一份描述当前系统实际状态的全局文档 |
| **下游 Agent 消费者** | 其他 Agent 可引用产品全貌输出了解当前系统全貌 |

## 3. 目标与非目标
> 明确需求范围，防止范围蔓延

### 3.1 目标 (Goals)
> 明确本次要达成的业务目标

| # | 目标描述 | 对应问题 |
|---|---------|---------|
| G-001 | 补全 @sddu-docs 指令模板，使 Agent 从占位骨架变为可执行 | Q-001 |
| G-002 | 创建输出模板 `sddu-docs.md.hbs`，定义业务全景 + 技术全景的结构化输出格式 | Q-002 |
| G-003 | 建立模板库机制，支持多场景模板（LLM 按需选择与维护） | 用户需求 |
| G-004 | 定义产物落盘策略（`.sddu/docs-tree-root/`），使输出可被下游消费 | Q-003, Q-004 |
| G-005 | 明确定义 @sddu-docs / @sddu-tree / @sddu-roadmap 三个辅助 Agent 的精确边界 | Q-005, Q-006 |
| G-006 | 支持用户自定义输出模板覆盖（与 FR-TPL-001 模板体系一致） | Q-007 |
| G-007 | 更新示例对话，与实际工作流保持一致 | Q-008 |
| G-008 | 限定触发方式为手动触发（`@sddu-docs`），不纳入自动触发体系 | Q-009 |
| G-009 | 实现增量更新策略 — 当 PROJECT.overview.md 已存在时，Agent 检测变更并仅更新变化部分，替代全量重建 | 新增需求 |

### 3.2 非目标 (Non-Goals)
> 明确本次不涉及的范围，防止需求蔓延

| # | 明确不做 | 理由 |
|---|---------|------|
| NG-001 | 不实现自动触发机制 | 产物变化频率高，自动触发不合适（用户决策） |
| NG-002 | 不实现 AST 级别的代码语义分析 | 依赖现有产物（spec.md / plan.md）聚合，不要求解析源代码 AST |
| NG-003 | 不修改 Handlebars 模板引擎本身 | 复用现有模板渲染基础设施 |
| NG-004 | 不修改 @sddu-tree 或 @sddu-roadmap 的指令模板 | 边界定义仅写入 @sddu-docs 的指令模板，不跨 Agent 修改 |
| NG-005 | 不实现 FR-KB-002「项目级知识自动沉淀」 | 本 Feature 是 FR-KB-002 的前置依赖，为知识沉淀提供可执行 Agent；KB-002 在其自身 Feature 中实现 |

## 5. 功能需求 (FR)
> 每个需求必须有唯一标识符且可测试

| ID | 需求描述 | 验收标准 | 优先级 |
|----|---------|---------|:--:|
| FR-001 | **指令模板补全** — 补全 @sddu-docs 指令模板中的工作流程，从占位「待后续 Feature 定义」变为完整执行步骤，至少包含：(a) 扫描 `.sddu/` 下所有 Feature 目录，(a2) 同一 Feature 存在多版本时仅取最新版本的 spec.md / plan.md，(b) 从每个 Feature 的 spec.md 提取模块/功能/目标信息，(c) 从 plan.md 提取架构/技术栈/依赖信息，(d) 按输出格式结构聚合，(e) 写入产物落盘路径，(f) 输出完成摘要（含所聚合的 Feature 数量与版本清单） | 运行 `@sddu-docs` 后 Agent 能按步骤执行，无「待后续 Feature 定义」占位文本；每个步骤有明确的操作指令和输出约束 | P0 |
| FR-002 | **输出文档内容结构** — @sddu-docs 输出的最终文档集合应使读者能按层级（整体 → 子系统 → 模块 → 对象）逐步了解系统。每级应包含本级的关键描述和本级内部子组件间的关系描述。内容来源于各 Feature 产物的聚合提取（spec.md / plan.md / state.json / ADR） | 运行 @sddu-docs 后生成的文档集合支持按层级逐级展开浏览，每级描述本级概况及子组件关系，内容来源于对 Feature 产物的聚合提取 | P0 |
| FR-003 | **模板库机制** — 建立模板库，LLM 在运行时按内容特征匹配选择最合适的模板组合。模板库包含多个内置模板（如全景入口、API 文档、数据模型、业务流程等），每个模板定位明确，LLM 读取其声明后判断是否适用于当前内容，按需组合选用。用户在自定义目录下放置同名模板文件即可覆盖内置模板 | 验证：(a) 模板库存在多个可用的内置模板，(b) LLM 执行时按内容特征（如是否涉及 API、数据模型、业务流程）匹配选择合适模板，(c) 用户自定义模板可覆盖内置模板 | P1 |
| FR-004 | **产物落盘机制** — @sddu-docs 聚合输出应按业务层级组织，使用者可按层级逐级展开浏览。每级应有本级全景描述和子级组件关系说明。产物支持增量更新策略——当部分产物已存在时，系统检测变更并仅更新变化部分。具体的目录结构、文件命名、层级深度和文件数量由 plan 阶段确定 | 运行 `@sddu-docs` 后：(a) 产物按业务层级组织生成，(b) 每级包含本级全景描述和子组件关系，(c) 已存在产物时支持增量更新（仅更新变化部分）或全量重建 | P0 |
| FR-005 | **精确边界划分** — @sddu-docs 必须明确定义自身与 @sddu-tree、@sddu-roadmap 的职责边界，至少包含以下 7 个维度：(a) 扫描范围 — 关注哪些目录/文件，(b) 不可触碰区 — 明确不操作的目录/文件，(c) 输入 — 依赖哪些上游产物，(d) 输出 — 产出哪些产物文件，(e) 消费方 — 哪些下游 Agent 或用户消费其输出，(f) 触发时机，(g) 与同类的区别 — 一句话区分 | @sddu-docs 在运行时不扫描/不修改 @sddu-tree 和 @sddu-roadmap 的专属领域；三个 Agent 的输入输出无重叠；边界信息对用户可查询 | P1 |
| FR-006 | **输出格式覆盖规则定义（设计态）** — @sddu-docs 的输出格式遵循以下优先级规则：(a) 用户自定义格式优先于内置默认格式，(b) 两者均不可用时报错。此规则须与 FR-TPL-001 模板体系保持一致，不涉及运行时行为 | 规则被文档化且对用户可见；规则与 SDDU 模板体系优先级逻辑一致（用户自定义优先于内置） | P1 |
| FR-006a | **输出格式选择（运行态）** — @sddu-docs 在运行时按 FR-006 定义的优先级规则加载输出格式：(a) 若用户自定义格式存在则优先使用，(b) 否则使用内置默认格式，(c) 若两者均不可用则显式报错并终止执行 | (a) 用户提供自定义格式后运行 @sddu-docs → 产物使用自定义格式，(b) 移除自定义格式后运行 @sddu-docs → 产物使用内置格式，(c) 两处都不可用时运行 @sddu-docs → Agent 报错并终止 | P1 |
| FR-007 | **示例对话更新** — @sddu-docs 向用户展示的示例交互应与 FR-001 定义的实际工作流一致 | @sddu-docs 展示的示例交互流程与 FR-001 定义的工作流步骤一致 | P2 |
| FR-008 | **输出格式描述修正** — @sddu-docs 关于输出格式的描述存在矛盾（既声称「内置固定格式」又支持模板查找）。修正为：明确输出格式可由用户覆盖（非绑定固定格式），输出按 FR-006 的优先级规则确定 | @sddu-docs 的输出格式描述中不存在「固定格式」与模板查找并存的矛盾表述 | P2 |
| FR-009 | **增量更新策略** — 当产物已存在时，@sddu-docs 应支持增量更新：(a) 扫描各 Feature 目录检测变更（最新版本目录存在性、`state.json` 或 spec.md/plan.md 的修改时间戳），Feature 新增版本目录视为变更，(b) 仅重新聚合发生变更的 Feature 对应的目录子树，(c) 在文档中标注每个 Feature 的最后更新时间戳与所取版本号，(d) 未变更的 Feature 保留原有描述和结构 | (a) 执行首次全量生成 → Feature 经历新版本迭代（新增 v2/） → 再次运行 @sddu-docs → Agent 检测到该 Feature 变更 → 仅重写该 Feature 对应的目录子树 → 其他 Feature 内容不变，(b) 首次运行（产物不存在）时自动执行全量生成 | P1 |

## 6. 非功能需求 (NFR)
> 性能、安全、可用性等跨切面需求

| ID | 类别 | 需求描述 | 验收标准 |
|----|------|---------|---------|
| NFR-001 | 性能 | 首次全量扫描（17 个 Feature，约 30+ 个 spec.md / plan.md 文件）应在 120 秒内完成，不阻塞用户后续操作 | 在当前 SDDU 项目上执行全量扫描，记录 wall-clock 时间，≤ 120 秒 |
| NFR-002 | 兼容性 | 输出模板必须与现有 Handlebars 渲染基础设施兼容（使用 `#each`、`#if` 等标准 Handlebars 语法），不需要修改引擎代码 | 使用现有渲染管线渲染输出模板，无引擎报错 |
| NFR-003 | 可维护性 | 模板库的变体扩展机制应标准化 —— 新增场景模板只需创建 `sddu-docs.{scenario}.md.hbs` 文件，无需修改 Agent 指令模板或 build-agents.cjs | 创建新的场景模板文件后，Agent 能自动发现并（在匹配场景下）选择使用 |
| NFR-004 | 信息时效 | 文档应包含生成时间戳和所依赖 Feature 的版本号（从 state.json 读取），让读者能判断文档的时效性 | 输出的 `PROJECT.overview.md` 包含生成时间和各 Feature 版本清单 |

## 7. 边界情况 (EC)
> 异常场景和边界条件的处理方式

| ID | 场景 | 处理方式 |
|----|------|---------|
| EC-001 | 项目目录为空（无 `.sddu/` 目录或 Feature 目录） | Agent 提示「项目无可分析的 SDDU Feature 产物，请先完成至少一个 Feature 的 spec/plan 阶段」，不写入空文档 |
| EC-002 | 产物已存在 | 系统应检测变更并支持用户选择增量更新（仅更新变化部分）或全量重建 |
| EC-003 | 部分 Feature 的 `spec.md` 或 `plan.md` 缺失 | Agent 跳过缺失文件的 Feature，在全景文档中标注「缺失 spec/plan」及 Feature 名称，继续聚合其他完整 Feature |
| EC-004 | 某个 Feature 的 `spec.md` 格式与模板不一致（非标准结构） | Agent 尝试按章节标题模糊匹配提取信息；完全无法解析时标注「格式异常」并跳过该 Feature 的结构化提取，仅保留 Feature 名称 |
| EC-005 | 模板库中无匹配当前内容的模板 | Agent 回退到通用模板，输出结构化文档，不报错 |
| EC-006 | 用户自定义模板语法错误导致 Handlebars 渲染失败 | Agent 捕获渲染异常，提示「自定义模板渲染失败：[错误信息]，已回退到内置模板」，使用内置模板继续输出 |
| EC-007 | 产物目录 `.sddu/docs-tree-root/` 无写入权限 | Agent 提示「无法写入 .sddu/docs-tree-root/，请检查目录权限」，将完整输出写到对话窗口作为兜底 |
| EC-008 | 项目包含嵌套子 Feature（specs-tree-root 下的子目录结构） | Agent 递归扫描所有层级，在业务全景中按层级树展示 Feature 结构，不扁平化处理 |
| EC-009 | **增量更新 — 产物已存在时的变更检测** | 流程：(1) Agent 检测产物已存在，(2) 扫描各 Feature 的 state.json（phase 字段）和 spec.md/plan.md 的 mtime 对比上次生成时记录的时间戳，(3) 列出变更清单（如「检测到 3 个 Feature 发生变更：FR-AUTH, FR-API, FR-DB」），(4) 仅重写变更 Feature 对应的目录子树，未变更部分保持不变，(5) 增量更新完成后在文档中更新变更标记和本次变更的 Feature 清单 |
| EC-010 | **输出格式加载 — 用户自定义格式和内置格式均不可用** | Agent 按 FR-006 定义的优先级查找：用户自定义格式不存在 → 内置格式不存在 → 显式报错「未找到可用的输出格式，请确保至少存在用户自定义格式或内置格式」，终止执行 |
| EC-011 | **Feature 目录包含多个版本子目录（如 v1/、v2/）** | Agent 按版本号排序取最新版本目录，仅聚合该版本下的 spec.md / plan.md；在全景文档中标注所取版本号并列出该 Feature 的历史版本清单；历史版本的文档内容不纳入聚合 |
