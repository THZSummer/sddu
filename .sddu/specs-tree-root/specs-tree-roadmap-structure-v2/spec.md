## 2. 上下文
> 回顾问题背景和目标用户

上游 Feature FR-ROADMAP-TPL-001（v4.1.0）已把 `.sddu/ROADMAP.md` 从"随心所欲"收敛为**固定的 8 个 H2 章节**（项目愿景与定位 / 版本总览 / 特性索引 / 优先级（RICE Top N）/ 版本规划详述 / 依赖与风险 / 下一步行动 / 修订记录），并建立了 zone / entry 两级增量标记与合并机制。但章节**内部的组织逻辑**仍是扁平的、混装的 —— 用户在多轮对话中诊断出的核心痛点是：**「『下一步行动』就是个横切杂物箱，什么都往里装」**（P1），并叠加**双时间轴打架**（P2：版本轴 vs「立即/短期/中期/远期 + Phase/Wave」）、**问题无独立身份**（P3）、**独立「依赖与风险」章破坏三主体闭合**（P4）、**未立项提案无承载位**（P5）、**全文字表格无图**（P6）五个问题。

**用户已拍板（D1~D5，本 spec 不再追问）**：
- **D1 概览 / 详情分层**：清单层（版本 / 特性 / 问题 3 章粗表）+ 详情层（版本 / 特性 / 问题 3 章展开）+ 首尾（愿景 / 修订记录）= **8 H2**。
- **D2（用户A）**：依赖与风险取消独立章节，融入三主体（版本级 → 版本详情字段；特性级 → 特性详情字段；项目级 → 问题类型枚举 `风险` / `依赖`）；**每章章首加 1 个 Mermaid 图**描述本章。
- **D3（用户B）**：RICE 评分淘汰，优先级改 **P0/P1/P2**（特性详情字段）。
- **D4（用户C）**：章节命名区分 —— 清单层「XX 清单」vs 详情层「XX 详情」。
- **D5 执行边界**：本次仅改模板 + agent 指令（bump **v3.2.0**）；`.sddu/ROADMAP.md` 重排延后（用户手动装新版体验）；validate 阶段允许 `/tmp` 沙箱演练。

**目标用户**：SDDU 框架维护者（本项目 dogfooding）、ROADMAP 下游读者 / Agent（需按稳定语义定位版本 / 特性 / 问题）、SDDU 贡献者（读 Agent 指令理解章节语义）、框架使用者（后续按新模板自行迁移）。

**本次范围严格限定为设计态源码**（`src/`），依据 README「项目约束（Agent 必读）」——`.opencode/`（安装产物）与 `.sddu/`（流程产物）不得列为实现目标。

### 5.2 8 章结构与 zone 分配表（FR-001 / FR-002 / FR-003）
> 「清单层 ↔ 详情层」两粒度；模式 = `rewrite`（每次按最新内容整块重建）/ `preserve`（按键控合并，既有内容不静默丢弃）

| # | H2 章节 | zone id | mode | 层级 | 章首 Mermaid 图 |
|---|---------|---------|:----:|------|----------------|
| 1 | 项目愿景与定位 | `vision` | rewrite | 首尾 | 定位图 |
| 2 | 版本清单 | `version-list` | rewrite | 清单层 | 版本时间线 |
| 3 | 特性清单 | `feature-list` | rewrite | 清单层 | 特性状态分布 |
| 4 | 问题清单 | `issue-list` | preserve | 清单层 | 问题类型分布 |
| 5 | 版本详情 | `version-detail` | preserve | 详情层 | 版本-特性-问题关系图 |
| 6 | 特性详情 | `feature-detail` | preserve | 详情层 | 特性归属图 |
| 7 | 问题详情 | `issue-detail` | preserve | 详情层 | 问题归属图 |
| 8 | 修订记录 | `revision-log` | preserve | 首尾 | 修订时间线 |

> zone 合计 8 个（3 rewrite + 5 preserve）；元数据头沿用既有 `meta` 处理，不计入本表 8 个 content zone（FR-010）；`preserve` 区的 Mermaid 图随区**逐字保留**，`rewrite` 区的图随区**整体重建**（FR-003）。

### 5.3 依赖 / 风险信息归属判定表（FR-004）
> 取消独立「依赖与风险」章后，按"最近归属主体"判定承载位；无法归属任何版本 / 特性者视为项目级

| 归属层级 | 判定条件 | 承载位 | 形式 |
|---------|---------|--------|------|
| 版本级 | 依赖 / 风险指向某个具体版本（影响该版本交付） | §5 版本详情 | 对应版本 entry 的「风险与依赖」字段 |
| 特性级 | 依赖 / 风险指向某个具体特性 / 提案（影响该条目实现） | §6 特性详情 | 对应 entry 的「风险与依赖」字段 |
| 项目级 | 无法归属任何具体版本或特性（跨版本 / 全局性） | §4 问题清单 + §7 问题详情 | 类型枚举 = `风险` / `依赖` 的 P-xxx 条目 |

| NFR-008 | 可判定性 / 防漂移 | 信息归属判定表（§5.3）显式、可判定，防止依赖 / 风险再次漂移到错误章节 | agent 指令 §5.5 含判定表；三条归属规则均可由读者一次性判定，无歧义 |

## 7. 边界情况 (EC)
> 异常场景和边界条件的处理方式

| ID | 场景 | 处理方式 |
|----|------|---------|
| EC-001 | 既有产物**无任何 zone 标记** | 判定为**非模板结构**，**不重写**（非破坏）；提示用户由人工决定重构 / 保留 / 增量补充 |
| EC-002 | 既有产物含旧 zone 标记（如 `next-actions` / `version-overview` / `priority` / `dependencies-risks`） | 识别为**旧结构**，**不静默重写**；提示按新模板完整迁移（FR-012），由用户决定处理方式 |
| EC-003 | 模板中 zone 标记与 entry 标记**不配对**（开/闭缺失或错位） | **中止写入并输出诊断**（含 zone id / 位置），不产出结构不完整的文件 |
| EC-004 | 未立项提案缺 `PR-xxx` 编码 | 按规则**生成 `PR-xxx`**（`PR-001` 起顺序编号），不跳过登记 |
| EC-005 | `P-ID` 编码冲突（同号已存在） | **追加新号**（不复用、不覆盖既有编号），并在迁移提示中说明 |
| EC-006 | 特性在 `.sddu/specs-tree-root/` 下无对应 `state.json` | 保留该条目并在字段中**标注「推断」**及来源，不静默丢弃 |
| EC-007 | Mermaid 代码块损坏 / 语法非法 | **文档仍可读**（图退化为代码块，不阻塞正文与其他章节），并在验证阶段修复 |
| EC-008 | 在 §5 版本详情内发现应登记的问题 | 将该问题**外移至 §4 / §7** 登记，并在 §5 entry 内以锚点引用（不重复承载问题台账） |
| EC-009 | `preserve` 区已有既有内容 | **逐字保留**，仅按 entry 键控合并新增 / 更新条目，不静默丢弃既有内容 |
| EC-010 | 详情 entry 内含实现明细（文件级 / 任务级内容） | **禁止**；详档锚点指向 `specs-tree`（spec / plan / tasks），entry 仅承载规划级摘要 |
