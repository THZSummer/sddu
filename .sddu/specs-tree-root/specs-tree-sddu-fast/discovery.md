## 1. 问题定义
> 概括核心问题及其业务影响，回答"为什么需要关注"

| 核心问题 | 业务影响 | 不解决的成本 |
|---------|---------|------------|
| SDDU 缺少轻量入口 — 面对 bug 修复、配置调整、代码重构等日常简单任务（估算占 60-70% 工作量），用户被迫在"走完整 8 阶段"和"完全不用 SDDU"之间二选一，没有中间地带 | 用户日常高频的简单任务绕开 SDDU，改用普通 AI 对话；SDDU Agent 的领域知识（框架规范、模板系统、specs-tree 结构）和项目上下文能力被闲置 | SDDU 被定位为"重型框架"，仅用于复杂 Feature，丧失了覆盖开发者大部分日常工作的机会；SDDU 的领域知识壁垒无法在日常工作中发挥价值 |
| SDDU 完整流程对简单任务形成过度工程 — discovery→spec→plan→tasks→build→review→validate 的 8 阶段状态机要求产出 6 份中间文档、维护 state.json、走多 Agent 串行调度 | 用户在面对 1-2 个文件的小改动时，文档编写和状态管理的时间远超实际编码时间，造成强烈的"杀鸡用牛刀"感知 | 用户形成心理模型"小事不要用 SDDU"，框架在日常工作中持续失位；长期积累导致 SDDU 的活跃度和用户粘性下降 |
| SDDU 当前入口的认知负担过高 — 用户需理解 8 个阶段的语义、父子 Feature 规则、phase vs status 两字段模型、路由协议等概念才能正确使用 | 新用户上手周期长，轻量用户不愿投入学习成本；老用户在执行简单任务时需主动"跳过阶段"，心理上始终有"流程不完整"的负担 | 用户增长受限 — 只有愿意投入学习 SDDU 工作流的开发者才会成为活跃用户；大量潜在轻量用户被挡在门外 |

## 2. 用户画像
> 描述受影响用户角色及其场景，回答"谁遇到了什么问题"

| 用户角色 | 典型场景 | 关键痛点（用户原话） | 当前应对方式 |
|---------|---------|-------------------|------------|
| **SDDU 框架维护者**（核心用户） | 修改 Agent 模板、调整 opencode.json 配置、修插件注册 bug、补充测试用例 — 每天高频遇到 1-2 个文件的小改动 | 「改一个配置文件也要走 discovery→spec？太麻烦了。」 | 用普通 AI 对话直接改，放弃 SDDU Agent 的领域知识 |
| **SDDU 使用方开发者** | 在自己的项目中日常遇到小 bug 修复、代码重构、文档补充、代码审查辅助 — 不值得为此建立 Feature 目录 | 「我知道 SDDU 能做，但为一个小 bug 建整个 feature 目录太夸张了。」 | 手动直接改代码或用普通 AI 对话解决 |
| **SDDU 新手** | 刚接触 SDDU，被 8 阶段工作流和路由系统吓退，只想快速体验 SDDU Agent 的能力 | 「8 个阶段？我能不能先试试简单的？」 | 浅尝辄止，未形成使用习惯就放弃 |
| **SDDU 重度用户** | 已在完整流程中推进复杂 Feature，但中途遇到小问题（如调整 build 配置、补充遗漏的测试）需要快速解决，不希望打断主流程 | 「我不想为这个小修小补中断 spec→plan 的节奏，但又希望 Agent 知道当前 Feature 的上下文。」 | 切到普通 AI 对话，失去 Feature 上下文 |

### 用户场景还原（典型旅程）

**场景 A：SDDU 框架维护者修一个 Agent 注册 bug**

1. 发现 `sddu-docs` Agent 的描述文案有误
2. 需要修改 `src/adapters/opencode/agents/sddu-agents.ts` 中一行 description 字符串
3. **期望状态**：用 `@sddu-fast` 说出问题 → Agent 定位文件 → 修改 → 验证 → 结束，全程 30 秒
4. **当前状态**：要么手动改（失去 Agent 辅助），要么走完整 SDDU 流程（为 1 行改动建 feature 目录，产出 6 份文档）

**场景 B：SDDU 使用方开发者在开发中需要一个 code review**

1. 写完一段代码，想快速让 Agent review 一下
2. **期望状态**：`@sddu-fast review 这段代码` → 得到审查意见 → 结束
3. **当前状态**：要么用普通 AI 对话（失去 SDDU Agent 对项目结构的理解）

**场景 C：从 Fast 到完整 SDDU 的升级路径**

1. 用户用 `@sddu-fast` 开始修一个 bug，Agent 发现根因涉及 3 个模块、需要 API 变更
2. Agent 判断复杂度超阈值，建议："这个问题涉及跨模块变更，建议升级到 `@sddu 开始` 走完整流程"
3. 用户确认升级 → 手动运行 `@sddu 开始`（或 `@sddu-discovery`），从 discovery 或 spec 开始
4. Fast 会话内容作为非正式参考，不自动继承到 SDDU 流程中

## 3. 问题清单
> 按影响程度分级梳理所有识别到的问题，每项赋予唯一编号 Q-xxx

### 3.1 核心问题
> 影响面大、频率高、用户强烈感知

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-001 | **SDDU 入口"全或无"问题**：当前 SDDU 只有一个入口 —— 完整 8 阶段流程。用户面对简单任务（bug 修复、配置调整、代码重构、文档补充、测试编写、代码审查辅助、问题答疑、小型功能开发）时，必须在"走完整流程产出 6 份文档 + state.json"和"完全不用 SDDU"之间二选一。估算 60-70% 的日常开发任务落在这个中间地带（数据来源：用户反馈推测，非硬数据统计，标注为待验证假设 A-001）。 | 所有 SDDU 用户（框架维护者 + 使用方），每天多次 |
| Q-002 | **文档/状态管理负担遏制轻量使用**：8 阶段流程要求每个 Feature 产出 discovery.md → spec.md → plan.md → tasks.md → state.json → build.md → review.md → validate.md 共 6-8 份产物。对于 1-2 个文件的小改动，文档编写时间远超实际编码时间。用户反馈：「为一个小 bug 建整个 feature 目录太夸张」。 | 所有面临简单任务的用户 |
| Q-003 | **认知负担阻碍新用户上手和轻量使用**：用户需理解 8 阶段的语义（registered→discovered→...→validated）、父子 Feature 规则（父 Feature 不能执行 tasks/build/review/validate）、phase vs status 两字段模型、路由协议（sddu 入口 → 子 Agent 调度）、标记命令（suspended/terminated/merged）等概念。即使用户理解了，执行简单任务时仍需主动"跳过阶段"，心理上始终有"流程不完整"的负担。 | 新用户（100% 受影响），轻量用户（高频受影响） |
| Q-004 | **多 Agent 串行等待增加简单任务的时间成本**：完整流程涉及 sddu-discovery → sddu-spec → sddu-plan → sddu-tasks → sddu-build → sddu-review → sddu-validate 共 7 个 Agent 的串行调度，每个 Agent 启动都有上下文加载和工具调用开销。对于只需改一行配置的任务，等待 Agent 串行启动的时间远大于实际工作。 | 所有简单任务场景 |

### 3.2 次要问题
> 影响面中等、或为核心问题的衍生问题

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-005 | **绕过 SDDU 导致领域知识浪费**：用户用普通 AI 对话替代 SDDU 后，失去了以下能力：(a) SDDU 框架领域知识（Agent 模板规范、状态模型、specs-tree 目录结构、插件注册机制等）；(b) 项目上下文感知（当前 .sddu/ 目录中存在哪些 Feature、Agent 注册状态、模板文件位置等）。用户原话：「普通 AI 对话不知道 SDDU 框架的结构，我得花时间解释上下文。」 | 所有 SDDU 用户执行简单任务时 |
| Q-006 | **缺少升级路径感知**：当前不存在"先轻量试探再正式立项"的工作模式。用户要么一开始就承诺完整的 SDDU 流程，要么完全不碰。对于复杂程度不确定的任务（如"看起来是个小 bug 但可能很深"），用户缺乏低成本试探手段。一旦轻量尝试后发现复杂，没有从试探到正式立项的平滑过渡。 | 面对复杂度不确定任务的用户 |

### 3.3 潜在问题
> 目前影响小但可能恶化，或信息不足待验证

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-007 | **Fast 模式可能弱化 SDDU 的规范性价值**：如果 `@sddu-fast` 太好用，用户可能倾向于所有任务都用 Fast 模式，SDDU 的文档可追溯、阶段审查、质量保障等核心价值被稀释。当简单任务占比 60-70% 时，存在"fast becomes the norm"的风险。 | 长期使用者行为演变 |
| Q-008 | **两个入口的认知冲突**：`@sddu-fast` 和 `@sddu` 两个入口并存，用户可能对"什么时候用哪个"产生新的困惑。SDDU 路由 Agent（`@sddu`）是否需要感知或推荐 Fast 模式？两个入口的职责边界如何向用户传达？ | 所有 SDDU 用户 |

## 4. 竞品参考
> 记录竞品对类似问题的处理方式，回答"别人怎么做的、我们有什么不同"

| 竞品 | 是否处理过类似问题 | 处理方式 | 与我们场景的差异 |
|------|-------------------|---------|----------------|
| **Superpowers (StackBlitz)** | 是 — Superpowers 的核心设计就是"轻量对话式 + 按需深度" | (a) Skills 是纯 Markdown 文件，无状态机、无编译；(b) 用户在对话中直接触发 skill，Agent 按 SKILL.md 中的步骤执行；(c) 会话启动时自动注入 `using-superpowers` 指令提供全局上下文；(d) 各 skill 独立，skill 之间不耦合，无路由层；(e) 模块化设计：主控制器 + 子代理，子代理专注具体任务执行；(f) 支持 TDD 驱动开发和系统化调试流程 | Superpowers 的 Skill 系统无"完整流程"vs"快速模式"的二分，其所有 Skill 都是轻量级的；SDDU 需要保留 8 阶段流程的严谨性，同时增加轻量入口，是"双模"架构而非"全轻量" |
| **Claude Code** | 是 — Claude Code 提供极简入口 | (a) 无状态机，无阶段划分；(b) 单 Agent 对话式交互，理解问题→直接解决→验证结果；(c) 无中间文档产出，无 Feature 目录要求 | Claude Code 是完全无结构的自由对话，缺少 SDDU 的领域知识和项目上下文感知能力；SDDU Fast 模式需要在"无状态"和"有领域知识"之间取得平衡 |
| **Cursor Composer** | 是 — Cursor 支持快速任务和完整规划两种模式 | (a) Cmd+K（快速编辑，零上下文）vs Composer（完整上下文，多文件规划）；(b) 快速模式不需要上下文加载，直接运行；(c) 用户在同一 IDE 内切换模式，无需 exit/re-enter | Cursor 是 IDE 层产品，模式切换由 UI 实现；SDDU 是 Agent 层框架，模式切换需要在 prompt 和路由层实现 |

> ⚠️ **注意**: 以上竞品信息仅描述事实，不做方案推荐。SDDU Fast 模式的具化方案将在 spec 和 plan 阶段结合 SDDU 的实际约束（单包插件、独立 Agent 形态、无状态机、Handlebars 模板引擎）进行评估。

## 5. 假设与风险
> 记录问题挖掘过程中识别的假设和风险，供后续阶段验证和关注

### 5.1 关键假设
> 记录我们对问题理解所基于的假设，标注待验证项

| # | 假设内容 | 验证方式 |
|---|---------|---------|
| A-001 | **"60-70% 日常任务是简单任务"**是基于用户反馈推测，非硬数据统计。实际比例可能因项目类型、团队规模、开发阶段而异。 | 在 Fast 模式上线后，统计 `@sddu-fast` vs `@sddu 开始` 的调用比例，对比实际使用分布 |
| A-002 | **用户会从"普通 AI 对话"迁移到 `@sddu-fast`** — 假设用户愿意额外输入 `@sddu-fast` 前缀来换取 SDDU 领域知识和项目上下文感知。如果迁移成本（多输入 12 个字符）大于感知收益，用户可能继续用普通 AI 对话。 | 观察早期用户的调用频率和行为模式；收集"为什么不直接用普通对话"的反馈 |
| A-003 | **"完全信任"质量模型足够** — 假设 Fast 模式不需要 spec/plan/review 等质量关卡，Agent 自身的行为约束（通过 .hbs 模板定义）足以保证输出质量。这依赖 Agent 模板的编写质量。 | 对比 Fast 模式产出与完整 SDDU 流程产出的质量差异（抽样审查） |
| A-004 | **"按需读取"项目上下文是充分的** — 假设 Agent 不需要在启动时全量加载 .sddu/ 目录结构和项目文件，可在用户提及相关概念时按需读取。这依赖 Agent 的判断准确性（何时该读、何时不读）。 | 测试 Agent 在"用户未提及 Feature 名但任务涉及已有 Feature"场景下的上下文感知准确性 |
| A-005 | **用户能自行判断升级时机** — 升级路径设计中，用户自行决定从 discovery 还是 spec 开始。假设用户有足够信息做出正确判断。若用户经验不足，可能选错起点导致返工。 | 观察升级后的返工率（从 spec 退回 discovery 的比例） |

### 5.2 主要风险
> 识别可能影响问题判断或后续决策的风险因素

| # | 风险描述 | 影响程度 |
|---|---------|---------|
| R-001 | **两个入口的认知混乱**：用户可能不理解 `@sddu-fast` 和 `@sddu` 的区别和适用场景，导致使用焦虑或错误选择。如果路由 Agent (`@sddu`) 不引导 Fast 入口，用户可能根本不知道 Fast 模式存在。 | 中 |
| R-002 | **"Fast becomes the norm" 风险**：如果 Fast 模式体验好，用户可能滥用它处理不应走轻量模式的任务，导致代码质量下降、文档缺失、上下文丢失等 SDDU 核心价值被稀释。需要清晰的边界提示或 guardrails。 | 中 |
| R-003 | **Agent 升级判断不准**：Fast 模式依赖 Agent 自身判断"何时该建议升级"。如果判断阈值设置不当 — 太激进（频繁建议升级，失去轻量意义）或太保守（复杂任务不升级，产出质量低）— 都会影响用户体验。 | 中 |
| R-004 | **模板编写质量决定 Agent 行为**：`.hbs` 模板是 Fast 模式的行为定义蓝图。如果模板质量不足（边界不清晰、行为约束不明确），Agent 可能越界产出 spec 阶段的产物或反过来过于保守不敢行动。 | 高 |
| R-005 | **与现有 Agent 体系的命名冲突风险**：`@sddu-fast` 名称在现有 sddu-* 命名空间中无冲突，但需确保路由 Agent（`@sddu`）能正确区分。且如果未来需扩展其他"轻量"Agent（如 `@sddu-quick`），命名规范需提前约定。 | 低 |
