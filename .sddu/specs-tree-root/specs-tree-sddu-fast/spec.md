## 2. 上下文
> 回顾问题背景和目标用户

SDDU 框架当前入口存在"全或无"问题：用户面对 60-70% 的日常简单任务（bug 修复、配置调整、代码重构、文档补充、测试编写、代码审查辅助），被迫在"走完整 8 阶段流程（产出 6-8 份文档 + state.json）"和"完全不用 SDDU"之间二选一。缺少中间地带的轻量入口，导致：

- **核心问题**：轻量任务被迫绕开 SDDU，改用普通 AI 对话，SDDU Agent 的领域知识（框架规范、模板系统、specs-tree 结构）和项目上下文能力被闲置
- **文档负担**：8 阶段流程要求每个 Feature 产出多份中间文档，对 1-2 个文件的小改动，文档编写时间远超实际编码时间
- **认知壁垒**：新用户被 8 阶段状态机、phase/status 两字段模型、父子 Feature 规则等概念吓退
- **时间成本**：完整流程涉及 7 个 Agent 串行调度，每个 Agent 启动都有上下文加载开销

本 Feature 通过提供一个独立、无状态、零产物的轻量入口 `@sddu-fast`，形成与 `@sddu` 完整流程互补的"双模"架构，让用户根据任务复杂度自由选择入口——简单任务走 Fast 模式快速解决，复杂任务走完整 SDDU 流程保证质量。

**目标用户**：

| 用户角色 | 典型诉求 |
|---------|---------|
| SDDU 框架维护者 | 修改 Agent 模板、调配置、修注册 bug，期望 30 秒完成 |
| SDDU 使用方开发者 | bug 修复、代码重构、文档补充、code review，不想建 Feature 目录 |
| SDDU 新手 | 浅尝 SDDU Agent 能力，被 8 阶段吓退，需要一个低门槛入口 |
| SDDU 重度用户 | 主流程中遇到小修小补，不想中断 spec→plan 节奏 |

## 3. 目标与非目标
> 明确需求范围，防止范围蔓延

### 3.1 目标 (Goals)
> 明确本次要达成的业务目标

| # | 目标描述 | 映射问题 |
|---|---------|:-------:|
| G-001 | 提供零摩擦的轻量入口，让用户面对简单任务时无需走完整 8 阶段流程即可获得 SDDU Agent 辅助 | Q-001 |
| G-002 | 消除文档/状态管理负担 — Fast 会话不产生任何中间产物（discovery/spec/plan/tasks/state.json），执行完就结束 | Q-002 |
| G-003 | 降低认知负担 — Fast 模式无阶段概念、无状态追踪、无路由协议，用户只需描述问题 | Q-003 |
| G-004 | 消除多 Agent 串行等待 — 单一 Agent 在理解问题后直接动手解决，无需调度其他 Agent | Q-004 |
| G-005 | 保留 SDDU 领域知识价值 — Agent 理解 SDDU 框架结构、模板规范、specs-tree 组织、`docs-tree-root/` 项目全景文档、ROADMAP 版本路线图、`docs/` 参考文档等完整的项目知识体系，日常任务中持续发挥框架上下文优势 | Q-005 |
| G-006 | 提供升级路径 — 当任务复杂度超出轻量模式范围时，Agent 主动建议升级到 `@sddu 开始` 走完整流程 | Q-006 |
| G-007 | 缓解"Fast becomes the norm"风险 — Agent 内嵌任务边界自律，明确不适合 Fast 模式的任务类型并主动拒止 | Q-007 |
| G-008 | 消除双入口认知冲突 — 明确 `@sddu-fast` 和 `@sddu` 的职责边界和使用场景，确保用户知道何时用哪个 | Q-008 |

### 3.2 非目标 (Non-Goals)
> 明确本次不涉及的范围，防止需求蔓延

| # | 明确不做 | 说明 |
|---|---------|------|
| NG-001 | 不引入状态机或阶段划分 | Fast 模式的核心价值是"无状态"，任何 phase/status 追踪都违反设计原则 |
| NG-002 | 不产生 specs-tree-root 中间产物 | 不产出 discovery.md / spec.md / plan.md / tasks.md / state.json 等任何 SDDU 过程文档 |
| NG-003 | 不进 specs-tree-root 目录 | Fast 会话是一次性的，不在 .sddu/ 目录树中留下任何记录 |
| NG-004 | 不自动升级到完整 SDDU 流程 | 升级仅作为建议输出，用户手动执行 `@sddu 开始`；Fast 会话内容不自动迁移到 SDDU 流程 |
| NG-005 | 不支持复杂任务的多模块变更 | 跨模块架构调整、新 API 设计、新 Feature 规划等超出 Fast 模式范围的任务，由 Agent 拒止并建议升级 |
| NG-006 | 不替代现有 SDDU Agent（discovery/spec/plan/tasks/build/review/validate） | `@sddu-fast` 是补充入口，不修改、不弱化、不取代任何现有 Agent |
| NG-007 | 不修改 `@sddu` 状态机路由逻辑 | `@sddu` 的状态机 pipeline（registered→discovered→...→validated）不受影响；调度到 `@sddu-fast` 时不触发 phase 流转，Fast 任务不出现在 specs-tree-root 的追踪中 |

## 5. 功能需求 (FR)
> 每个需求必须有唯一标识符且可测试

| ID | 需求描述 | 验收标准 | 优先级 | 映射问题 |
|----|---------|---------|:----:|:-------:|
| FR-001 | **融入 SDDU 路由体系**：`@sddu-fast` 作为 SDDU 框架的增量子 Agent 注册到 OpenCode，拥有自己的 .hbs 模板和 agent 定义。`@sddu` 入口可识别简单任务并调度到 `@sddu-fast`；用户也可直接调用 `@sddu-fast`。Fast Agent 不经过 SDDU 状态机 pipeline，不与 sddu-core 共享状态管理代码，但受 `@sddu` 路由协调 | ① `@sddu` 收到简单任务（如"修复一个拼写错误"）时，可调度 `@sddu-fast` 处理；② 用户直接执行 `@sddu-fast "hello"` 时，系统调用的是 sddu-fast Agent；③ `@sddu-fast` Agent 的行为由其专属 .hbs 模板定义，不参与 state.json 的状态流转 | P0 | Q-001, Q-004 |
| FR-002 | **无状态对话**：Fast 会话不追踪 phase、不维护 status、不写入 state.json。每次会话独立，无跨会话状态保留。约束方式：在 .hbs 指令模板中禁止任何 phase 操作和 state.json 写入行为 | ① `.hbs` 模板中无 `phase` / `status` / `state.json` 写入指令；② 连续执行 3 次 `@sddu-fast` 会话，每次都是全新上下文（不携带前次会话的中间状态） | P0 | Q-002, Q-003 |
| FR-003 | **零中间产物**：Fast 会话不产出 discovery.md、spec.md、plan.md、tasks.md 等 SDDU 过程文档；不创建 specs-tree-root 下的 Feature 目录。约束方式：在 .hbs 指令模板中禁止"写入文档"和"创建 Feature 目录"的行为 | ① `.hbs` 模板中不包含"写入文档"或"创建 Feature 目录"的指令；② 模板中明确声明"Fast 模式不产出任何中间产物"作为行为约束 | P0 | Q-002 |
| FR-004 | **SDDU 领域知识注入**：Agent 在启动时或按需加载 SDDU 框架的领域知识——包括 Agent 模板规范、specs-tree 目录结构、插件注册机制、状态模型、路由协议、`docs-tree-root/` 项目全景文档、ROADMAP 版本路线图、`docs/` 参考文档等 | ① 向 `@sddu-fast` 提问"SDDU 的状态模型是什么？"，Agent 返回基于 SDDU 项目实际约定的回答（而非通用 AI 猜测）；② 向 `@sddu-fast` 提问"当前项目有哪些 Agent？"，Agent 能读取并列出 agents 目录下的注册信息；③ 向 `@sddu-fast` 提问"当前项目的版本路线图是什么？"，Agent 能读取 ROADMAP.md 并返回版本规划摘要 | P0 | Q-005 |
| FR-005 | **项目上下文感知**：Agent 可以读取 .sddu/ 目录结构，识别以下上下文信息：(a) specs-tree-root 下存在的 Feature 及其状态，(b) docs-tree-root 下由 @sddu-docs 产出的项目全景文档，(c) Agent 注册状态，(d) 模板文件位置，(e) ROADMAP 版本路线图。支持按需读取（不强制全量预加载） | ① 向 `@sddu-fast` 提问"specs-tree-root 下有哪些 Feature？"，Agent 读取目录并返回当前存在的 Feature 列表；② 用户未提及 Feature 名但任务涉及已有 Feature 时，Agent 能在相关文件中识别引用并提示；③ 向 `@sddu-fast` 提问"SDDU 的模板体系是怎么设计的？"，Agent 能读取 docs-tree-root/模板体系/ 下的全景文档并返回结构化回答 | P1 | Q-005 |
| FR-006 | **直接解决能力**：Agent 遵循"理解问题 → 直接解决 → 验证结果"的对话循环。在一次对话中完成文件读取、代码编辑、命令执行、结果验证的全流程 | ① 用户说"修复 sddu-docs Agent 的 description 拼写错误"，Agent 在一个会话中完成：定位文件→修改内容→确认语法正确→报告完成（无需用户说"下一步"）；② Agent 解决完问题后主动验证（如运行相关测试、检查语法），并将验证结果展示给用户 | P0 | Q-001, Q-004 |
| FR-007 | **升级建议**：当 Agent 判断当前任务超出 Fast 模式范围时，主动输出升级建议。建议内容包括：(a) 判断理由（为何超出 Fast 范围），(b) 建议起点（从 discovery 开始还是从 spec 开始），(c) 具体操作命令（`@sddu 开始` 或 `@sddu-discovery [feature名]`） | ① 向 `@sddu-fast` 提出"设计一个新的 API 认证模块"，Agent 识别为复杂 Feature 规划任务，输出升级建议而非直接执行；② 向 `@sddu-fast` 提出"重构整个数据访问层（涉及 10+ 文件、接口变更）"，Agent 识别为跨模块变更，建议升级；③ 升级建议中包含明确的"为什么不直接做"的理由说明 | P0 | Q-006 |
| FR-008 | **任务边界自律**：Agent 内嵌任务适宜性判断逻辑，明确区分"适合 Fast 模式的任务"和"应走完整流程的任务"。适合 Fast 的任务包括：bug 修复（单文件/少量文件）、配置调整、代码重构（范围可控）、文档补充、测试编写、代码审查辅助。不适合的任务包括：新 Feature 设计规划、跨模块架构变更、API 设计、需要正式文档产出的流程 | ① Agent 收到"设计一个用户权限系统"任务时，将其判定为"不适合"并建议升级；② Agent 收到"修复 src/config.ts 中 API_BASE_URL 拼写错误"时，将其判定为"适合"并直接执行；③ 任务边界判断逻辑在 .hbs 模板中明确定义，可被审查和调整 | P0 | Q-007, R-002 |
| FR-009 | **路由调度集成**：`@sddu` 入口具备识别简单任务并调度 `@sddu-fast` 的能力：(a) `@sddu` 收到用户请求后评估复杂度，简单任务直接调度 `@sddu-fast`，(b) `@sddu` 的 help/welcome 消息中列出 `@sddu-fast` 入口及简要说明，(c) `@sddu` 在调度到 `@sddu-fast` 时不做状态机流转 | ① 用户通过 `@sddu "修一个配置文件的拼写错误"` 时，Agent 识别为简单任务并调度到 `@sddu-fast` 处理；② 用户执行 `@sddu 帮助`，输出中包含 `@sddu-fast` 入口的描述；③ 被 `@sddu` 调度的 Fast 会话不触发 phase 变更 | P0 | Q-001, Q-008 |
| FR-010 | **双入口消歧**：`@sddu-fast` Agent 的 welcome 消息或自我介绍中明确说明其定位和使用场景，与 `@sddu` 的职责边界清晰区分。当用户提出模糊请求时，Agent 主动澄清并引导到合适的入口 | ① 首次调用 `@sddu-fast` 时，Agent 的问候语包含"我是 SDDU Fast 模式，适合 X 类任务，不适合 Y 类任务"的定位说明；② 用户在 Fast 会话中说"我想正式立项一个 Feature"，Agent 回应"Fast 模式不支持正式立项，请使用 `@sddu 开始` 或 `@sddu-discovery [feature名]` 走完整流程" | P1 | Q-008 |

## 6. 非功能需求 (NFR)
> 性能、安全、可用性等跨切面需求

| ID | 类别 | 需求描述 | 验收标准 | 优先级 |
|----|------|---------|---------|:----:|
| NFR-001 | 性能 | **会话启动响应速度**：从用户输入 `@sddu-fast` 到 Agent 返回首个有意义的响应（非纯问候语），应在 3 秒内完成。Agent 是单 Agent 对话，无需串行等待其他 Agent 调度 | ① 在正常项目和网络条件下，执行 `@sddu-fast "hello"` 计时，首响应 ≤ 3 秒；② Agent 不执行"加载所有 Agent 上下文"等阻塞性启动操作 | P0 |
| NFR-002 | 可维护性 | **模板质量要求**：.hbs 模板作为 Agent 行为的唯一定义来源，必须包含：(a) 清晰的任务边界定义（适合/不适合的任务类型），(b) 升级判断标准（何时建议升级），(c) 行为约束（不产出文档、不操作 state.json、不越界做技术设计），(d) 错误处理策略 | ① 模板文件可通过 code review 单独审查；② 模板中的任务边界定义和升级标准明确、可读、便于后续调整阈值；③ 模板不依赖外部状态文件（如 state.json）做决策 | P0 |
| NFR-003 | 零侵入 | **隔离性**：Fast 模式不得修改或干扰现有 SDDU 产物，包括：不修改 specs-tree-root 下任何文件、不修改现有 state.json、不影响其他 Agent 的注册状态、不修改 .sddu/ 目录结构（除读取外） | ① 执行 `@sddu-fast` 会话前后，git diff .sddu/ 无任何差异；② 运行中的 `@sddu` 流程不受并发 `@sddu-fast` 会话影响 | P0 |
| NFR-004 | 可靠性 | **错误处理与降级**：当文件操作失败、命令执行出错、或上下文不明确时，Agent 输出清晰的诊断信息，不静默失败、不猜测执行 | ① 文件读取失败时，Agent 明确报告"无法读取 [文件路径]：[错误原因]"；② 命令执行出错时，Agent 报告退出码和错误输出；③ 上下文模糊时，Agent 主动向用户确认，而非基于不完整信息行动 | P1 |
| NFR-005 | 可用性 | **无历史负担**：Fast 会话之间完全独立，不累积状态。用户可以连续执行无限次 Fast 会话而不会产生性能退化或上下文膨胀 | ① 连续执行 20 次 Fast 会话，会话间启动速度无明显衰减；② 系统资源（内存、文件描述符）不随 Fast 会话次数线性增长（每次会话结束后清理） | P1 |
| NFR-006 | 兼容性 | **与现有 Agent 体系共存**：`@sddu-fast` 的命名（`sddu-fast`）不与现有 `sddu-*` Agent 冲突。注册方式遵循现有 subagent 注册规范 | ① `@sddu-fast` 注册后，所有现有 `sddu-*` Agent 仍正常工作；② 注册配置不修改现有的 agent routing 逻辑 | P1 |

## 7. 边界情况 (EC)
> 异常场景和边界条件的处理方式

| ID | 场景 | 处理方式 | 优先级 |
|----|------|---------|:----:|
| EC-001 | 用户用 `@sddu-fast` 提出明显超出范围的任务（如"设计一个完整的用户权限系统"、"从零搭建微服务架构"） | Agent 判定为"不适合 Fast 模式"，输出升级建议（含判断理由、建议起点、操作命令），拒绝直接执行。不可用"先做一部分再升级"的模糊策略 | P0 |
| EC-002 | 用户在一个没有 .sddu/ 目录结构的裸项目中调用 `@sddu-fast` | Agent 照常工作——代码读写、命令执行、快速解决问题等核心能力不受影响。缺少 .sddu/ 只是少了一部分项目上下文信息（specs-tree、docs-tree、ROADMAP 等），不影响 Fast 模式的核心价值。Agent 不强制创建 .sddu/ 目录 | P0 |
| EC-003 | 用户要求在 Fast 会话中产出 spec.md 或 plan.md | Agent 明确回应"Fast 模式不产出过程文档"，并建议使用 `@sddu` 完整流程。如果用户坚持需要文档产出，引导升级 | P1 |
| EC-004 | 用户连续用 `@sddu-fast` 完成多个小任务但累积下来实际构成了一个大型重构 | Agent 无状态，不追踪跨会话的累积效应。这是 Fast 模式的设计取舍——不被追踪意味着也不会被提醒"该升级了"。如果用户意识到累积效应，应自行切换到 `@sddu` 流程 | P1 |
| EC-005 | `@sddu-fast` 会话执行的文件操作与另一个并发会话（包括另一个 Fast 会话或 build Agent）冲突 | 依赖底层系统的文件冲突机制（git merge conflict 或文件锁）。Fast 模式本身不实现分布式锁或事务——这是并发操作的自然风险，Fast 模式只需在被操作系统报错时清晰报告，不静默失败 | P2 |
| EC-006 | 用户在 Fast 会话建议升级后，立即在同一个上下文中说"好的，升级" | Agent 回应"请手动执行 `@sddu 开始` 或 `@sddu-discovery [feature名]`"，不自动触发升级流程。Fast 会话内容不自动迁移到 SDDU 流程（按设计决策 3） | P0 |
| EC-007 | 用户问 Fast Agent "我当前在哪个阶段？"或"这个 Feature 的 phase 是什么？" | Agent 回应"Fast 模式无阶段/状态概念"，简要解释 Fast 的定位差异。不创建 state.json 来回答此问题 | P2 |
| EC-008 | 用户在 Fast 会话中引用 specs-tree-root 下一个存在的 Feature 名称（如"这个改动和 specs-tree-sddu-fast 有关"） | Agent 可以读取对应 Feature 目录的上下文文件（discovery.md/spec.md 等），将其作为理解任务背景的参考，但 fast 本身不修改这些文件，也不将当前会话"关联"到该 Feature | P2 |
| EC-009 | Agent 判断任务复杂度在边界线上（如涉及 3-5 个文件、有小范围接口变更但整体可控） | Agent 采取"先询问后行动"策略：向用户说明任务复杂度判断及其不确定性，给出"可以在 Fast 模式尝试"或"建议升级"两个选项，让用户做最终决策。不可替用户决定 | P1 |
