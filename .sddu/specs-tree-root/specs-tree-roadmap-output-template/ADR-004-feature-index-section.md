# ADR-004: 新增「特性索引」章节 — 第 8 个 H2 + `feature-index`（`mode="rewrite"`）投影区

## 状态
ACCEPTED

## 背景

用户查看按 R2 修复后模板试渲染的 `.sddu/ROADMAP.preview-v2.md`（133 行）后指出：

> 「缺少特性清单，与 specs-tree 承接不起来，有了断层，那么多特性哪里来的」

经核实，这是本 Feature 的**规格内部矛盾**：

- `src/templates/agents/sddu-roadmap.md.hbs` **§1 职责边界**声明「**输出**: **特性清单** + 版本路线图」；
- 但输出模板**骨架仅有 7 个 H2**（`spec.md` FR-003 及 agent §5.5 均规定「集合与顺序固定为 7 个……不得新增」），其中**没有任何位置**承载「特性清单」；
- 且 agent §5.5 排除内容表 / §5.7 自检项写明「**不含逐 Feature 明细表**」。

结果：`.sddu/specs-tree-root/` 下 **24 个 Feature** 中，roadmap 产物仅在 `version-overview` / `priority` / `version-plan` 零星点名 **5 个**，且 **0 个**带 specs-tree 目录锚点 —— roadmap 与 specs-tree 之间出现**断层**：读者无法从 roadmap 追溯到「这么多 Feature 从哪来、各自状态与目录归属如何」。这与本 Feature 的动机（G-001 消除结构漂移、可被下游稳定解析引用）直接冲突。

约束条件（沿用 plan 阶段验证的既有结论，未变）：

1. **无运行时渲染代码**：模板查找、`<<变量名>>` 替换、渲染全由 LLM Agent 依指令执行（ADR-003）；索引内容取自 `.sddu/specs-tree-root/*/state.json`，属**实时推导**数据，非用户手写资产。
2. **H2 上限**：FR-006 规定 H2 章节数 ≤ 8。修订前为 7 个，尚有 1 个余量，**无需突破上限**。
3. **可解析性**：NFR-006 / EC-010 要求标题稳定；新增章节须记入「修订记录」。
4. **「精简顶层规划」定位**：不得借机引入与 docs 重叠的现状审计或与 spec/plan/tasks 重叠的实现明细。

## 决策

**新增第 8 个 H2「特性索引」**，并配套新增 1 个 `mode="rewrite"` zone，具体如下：

1. **位置：紧随「版本总览」之后**（原 §2 之后），其余章节顺延编号：

   `1 项目愿景与定位 → 2 版本总览 → 3 特性索引（新增） → 4 优先级 → 5 版本规划详述 → 6 依赖与风险 → 7 下一步行动 → 8 修订记录`

   理由：形成「**版本（总量） → 构成版本的特性（明细索引） → 优先级 → 版本规划详述（逐版本落地）**」的自上而下阅读流；「修订记录」恒为**最后一个 H2**（既有约定不破）。

2. **新 zone：`id="feature-index"`，`mode="rewrite"`**（zone 总数由 8 = 5+3 变为 **9 = 6+3**）。
   - 选 `rewrite` 而非 `preserve`：本区是**从 `.sddu/specs-tree-root/` 实时推导的投影**（数据源为各 Feature `state.json`），必须随 Feature 状态变化整体重建，**不应承载用户手写内容**；若用 `preserve` 则会与「实时投影」语义冲突并造成陈旧数据滞留。
   - 该 zone 与 H2 标题解耦（ADR-001 R5），不影响既有合并机制。

3. **索引级内容（禁止滑向明细）**——列固定为 5 列：

   | 列 | 取值 |
   |----|------|
   | Feature ID | `state.json.featureId`；缺失时按目录名推断并标注「推断」 |
   | 名称 | `state.json.name`（缺失时按目录名推断） |
   | specs-tree 目录 | `.sddu/specs-tree-root/` 下的实际目录名（**承接锚点，逐行给出**） |
   | 状态 | `state.json.status`；缺失时按统一规则由 `phase` 推断（`validated`/`7` → `completed`；中间阶段 → `in-progress`；无 `phase` → `unknown`） |
   | 版本归属 | `state.json.version`；缺失时写「不适用」 |

   排序依据须在章节内**显式声明**且全文一致（默认按「版本归属」升序、无版本归属置末，同版本内按目录名字典序）。

4. **规格同步**：FR-003 的「7 个 H2」由本 Feature `spec.md` §5.1 **SUP-002** 显式修订为 8 个；agent 指令 §1 / §5.4.1 / §5.4.4 / §5.5 / §5.7 / 修订记录 逐处同步；输出模板新增章节 + zone + 尾部 NOTE（7→8）。
5. **承接锚点补强**：`version-plan` 各 entry 的「关键特性」项中的 Feature 引用一律带 specs-tree 目录锚点（形如 `FR-AGENT-SCOPE-001（specs-tree-agent-scope-realignment）`），使 roadmap 内每一处 Feature 引用都能走到目录。

## 后果

**正向**：

- **断层闭合**：`roadmap` 与其上游 `specs-tree-root` 之间建立逐行目录锚点，「特性清单」在 §1 承诺的承载位落地；24 个 Feature 可被完整索引，而不再是「5 个被点名」。
- **可解析性保持**：新增章节标题稳定、顺序固定、编号连续；「修订记录」仍为末位 H2；下游按标题字符串解析不受影响。
- **定位不漂移**：索引 ≠ 明细——本区仅承载索引级字段，与 docs 重叠的审计 / 覆盖率、与 spec/plan/tasks 重叠的实现明细继续排除，符合 G-004。
- **上限不突破**：H2 由 7 → 8，仍在 FR-006 的 ≤ 8 上限内（现为恰好 8）。
- **机制同构**：新 zone 沿用既有双端注释 + `mode` 语义，`rewrite` 与 `meta` / `version-overview` 等同类，无新机制、无新代码。

**代价 / 残余风险**：

- 既有章节编号整体后移 1，H2 标题字符串随之变化 → 属 EC-010「结构变更须记入修订记录」的适用场景，已在 agent 修订记录 v3.1.2 / spec 修订记录 v1.1 / 本 ADR 显式记录。
- 对**已渲染产物**而言，新增章节意味着一次结构变更；本 Feature 约定**不迁移**现存 `.sddu/ROADMAP.md`（RT-004 / NG-001），故仅影响后续按新模板生成 / 重写的产物。
- 24 个 Feature 的实时索引依赖 `state.json` 字段完整度；对 `featureId` / `status` / `version` 缺失者，统一按推断规则处理并标注（避免因个别残缺而中断索引）。
- 索引长度随 Feature 数增长（当前 24 行）→ 由 FR-006 的篇幅指导上限 ≤ 400 行兜底；若逼近上限，优先压缩 `version-plan` 明细而非牺牲索引（索引是承接锚点）。

**对既有 ADR 的修订**：本 ADR **修订 ADR-001 中「8 个 zone 与 spec FR-003 的『固化 5 + 保留 3』一一对应」的基线** —— 经本 ADR，zone 基线更新为 **9 个 = 6 rewrite + 3 preserve**（新增 `feature-index` 为 rewrite）。ADR-001 的标记语法、命名空间、缺省安全语义等**机制性结论全部不变**，仅区段数量与枚举随之扩充；ADR-002 的三类合并策略（`version-plan` / `next-actions` / `revision-log`）不受影响（`feature-index` 属 rewrite，走 C1 整块替换）。

## 备选方案与否决理由

| 备选 | 否决理由 |
|------|---------|
| 置于「优先级」之后（而非「版本总览」之后） | 阅读流断裂：读者先被 RICE 排名带向「未来提案」，再回头补 Feature 全量索引，割裂「版本 → 构成版本的特性」的顺次呈现；且「优先级」聚焦**活跃提案**，与「特性索引」全量承接的系统视图不同层，不宜相邻 |
| 置于末尾（「修订记录」之前） | 索引是承上启下的导航性内容，置于文件末尾会使其与 §1 承诺的「特性清单」位置感脱节；且需重排「修订记录」末位约定 |
| 用 `mode="preserve"` 承载 `feature-index` | 与「实时投影」语义冲突：该区数据源为各 Feature `state.json`，必须每次重建；`preserve` 会保留陈旧行、无法反映 Feature 状态变化，并诱发「索引被当作用户手写资产」的误用 |
| 不新增章节，把 Feature 清单塞进 `version-overview` 或 `priority` 的既有表格 | 表格列语义与承载容量均不匹配（版本表 / RICE 表列固定），且会把「版本」「提案」与「全量特性」三种不同实体混在同一表内，破坏 NFR-006 的稳定解析 |
| 扩成「逐 Feature 明细表」（含实现 / 任务 / 覆盖率） | 直接违反 FR-006 与「精简顶层规划」定位（G-004）、越界侵犯 spec/plan/tasks/docs 职责；本 ADR 明确「索引 ≠ 明细」 |
| 新增第 9 个 H2 或拆分多文件承载索引 | 突破 FR-006 的 H2 ≤ 8 上限 / 违反 NG-002 单文件原则；而当前恰有 1 个 H2 余量可用，无需越界 |
