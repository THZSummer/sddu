# ADR-001: roadmap 增量保留区标记语法 — 双端 HTML 注释 + zone/entry 两级 + 显式 mode

## 状态
ACCEPTED

## 背景

`@sddu-roadmap` 的产物 `.sddu/ROADMAP.md` 是**单文件 + 增量更新**的长文档（当前项目实测 1382 行），且本 Feature 要求以外部 Handlebars 模板（`sddu-roadmap.md.hbs`）作为结构的唯一权威来源（spec FR-001/FR-003/FR-005）。这带来一个必须解决的技术矛盾：

- 模板是**每次渲染的新骨架**（章节集合与顺序唯一、可预期 → G-001）；
- 产物却是**被增量维护的历史文档**（版本规划详述、下一步行动、修订记录需要跨次保留 → RT-003）。

「保持章节层级不变」与「增量更新既有内容」若不显式区分，只能二选一：整篇重写会丢失历史内容，按内容猜测定位则退化为结构漂移。spec 因此把该机制（OP-002）显式移交 plan：FR-005 只定「模板须显式区分重写区 / 保留区」，标记语法与合并算法由 plan 设计。

约束条件（plan 阶段源码验证得到，直接影响可选方案空间）：

1. **无运行时渲染代码**：模板查找、`<<变量名>>` 替换、渲染全部由 LLM Agent 依指令执行（`grep -rn "\.hbs" src/ --include='*.ts'` 仅命中一条注释；`package.json` 无 handlebars 依赖）。因此标记必须是**纯文本、无模板逻辑**（FR-001 亦禁止渲染期脚本逻辑）。
2. **NFR-006 / EC-010**：H2 标题字符串必须稳定可被下游解析，不得因机制引入而漂移。
3. **NG-005 / C-004**：不得触碰 `.sddu/`、`.opencode/` 作为实现目标；因此锚点只能存在于「模板 + 产物」两者之中。

## 决策

采用**双端 HTML 注释标记**，语法如下：

```text
zone-open   ::= '<!-- sddu:zone id="' ZONE_ID '" mode="' ('rewrite'|'preserve') '" -->'
zone-close  ::= '<!-- /sddu:zone -->'
entry-open  ::= '<!-- sddu:entry id="' ENTRY_ID '" -->'      ; 仅在 mode="preserve" 内
entry-close ::= '<!-- /sddu:entry -->'
ZONE_ID  ::= [a-z][a-z0-9-]*    ; 模板内固定，与 H2 标题解耦
ENTRY_ID ::= 渲染后不含空格/引号/斜杠的稳定键（roadmap 取版本号）
```

关键设计取舍：

1. **标记随产物写出（双端）**，而非仅存于模板。产物因此自携带定位锚点，下次运行无需猜测。
2. **8 个 zone 与 spec FR-003 的「固化 5 + 保留 3」一一对应**：`meta` / `vision` / `version-overview` / `priority` / `dependencies-risks` = `rewrite`；`version-plan` / `next-actions` / `revision-log` = `preserve`。
3. **zone 只包裹 H2 标题之下的内容区**，H2 标题始终由模板产出 → 标题集合与顺序不受合并影响（满足 NFR-006，机制与标题解耦）。
4. **缺省安全语义**：未标注 == `rewrite`。标记丢失只会退化为「重写」，不会产生乱合并。
5. **`entry` 仅用于块状可独立合并的内容**（roadmap 只有 `version-plan`）。表格类区段（`revision-log`）改用「自然键列」合并——HTML 注释行会截断 Markdown 表格，故禁止在表内使用 entry 标记。
6. **保留命名空间 `sddu:`**：非 `sddu:` 前缀的 HTML 注释 = 编写期说明（如模板末尾 `<!-- NOTE: … -->`），不得写入产物。既有先例：`src/templates/outputs/sddu-plan.md.hbs:51` 的 Migration Note 注释在当前全部 `.sddu/*/plan.md` 产物中均不存在。

## 后果

**正向**：
- 合并从「依赖标题字符串（易漂移）」变为「依赖自携带锚点（确定）」；失败模式由「静默丢内容」转为「标记缺失/不成对 → 可检测 → 中止询问」（治理 EC-004 与 FR-012 的非破坏性要求）。
- 与既有 Agent-Native 模板机制同构，不引入第二套机制、不新增运行时依赖。
- 下游按 H2 字符串解析（EC-010）完全不受影响；标记在 Markdown 渲染视图中不可见。
- 静态可校验（`grep -c 'mode="preserve"'` = 3、`mode="rewrite"` = 5、`sddu:entry` = 2），review/validate 具备确定性检查手段。

**代价 / 残余风险**：
- 产物引入 16 行注释标记（对渲染不可见，但对原文阅读者是视觉噪声）；模板篇幅增加约 16 行（仍在 NFR-007 ≤ 200 行内）。
- 机制正确性依赖 LLM 依指令执行，无编译期保证 → 由 agent 指令 §5.4 强制流程 + §7 规则 + §8 异常表 + validate 幂等/配对测试兜底（载体决策见 ADR-003）。
- 未来若从 LLM 渲染改为代码渲染，`sddu:` 标记语法可被直接复用为解析契约（向前兼容）。

## 备选方案与否决理由

| 备选 | 否决理由 |
|------|---------|
| 单端标记（仅模板内）+ 标题驱动合并 | 锚点依赖标题字符串；用户自定义模板或 LLM 微调标题即失配，与「消除结构漂移」动机正面冲突；无法区分「模板结构」与「恰好同标题」，EC-004 判定退化 |
| 产物头部 YAML/JSON 元数据块记录保留区范围 | 与「元数据头部为 blockquote 统一约定」（FR-004 + NFR-001）冲突；行号范围会因任意编辑整体失效 |
| 独立旁路状态文件（如 `.sddu/.roadmap-state.json`） | 引入第二产物，违反「单文件」原则（NG-002）且需额外的工程边界与同步机制 |
