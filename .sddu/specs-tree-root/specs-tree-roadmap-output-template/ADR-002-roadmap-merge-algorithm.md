# ADR-002: roadmap 合并算法 — 条目级 upsert + 清单保留式 + 表格自然键追加

## 状态
ACCEPTED

## 背景

ADR-001 定义了标记语法（锚点），但「锚点如何驱动合并」仍需算法定义：spec FR-005 只要求「增量更新只改写保留区内对应片段，不得改变章节集合与顺序」，并把这部分（OP-002 机制）显式移交 plan。同时若干约束界定了算法的可行空间：

- **EC-003**：首次生成须全量生成，`生成方式` = 「完整生成」。
- **EC-004 / FR-012**：既有产物为旧/非模板结构时**不静默重写、不自动迁移**，由用户决定。
- **EC-006**：某章节不适用时允许标注「不适用」，但**不得改变章节集合与顺序**。
- **EC-007**：正文超 400 行 / 章节超 8 个 → **提示收敛或外移**，不静默截断、不静默扩章。
- **NFR-006 / EC-010**：标题稳定可解析；模板或结构变更须记入修订记录。
- 三个保留区的内容形态不同：`version-plan` = 按版本分块的 H3 块；`next-actions` = 行动项清单；`revision-log` = 追加式表格。**统一用一种合并策略必然在某类内容上失真**。

## 决策

按保留区的内容形态**分派三种合并策略**，并以统一的 Step A–D 流程收口：

**Step A 判定生成方式**
- A1 产物不存在 → `完整生成`（EC-003）。
- A2 产物存在且含 ≥1 个合法 `sddu:zone` → `增量更新`。
- A3 产物存在但无合法标记 → 判「非模板结构」：**不修改文件**，提示并给三选项（按新模板重构 / 保留现状 / 仅增量补充），等用户决策（EC-004 / FR-012）。

**Step B 快照既有保留区**：解析 zone 配对 → `zone_id → 原文`；`version-plan` 再解析 entry 为有序 `[(entry_id, 原文)]`；`next-actions` / `revision-log` 构建有序条目/行列表（键分别为条目文本、`版本` 列）。**B4：标记不成对/嵌套错乱 → 中止合并 + 诊断行号 + 询问用户，不静默重写。**

**Step C 渲染并合并**
- C1 `rewrite` 区（`meta`/`vision`/`version-overview`/`priority`/`dependencies-risks`）→ 整块替换。
- C2 `preserve` 区按形态分派：
  1. `version-plan` — **条目级 upsert（键 = 版本号）**：以快照顺序为基线；同 id → 替换该 entry（记「更新」）；新 id → 按版本序追加（记「新增」）；快照中未提及的 entry → **一律保留**（记「保留」）。不删除、不重排既有条目。
  2. `next-actions` — **清单保留式**：既有条目逐字保留；新行动项追加；已完成项仅在**用户显式确认后**才勾选/移除，否则记「保留」。
  3. `revision-log` — **追加式 + 自然键更新**：既有行逐字保留；本次变更追加新行；同「版本」列已存在 → 更新该行而非重复追加。
- C3 **结构校验（失败即中止，不写文件）**：H2 集合与顺序 == 模板（7 个）｜zone/entry 全部配对且 ZONE_ID 与模板一致｜H2 ≤ 8 且行数 > 400 时按 EC-007 提示，用户确认后方可写｜各 Markdown 表格列数与表头一致。

**Step D 写出与报告**：仅写 `.sddu/ROADMAP.md`；更新 `版本`/`更新人`/`更新时间`/`更新说明`/`生成方式`；输出合并摘要（新增/更新/保留计数 + 冲突项 + 超限提示）。

**冲突处理**：同 entry_id 内容冲突 → 以新内容为准但**必须在摘要列出差异要点**；无法自动裁决者（如要求移除既有版本）→ 交用户裁决，不静默处理。

**幂等性要求**：输入未变化时二次运行，rewrite 与 preserve 区均逐字节一致；**仅当本次确有内容变更时才追加修订记录行**。

## 后果

**正向**：
- 三种内容形态各得其法：块状内容按版本键控（可独立更新单个版本）、清单以「不丢用户资产」优先、表格追加式（符合审计语义）。
- 失败模式可检测且默认安全：A3/B4/C3 三道闸门保证「宁可不写，不可乱写」；C3 同时把 EC-006/EC-007 从「口头规则」变成「写文件前的校验」。
- 幂等要求直接转化为可执行回归测试（二次运行 diff、`revision-log` 不重复追加），使 LLM 行为的正确性具备可验证性。

**代价 / 残余风险**：
- 算法以自然语言写进 agent 指令 §5.4（约 40 行），有一定执行依赖（载体权衡见 ADR-003）。
- `version-plan` 的 entry 粒度依赖「版本号」为稳定键；若用户用非版本号命名（如「Q3 迭代」），键仍唯一但排序需按模板/用户给定顺序 → 已在算法中定义为「以快照顺序为基线，新条目按版本序追加」，避免依赖字典序。
- 既有内容永不自动删除：长期运行可能出现「已废弃版本仍保留」→ 由 EC-007 的收敛提示与人工裁决覆盖，符合「不静默处理」原则。

## 备选方案与否决理由

| 备选 | 否决理由 |
|------|---------|
| 章节级 last-write-wins（保留区也整块重写） | 直接丢失历史内容，与 RT-003「增量更新」及 FR-005 相悖 |
| 章节级 append-only（不改既有，只追加整块） | 同一版本信息会重复累积，违背「消除结构漂移 / 精简」目标（G-001、G-004） |
| 行级 diff/patch（通用三方合并） | 无版本控制上下文时无法判定「用户编辑 vs 旧内容」，冲突率极高；且要求 LLM 做行级 diff 不可靠 |
| 引入 `.sddu/` 旁路状态文件记录哈希/合并基线 | 违反单文件原则（NG-002），并新增第二个需同步的产物 |
