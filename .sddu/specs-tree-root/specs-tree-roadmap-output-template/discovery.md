## 1. 问题定义
> 概括核心问题及其业务影响，回答"为什么需要关注"

**动机（用户已确认，RT-002）**：当前 `.sddu/ROADMAP.md` 就是最好的反面教材 —— 用户原话：**「就拿当前项目的 roadmap 来作为反例，AI 简直是随心所欲，完全看不懂」**。即：产品线上最大的项目级产物，其输出结构完全不受约束，读不懂、指望不上。**本 Feature 的核心动机是消除输出结构漂移，而非仅仅"与其他 Agent 保持一致"。**

| 核心问题 | 业务影响 | 不解决的成本 |
|---------|---------|------------|
| `@sddu-roadmap` 产出真实落盘产物 `.sddu/ROADMAP.md`（当前 1382 行 / 19.0.0 版），却没有专属输出模板；其 §6 声明「输出为**内置固定格式**（不通过外部模板文件定义）」，结构实际由 §5 内联的一段约 47 行骨架"约束"——而该骨架早已失效 | 结构无权威来源 → 每次生成的章节命名/顺序/粒度随 LLM 自由发挥（用户原话：「AI 简直是随心所欲，完全看不懂」）。ROADMAP 是模板化体系里唯一的孤岛，下游无法对文档结构建立稳定预期 | 结构漂移随每次 ROADMAP 更新持续放大；项目级长文档无法被稳定解析、比对、引用；框架一致性承诺被持续侵蚀 |
| 内联骨架与实际产物严重不一致（**结构漂移已事实发生**）：§5 骨架仅含约 9 个章节，实际产物另含「项目状态速览 / 关键警示 / 功能完成时间线 / 已完成版本回顾 / 跨版本 RICE 总排名 / 附录 A 文件覆盖率 / 附录 B 全量审计」等大量章节；骨架内表格还存在列数不一致（行 214–216：表头 5 列，示例行 `\| v1.0.0 \| Phase 1 \| 2026-01-01 \| 基础功能 \| ✅ 已完成 \| SDDU Team \|` 为 6 列） | 指令里的"格式要求"与实际输出脱节，规范失去约束力，等于事实失效 | 结构漂移只会越演越烈，无人知道"正确的 ROADMAP 长什么样" |
| 输出格式定义位置偏离框架的**统一模板逻辑**：8 个有真实产物的 Agent（discovery/spec/plan/tasks/build/review/validate/docs）§6 均为「输出模板」节，声明「用户自定义模板（优先）`.sddu/templates/agents/output/sddu-X.md.hbs` > 插件内置模板（兜底）`.opencode/plugins/sddu/templates/output/sddu-X.md.hbs`」两级查找；`sddu-roadmap` 是唯一例外。且框架规范自相矛盾：FR-TPL-001 FR-021 / EC-004 规定「辅助 Agent（roadmap/tree/docs）输出为内置固定格式，不走用户自定义模板覆盖路径」，FR-DOCS-OPT-001 却为 docs 交付了 20 个模板 | roadmap 无法被用户覆盖，模板引擎（Handlebars `<<变量名>>`）与构建分发链路（`build-agents.cjs` 递归裸拷贝 `src/templates/outputs/**` → `dist/templates/output/`）对它均不生效；同类辅助 Agent 得到相反处置，标准不统一 | 后续每新增辅助 Agent 都要重新争论"要不要模板"；缺乏可复用的判定依据 |

> **规范矛盾的方向已由用户决策（RT-001 ①）**：**统一逻辑，支持覆盖** —— 修订 EC-004，让所有 agent 的输出模板走统一逻辑，roadmap 不再作为"内置固定格式"的例外。详见附录 A / 附录 B。

## 2. 用户画像
> 描述受影响用户角色及其场景，回答"谁遇到了什么问题"

| 用户角色 | 典型场景 | 关键痛点（用户原话） | 当前应对方式 |
|---------|---------|-------------------|------------|
| **SDDU 框架维护者（本项目 dogfooding）** | 作为 ROADMAP 的主要读者与框架 owner，打开当前项目的 ROADMAP 试图理解全局规划 | 「就拿当前项目的 roadmap 来作为反例，AI 简直是随心所欲，完全看不懂」（RT-002 原话） | 忍受现状；在 discovery 中把该缺口立为 Feature |
| **ROADMAP 的读者 / 下游 Agent** | `@sddu-spec`、人工读者需要按稳定结构定位 ROADMAP 中的章节 | 「同一份 ROADMAP，19.0.0 和上一版章节顺序就不一样了，没法写脚本引用」 | 人工阅读、人工判断章节位置，无法自动提取 |
| **ROADMAP 的自定义需求用户** | 希望 ROADMAP 按自己团队口径组织（如"本周优先事项"换成"双周迭代"、调整 RICE 表列），尝试按其他 Agent 的约定放置 `.sddu/templates/agents/output/sddu-roadmap.md.hbs` | 「别的 Agent 都能在 `.sddu/templates/` 下覆盖，roadmap 没这个口子」 | 无法覆盖；只能人工改 ROADMAP.md，下次增量更新即被覆盖 |
| **SDDU 贡献者 / 新维护者** | 阅读 roadmap Agent 指令，试图理解"输出格式到底以什么为准" | 「§5 是输出格式，§6 又说输出是内置固定格式，而且 §5 那段骨架跟真的 ROADMAP 差得很远」 | 以实际 ROADMAP.md 为事实标准，反向猜指令意图 |
| **SDDU 框架使用者（下游项目）** | 框架升级后，若要按新模板整理自己的 ROADMAP | 用户明确：迁移**不在**本 Feature 范围，用户后续自行按新模板让 AI 迁移/重写（RT-004） | 框架升级完成后自行迁移 |

### 3.1 核心问题
> 影响面大、频率高、用户强烈感知

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| Q-001 | **ROADMAP 输出结构无权威来源，产物"读不懂"（结构漂移已事实发生）**：§5 内联骨架（约 47 行，行 199–247）早已无法描述真实产物（1382 行，含 9 个骨架外章节）；骨架内表格列数不一致。用户以当前 ROADMAP 为反面教材，原话「AI 简直是随心所欲，完全看不懂」。**来源：用户访谈（RT-002）+ 源码/产物比对** | 每一份 ROADMAP.md；所有读者与下游消费者 |
| Q-002 | **输出格式定义位置偏离框架统一模板逻辑**：roadmap 是 9 个有产物 Agent 中唯一声明"内置固定格式、不走外部模板"的例外；Handlebars 占位符、两级模板查找、构建分发链路对它均不生效。**来源：源码扫描** | ROADMAP 的格式自定义能力；构建/分发链路一致性 |

## 4. 竞品参考
> 记录竞品对类似问题的处理方式，回答"别人怎么做的、我们有什么不同"

| 竞品 | 是否处理过类似问题 | 处理方式 | 与我们场景的差异 |
|------|-------------------|---------|----------------|
| **`@sddu-docs`（内部先例，FR-DOCS-OPT-001）** | 是 — 同为辅助 Agent，已补齐 20 个输出模板 | 模板库置于 `src/templates/outputs/docs/`；每个模板通过自身元数据头（`文档定位` / `输出文件名`）声明定位，Agent 运行时动态发现，**不在指令中硬编码模板清单**；用户自定义模板放 `.sddu/templates/agents/output/docs/` | docs 是**分域多文件**（按业务域拆分）；roadmap 是**单文件项目级长文档 + 增量更新**，不存在"按域选模板"的发现逻辑 |
| **SDDU 7 个主流程 Agent（内部先例，FR-TEMPLATE-001 / FR-TPL-001）** | 是 — 均采用「用户自定义 > 插件内置」两级模板查找 + `<<变量名>>` 占位符 | 指令 §6 声明查找优先级；模板放 `src/templates/outputs/`；`scripts/build-agents.cjs` 递归裸拷贝到 `dist/templates/output/` | 主流程 Agent 产物为 **Feature 级**（每次全量渲染、路径含 feature 名）；roadmap 产物为**项目级单例 + 增量更新**。**RT-001 已决策：统一逻辑 —— roadmap 并入同一机制** |
| **`@sddu-tree`（内部先例，FR-TREE-SKILL）** | 是 — 但选择了另一条路径 | 将 `@sddu-tree` **降级为 Skill**，不再作为 Agent 持有独立输出模板（FR-TREE-SKILL v3.1.0） | SDDU 对辅助能力有两条路径：**Skill 降级** vs **Agent + 模板**。本 Feature 显式选择后者（与 RT-001 的统一逻辑一致） |
| **Backstage (Spotify)** | 是 — 软件目录与技术文档一体化 | 通过 `catalog-info.yaml` 注册组件，聚合为统一开发者门户；门户结构由前端页面模板固定（来源：通用行业认知，本次未做联网核实） | Backstage 依赖显式注册与前端渲染；SDDU 的 ROADMAP 由 LLM 按模板生成 markdown，无前端层 |
| **外部 roadmapping 工具（ProductBoard / Aha! 等）** | 是 — 产品路线图有预置结构化视图 | 以固定字段（目标 / 时间窗 / 优先级 / 状态）驱动视图渲染，而非自由 markdown（来源：通用行业认知，本次未做联网核实） | 这些工具是**数据驱动视图**；SDDU 是**文档驱动**且由 LLM 填充内容，模板只能约束结构不能约束数据来源 |

> ⚠️ **注意**: 以上竞品信息仅描述事实，不做方案推荐。部分条目来源为通用行业认知、本次未做联网核实，如需采信建议在 spec 阶段补充调研。具体实现方式将在 spec 和 plan 阶段结合 SDDU 的实际约束（Handlebars 模板引擎、两级模板查找、单文件 + 增量更新语义、`src/` 工程边界）评估。

## 附录 B：范围与边界落定
> 依据用户答复 + README §209-211「项目约束（Agent 必读）」落定本 Feature 的范围与边界

### B.1 Feature 目标（事实陈述）
1. **消除 roadmap 输出结构漂移** — 以固定的输出模板替代已失效的 §5 内联骨架，使 ROADMAP 的结构可预期、可读、可被下游稳定引用。（动机来源：RT-002）
2. **并入框架统一模板逻辑** — roadmap 对齐「用户自定义模板（优先） > 插件内置模板（兜底）」两级查找与 Handlebars `<<变量名>>` 占位符机制，不再是"内置固定格式"的例外。（决策来源：RT-001）

### B.2 交付范围（仅设计态源码）
| 类型 | 目标 | 说明 |
|------|------|------|
| 新增 | `src/templates/outputs/sddu-roadmap.md.hbs` | roadmap 的专属输出模板（单文件 + 增量更新；骨架切分见附录 C OP-001） |
| 修订 | `src/templates/agents/sddu-roadmap.md.hbs` | 移除已失效的 §5 内联骨架、§6 改为统一模板引用（对齐其他 8 个 Agent 的写法）；顺带修正 Q-006 边界笔误 |
| 必要适配 | `scripts/`（如需） | 仅在现有 `build-agents.cjs` 递归裸拷贝无法覆盖时补充；A-006 待验证，预计无需改动 |

### B.3 明确非目标（不在范围内）
- ❌ **不迁移、不重写当前 `.sddu/ROADMAP.md`**（RT-004）—— 仅作反面参考素材；用户后续自行按新模板让 AI 迁移

- ❌ **不把旧 Feature `specs-tree-template-quality-unification/spec.md` 列为修改目标** —— EC-004 修订以「本 Feature spec 显式声明修订/取代」的方式记录（R-001）

- ❌ **不涉及 `sddu-fast` / `sddu` 的模板豁免统一**（RT-005 范围收敛）
