# ADR-003: 合并机制载体 — 沿用 Agent-Native 零代码路径（不新增运行时脚本）

## 状态
ACCEPTED

## 背景

标记语法（ADR-001）与合并算法（ADR-002）确定后，还有一个载体决策：**这套机制由谁执行**。可选载体有三类：

1. **Agent-Native（零代码）**：机制写成 agent 指令 + 模板注释，由 LLM 在运行时读取模板、解析产物标记、合并、写回。
2. **运行时代码**：新增确定性脚本/模块（如 `scripts/merge-roadmap.cjs`，或 TS 模块）负责解析与合并，agent 只调用。
3. **混合**：脚本渲染骨架，LLM 填语义内容。

现状事实（plan 阶段源码/环境验证）：

- 现有 8 个有产物 Agent 的模板查找、`<<变量名>>` 替换、渲染**全部是 Agent-Native**：`src/**/*.ts` 中无任何模板加载/渲染代码（`grep -rn "\.hbs" src/ --include='*.ts'` 仅一条注释），`package.json` 无 handlebars 依赖；`build-agents.cjs:158` 明确「raw copy, no Handlebars processing」。
- 内容本身（RICE 评分、版本划分、风险识别）**本质是 LLM 的语义工作**，无法代码化。方案 3 会产出一个「脚本渲染骨架 + LLM 填内容」的混合体，职责切分反而更复杂。
- spec 的工程约束：实现目标仅限设计态源码（`.sddu/`、`.opencode/` 不得作为实现目标）；规模定为 S（约 2 文件）。
- **现实反证**：本工作区中 sddu-tree Skill 引用的 `scripts/generate-tree.cjs` **并不存在**（`ls scripts/` 无此文件）——脚本型机制在本项目缺乏维护闭环，新增第三个脚本会累积同类负债。

## 决策

采用**方案 1：Agent-Native 零代码路径**。

- 机制不得包含任何运行时代码：不新增 `scripts/*.cjs`、不新增/修改 `src/**/*.ts`、不引入 handlebars 依赖。
- 机制的三处落点：
  1. `src/templates/outputs/sddu-roadmap.md.hbs` — zone/entry 标记（锚点的**声明**与**持久化**）；
  2. `src/templates/agents/sddu-roadmap.md.hbs` §5.4 — Step A–D 合并算法（**执行规程**）；
  3. 同文件 §6 / §7 / §8 — 两级查找、结构约束与异常处置（**护栏**）。
- 正确性不靠代码强制，而靠：**可检测的失败模式**（标记配对/缺省语义 → 缺失即退化而非乱合并）+ **静态可校验**（`grep` 计数、H2 集合比对）+ **可回归**（二次运行幂等 diff、既有 entry 逐字保留测试）。
- 若未来出现确定性要求更高的场景（如 CI 批量生成），可将 `sddu:` 标记语法直接复用为解析契约，在 `scripts/` 增设独立验证器（**不在本 Feature 范围**）。

## 后果

**正向**：
- 与既有模板机制完全同构，使用者无需理解第二套心智模型；`@sddu-roadmap` 从「例外」回归「统一逻辑」的目标（G-002）一步到位。
- 严格守住工程边界（NG-005 / NFR-003）：变更集仅 2 个 `src/` 文件；不触碰 `.opencode/`、`.sddu/` 与分发链路。
- 无新增依赖、无构建链路改动（`scripts/` 经实测无需改动，FR-011），回滚成本 = 2 个文件 revert。
- 避免了脚本型机制的维护断链（`generate-tree.cjs` 缺失的现实反证）。

**代价 / 残余风险**：
- **无编译期保证**：合并正确性依赖 LLM 依指令执行 → 缓解：双端标记的可检测性 + §5.4 强制流程 + §7 规则 + §8 异常表 + validate 场景 V-06/V-07/V-08（幂等、保留、非破坏性）。
- 无法单测（jest 不可覆盖）→ 缓解：以「静态校验 + 渲染产物行为测试」替代单测；在 review 清单（§7.1/§7.3）与 verify 场景（§8）中逐项落实。
- 机制演进（新增 zone 类型）需同步改模板与指令两处 → 由 EC-010 的「结构变更须记入修订记录」与 review 清单约束。

## 备选方案与否决理由

| 备选 | 否决理由 |
|------|---------|
| 运行时代码合并（`scripts/merge-roadmap.cjs`） | 需把模板查找/变量替换/内容生成一并代码化，而内容生成不可代码化 → 复杂度与范围远超 S 规模；触碰工程边界（新增脚本 + 分发/安装链路）；与既有 Agent-Native 机制不一致；存在工程边界不能作为实现目标（`.opencode/`）的硬阻断 |
| 混合（脚本渲染骨架 + LLM 填内容） | 职责切分最复杂（谁负责结构校验、谁负责幂等？），且同样需要新增脚本 |
| 引入 Handlebars 真渲染 + 自定义 helper 做合并 | `package.json` 无 handlebars 依赖；引入依赖 + 构建期渲染会改变现有一切模板的行为（违反 NFR-008「不影响其他 10 个 Agent」） |
