# ADR-002：同步机制——`sddu-skill-sync` Skill 按需同步

## 状态
PROPOSED

## 背景

根据 ADR-001 的双层架构，源目录中的 Skill 必须拷贝到实际目录（`.opencode/skills/`）才能被 OpenCode 原生 skill 机制加载。需要确定拷贝同步的技术策略。

**spec v2.3.1 用户最终设计决策**：否定 install.sh 主动同步方案（旧 plan v1.0 的 ADR-002），改用框架内置 `sddu-skill-sync` Skill 实现源目录到实际目录的同步逻辑。用户选择「Skill 优先」路径——sync 逻辑以 Skill 形式承载而非 bash 脚本硬编码。

核心约束：
- FR-020（重写 v2.3.1）：通过 `sddu-skill-sync` Skill 实现源目录到实际目录的同步。该 Skill 描述同步逻辑，用户通过对话触发（如「同步 SDDU Skills」）。拷贝规则：(a) 框架级 Skill 保持 `sddu-` 前缀拷贝；(b) 用户级 Skill 保持原名拷贝；(c) 命名冲突时框架级优先。
- FR-028（新增 v2.3.1）：`sddu-skill-sync` Skill 内置——Skill body 包含完整的同步流程描述。
- FR-024：源目录删除 Skill 后，同步时清理实际目录残留，但不影响用户手动放置的第三方 Skill。
- FR-023：命名冲突时框架级 Skill 优先。
- G-009（新增 v2.3.1）：内置 `sddu-skill-sync` Skill，用户按需指定调度，适配不同 LLM Agent 工具的实际目录差异。

备选方案：
- **方案 A**：`sddu-skill-sync` Skill 按需同步——Skill body 描述完整同步逻辑（源目录扫描 → 实际目录路径检测 → 全量拷贝 + 管辖标识标记 → 残留清理 → 同步报告）。用户对话触发，Agent 加载 Skill 后按指引执行文件操作。install.sh 仅初始化目录 + 提示用户运行 sddu-skill-sync。
- **方案 B**：install.sh 全量拷贝脚本——install.sh 内嵌 bash 拷贝函数，安装/更新时自动全量拷贝（旧 plan v1.0 方案，已被用户否决，作为对比基准保留）。
- **方案 C**：混合——install.sh 初始化 + Skill 增量同步。安装时由 install.sh 做一次性拷贝初始化，后续增量变更通过 sddu-skill-sync Skill 处理。

## 决策

我们决定采用 **方案 A（`sddu-skill-sync` Skill 按需同步）**。

**同步策略细节**：

1. **承载形式**：`sddu-skill-sync` 框架级 Skill（`src/skills/sddu-skill-sync/SKILL.md`），Skill body 使用自然语言描述完整同步流程：
   - (a) 扫描源目录（`.sddu/skills/` + `.opencode/plugins/sddu/skills/`）
   - (b) 检测当前 LLM Agent 工具的实际目录路径（如 OpenCode 使用 `.opencode/skills/`）
   - (c) 全量拷贝：清空实际目录中 SDDU 管辖的 Skill，从源目录全量重新拷贝
   - (d) 管辖标识标记：维护 `.opencode/skills/.sddu-manifest.txt` 清单文件，记录 SDDU 管辖的 Skill 列表
   - (e) 清理源目录中已删除的 Skill 在实际目录的残留
   - (f) 输出同步报告（新增/更新/删除 Skill 数量）

2. **触发时机**：用户对话触发（如「同步 SDDU Skills」「sync skills」「更新 SDDU Skills」等语义匹配）。不在 install.sh 安装/更新时自动触发。

3. **install.sh 职责变更**：
   - **继续**：Step 8 创建 `.sddu/skills/` 空目录；Step 5 将框架源 Skill 拷贝到 `.opencode/plugins/sddu/skills/`（插件分发，属于源目录维护）
   - **移除**：旧 plan 中的全量拷贝函数（`stash_sddu_skills()`）——不再将源目录 Skill 拷贝到 `.opencode/skills/`
   - **新增**：Step 8 结束时打印醒目提示——「SDDU Skills 已安装到源目录，请说『同步 SDDU Skills』来将 Skills 部署到实际目录」

4. **冷启动策略**：
   - 路径 1（主要）：install.sh 结束时的醒目提示
   - 路径 2（Agent 自检）：coordinator 模板中加入自检逻辑——若实际目录中无 SDDU 管辖 Skill，建议用户同步
   - 路径 3（兜底）：`@sddu-fast sync` 命令

5. **拷贝规则**：
   - (a) 框架级 Skill 保持 `sddu-` 前缀拷贝到实际目录
   - (b) 用户级 Skill 保持原名拷贝
   - (c) 命名冲突时框架级优先（框架源后拷贝，覆盖用户源）
   - (d) 保持源目录的完整目录结构（SKILL.md + scripts/ + references/ + assets/）

6. **管辖标识**：同步时创建/更新 `.opencode/skills/.sddu-manifest.txt`，记录 SDDU 管辖的 Skill 名称列表。同步时只清空清单中的 Skill，保留用户手动放入的其他第三方 Skill。

## 后果

### 正面
- **符合 spec v2.3.1 用户最终设计决策**——sync 逻辑以 Skill 形式承载，而非 bash 脚本硬编码
- **跨 LLM Agent 可适配**——适配不同工具（OpenCode / Codex / Claude Code）的实际目录差异时，只需更新 Skill body（Markdown），无需修改安装脚本。这正是 spec 选择 Skill 路径的核心原因
- **完成三元自举闭环**——与 `sddu-skill-discovery`（发现）、`sddu-skill-creator`（创建）并列，三者共同构成「用 Skill 发现 + 用 Skill 创建 + 用 Skill 同步」的完整 Skill 生态闭环（G-009）
- **用户可控、按需触发**——不强制在安装/更新时执行拷贝，用户根据需要主动触发同步。符合「Agent 不越界」的安全原则
- **上下文完整**——Agent 加载 Skill 后了解完整的「为什么同步 + 如何同步」，可做出智能决策（如检测到权限不足时给出建议、询问用户确认后执行）
- **与整体架构哲学一致**：「Agent 固定 + Skill 扩展」——同步机制作为扩展能力通过 Skill 实现，而非在核心安装脚本中硬编码

### 负面
- **冷启动问题**——首次安装后 `sddu-skill-sync` 自身仅在源目录中，不在实际目录中。用户需要知道并执行同步指令。缓解：install.sh 醒目提示 + Agent 自检
- **依赖 Agent 工具的文件操作权限**——不同 LLM Agent 工具的工具权限可能不同（OpenCode 有 full access，其他工具可能受限）。Skill body 中描述的文件拷贝操作可能被权限控制阻止。缓解：Skill body 使用通用自然语言描述操作；权限配置文档化
- **比 bash 脚本多一步推理开销**——Agent 解析 Skill body → 理解指令 → 执行文件操作，比直接运行 bash 多一步推理

### 未选择 B 的核心原因
方案 B（install.sh 全量拷贝）已被用户在 spec v2.3.1 中明确否决：
1. **硬编码路径不可跨 LLM Agent 适配**——不同 Agent 工具的实际目录不同（OpenCode 用 `.opencode/skills/`，Claude Code 用 `.claude/skills/`），bash 脚本需为每种工具写适配逻辑
2. **违反「Skill 优先」原则**——spec 明确：同步是扩展能力，应通过 Skill 实现，不应在核心安装脚本中硬编码
3. **不符合三元闭环设计**——缺少 sync Skill 就无法形成「发现 + 创建 + 同步」的完整闭环

### 未选择 C 的原因
方案 C（混合）增加双路径维护负担：
- 两套路径（install.sh bash + sddu-skill-sync Skill body）的同步逻辑可能产生分歧
- 增量场景下的行为不一致风险——install.sh 只做首装，Skill 做增量，但用户可能期望 install.sh 在更新时也同步
- 维护成本最高——任何同步逻辑变更需同时更新两个地方
