# 定位说明：SDDU 阶段方法论 与 dsh 原生能力的分工与共存

> **文档定位**: 回答「什么时候该走 SDDU 阶段、什么时候该用 dsh 原生能力、什么时候两者共存」
> **权威来源**: spec.md FR-010 / EC-009；dsh 事实锚定 2026-08-14 快照
> **创建人**: SDDU Build Agent
> **版本**: v1.0

---

## 0. 一句话定位

**SDDU 管「有状态、有产物、不可跳步的软件变更流程」；dsh 原生能力管「单次会话内的执行与上下文治理」。**
两者**不竞争**：SDDU 是**流程层**，dsh 原生能力是**会话层**。冲突只会在「同一件事被两层同时管」时出现，
处置原则是**明确单一归属 + 让归属可见**。

---

## 1. dsh 原生能力速览（快照 2026-08-14）

| 原生能力 | 作用范围 | 与 SDDU 的关系 |
|---------|---------|---------------|
| **plan mode**（如 `/plan [message]`、`/plan off`） | 会话内的执行日志软引导：把「打算做什么」写成计划并让会话围绕它推进 | **会话层**，不读写 SDDU 的 `state.json`；**不能替代** SDDU 的阶段产物与门禁 |
| **todo** | 会话内的任务清单勾选 | **会话层**；SDDU 的 `tasks.md` 是**跨会话持久产物**，粒度与生命周期不同 |
| **workflow** | 会话内多步编排 | **会话层**；SDDU 阶段是**跨会话、跨人**的流程契约 |
| **goal** | 单次目标设定与追踪 | **会话层**；SDDU 的 goal 落在 spec/plan 产物上 |
| **compaction** | 上下文压缩、长会话续命 | **基础设施层**；SDDU 的产物文件（`state.json` / `spec.md` / …）是 compaction 之后**仍可恢复**的事实源，二者互补 |

关键差异：**dsh 原生能力不产生 SDDU 的阶段产物，也不维护 `phase` 状态。**
SDDU 的权威状态只有一处：`.sddu/specs-tree-root/<feature>/state.json`。

---

## 2. 判定规则（先判归属，再执行）

| 判断问题 | 结论 |
|---------|------|
| 这件事是否需要**留下可复用的产物**（spec / plan / tasks / build / review / validate）？ | 是 → **走 SDDU 阶段** |
| 这件事是否需要**跨会话继续**，或需要别人接手？ | 是 → **走 SDDU 阶段**（产物 + `state.json` 承载） |
| 这件事是否需要**阶段顺序约束**（不跳步、产物齐全才推进）？ | 是 → **走 SDDU 阶段**（门禁协议承载） |
| 这件事只是**当前会话内的执行步骤记录**，做完即弃？ | 是 → **走 dsh 原生**（plan mode / todo） |
| 这件事只是**单次问答、查资料、改一行**，无需产物与状态？ | 是 → **走 dsh 原生**，或 `sddu-fast`（零产物） |
| **两者都对**（长会话里推进一个 Feature）？ | → **共存**：SDDU 承载流程与状态，dsh 原生承载会话执行与上下文治理 |

---

## 3. 判定示例

### 示例1｜走 SDDU：给某模块加一个带验收标准的新能力

用户目标：「给 specs-tree-x 增加一个导出 CSV 的能力，要有需求、方案、任务和验证」。

→ **走 SDDU 阶段**：`/sddu spec specs-tree-x` → `plan` → `tasks` → `build` → `review` → `validate`。
理由：需要持久产物、需要阶段顺序、需要跨会话可续。**不要**只用 dsh 的 todo 代替，因为 todo 不产生
`spec.md` / `plan.md` 这类可评审产物，也不维护 `phase`。

### 示例2｜走原生：在当前会话里把一个大重构拆成执行步骤并逐条勾选

用户目标：「这次会话内我要把 utils 拆成 5 个文件，帮我列出来并跟着做」。

→ **走 dsh 原生**（todo / plan mode）：一次性、单会话、无需持久化产物与阶段状态。
若中途变成「这是个需要评审的变更」，则**升级为 SDDU**（产出 spec 后再实施）。

### 示例3｜共存：在一个长会话里推进 SDDU 阶段，同时用原生能力治理上下文

用户目标：「接着上次的 specs-tree-y，继续推进到 build，会话很长注意别丢上下文」。

→ **共存**：
- **SDDU 侧**：读 `state.json` 确认 `phase`，按门禁协议推进到 `builded`，产出代码与 `build.md`，
  输出 `[SDDU-STATE-SYNC]`；
- **dsh 侧**：用 plan mode / todo 记录本次会话的执行步骤，用 compaction 续命长会话。
- 分工边界：**阶段是否推进由 SDDU 的门禁与状态协议决定**；**会话内怎么排步骤由 dsh 原生决定**。

### 示例4｜共存但归属易混：plan mode 的「计划」≠ SDDU 的 plan 阶段

用户目标：「用 /plan 写个计划，然后我们按 SDDU 的 plan 阶段来」。

→ **共存 + 显式区分**：`/plan` 写的是**会话内执行日志**（dsh 原生，一次性）；
`/sddu plan <feature>` 产出的是 **`plan.md` + ADR** 并推进 `phase: planned`（SDDU 持久产物）。
两者可以同时存在，但**不得互相冒充**：不要把 `/plan` 的输出当作 `plan.md`，也不要用它绕过门禁。

## 4. 同一会话混用时的可观测提示与建议（EC-009）

混用本身没有问题，风险是**归属不清**。请遵守以下可观测约定：

1. **状态提示唯一化**：任何阶段推进都必须输出 `[SDDU-STATE-SYNC]`，并且只有**一条**。
   若你看到会话里有两处「已推进到 X」而没有 SYNC 记录 → 视为不一致，按
   [`verification.md`](./verification.md) 的 V3 三方对账处理。
2. **门禁提示显式化**：进入阶段前必须出现 `[SDDU-GATE-ALLOW]`（若被拒绝则是 `[SDDU-GATE-DENY]`）。
   若阶段动作已开始但**没有任何门禁块** → 说明门禁被跳过，应立即停止并补做前置检查。
3. **产物 vs 会话计划分开表述**：在会话中明确区分「这是会话计划（dsh 原生）」与
   「这是阶段产物 `plan.md`（SDDU）」，避免把一次性的会话计划误认为可复用的阶段产物。
4. **冲突时以 SDDU 为准（仅限流程与状态）**：当会话计划与 `state.json` 冲突时，
   **流程与状态**以 `state.json` 为准（dsh 会话日志只是观测/对账源）；
   反之，**上下文治理**（compaction / 会话编排）以 dsh 原生为准，SDDU 不介入。
5. **建议**：一个 Feature 的推进尽量保持在**同一条会话线**内，减少并发写 `state.json` 的覆盖风险；
   若必须并行，推进后互相对账一次 `state.json` 的 `phaseHistory` 是否缺中间条目。

## 5. 一张图记住分工

```text
┌──────────────────────────────────────────────────┐
│  dsh 会话层：plan mode / todo / workflow / goal   │  ← 单次会话内的执行与上下文治理
│  dsh 基础设施层：compaction                        │
├──────────────────────────────────────────────────┤
│  SDDU 流程层：7 阶段 + 门禁 + state.json 唯一权威  │  ← 跨会话、可评审、不可跳步的变更流程
│  （产物：discovery/spec/plan/tasks/build/review/validate）│
└──────────────────────────────────────────────────┘
      流程怎么走 → 看 SDDU；       这次会话怎么干 → 看 dsh 原生
```

> ⚠️ 边界提醒：dsh 侧的门禁是**显式可观测的软引导**（FR-004b），**非硬强制**；
> 不要把「没有报错」等同于「门禁生效」。强制力落差见 [`dual-platform-diff.md`](./dual-platform-diff.md)。
