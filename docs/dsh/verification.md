# 验证方法：V1~V5 场景 + 最小人工验证清单

> **文档定位**: 交付「**如何验证** + 验证场景 + 人工观测指引」（FR-006 / NFR-005 / NFR-006 / EC-006）
> **权威来源**: spec.md 附录验证场景表；ADR-003（门禁降级断言）/ ADR-004（三方对账）
> **创建人**: SDDU Build Agent
> **版本**: v1.0

---

## 0. ⚠️ 性质声明（置顶，务必先读）

> **V1~V5 是「验证方法与验证场景」，不是端到端验收标准。**
> **端到端验证不在本 Feature 的实施范围内**（既定约束）；执行由**用户配合人工完成**。
> 本 Feature 的验收以其需求条款（spec §5/§6/§7）为准，而非以 V1~V5 的执行结果为准。

其他必须遵守的边界：

- **无 CLI**：dsh 侧没有命令行入口，V1~V5 **无法做自动化断言**，全部依赖人工观测。
- **「未观测」≠「通过」**：任何未实际观测到的项，一律标记为**待用户配合验证**，
  **不得**把「未观测」「没报错」「看起来正常」写为「通过」（EC-006）。
- **本地测试的定位**：仓库内的 `jest` 套件（`skill-package.test.ts`）**只断言生成物的静态结构**
  （目录齐全、协议块存在、版本锚定、隔离规则），**不冒充实机验证**，也不构成 V1~V5 的替代。

---

## 1. 观测依据（三源）

| # | 观测源 | 能看到什么 |
|:--:|--------|-----------|
| ① | **dsh Web UI 会话内容** | skill 列表与来源标识（V1）、入口是否被识别（V2）、门禁块与 SYNC 记录（V3/V4） |
| ② | **`.sddu/` 产物文件** | 阶段产物是否存在且非空、`state.json` 的 `phase` / `phaseHistory`（V3 对账） |
| ③ | **dsh 侧会话事件日志（`SessionEvent`，可回放）** | `[SDDU-GATE-*]` / `[SDDU-STATE-SYNC]` 记录是否留在日志中、能否回放（V3/V4 证据） |

无需命令行：以上三源都可以在 **Web UI + 文件浏览**中完成。

## 2. V1~V5 逐项

### V1 装配可见

- **步骤**：
  1. 安装 Skill 包（二选一）：
     - 一键：`curl -fsSL https://raw.githubusercontent.com/THZSummer/sddu/main/bootstrap.sh | bash -s -- ./my-project --platform dsh`（README §2.0）；
     - 本地：`scripts/install-dsh.sh --project-root ./my-project`（README §2.1）。
  2. 确认宿主触发 `skills/change` 并刷新 skill 发现缓存；
  3. 在 dsh Web UI 中列出可用 skill。
- **观测方式**：dsh **Web UI** 的 skill 列表（无 CLI）。
- **通过判据**：列表中出现 **11 个** SDDU 条目（`sddu` + 10 个 `sddu-*`）；
  条目**来源可辨识**（`adapters/dsh@<版本>#<快照日期>`）；**无**非预期的遮蔽冲突
  （若存在同名条目，安装脚本已显式提示，需人工确认遮蔽预期）。
- **配合方**：**用户**（提供列表截图或列表文本）。

---

### V2 入口可用

- **步骤**：
  1. 在 dsh Web 会话中输入 `/sddu`（应输出状态仪表盘 / 下一步推荐）；
  2. 输入 `/sddu discovery <feature>`（或降级用法 `sddu discovery <feature>`）；
  3. 再输入一个**非法**阶段标识（如 `/sddu bogus <feature>`）观察拒绝行为。
- **双通道等价（FR-006）**：bootstrap 安装与 install-dsh.sh 安装的落位结果应一致（11 个 skill、来源标识相同）。
- **观测方式**：dsh **Web UI** 会话中的对话内容。
- **通过判据**：
  - 合法入口：进入正确阶段并表现出对应阶段行为；
  - 非法入口：输出 `[SDDU-ROUTE-REJECT] {"input":"…","valid":[…],"hint":"…"}`，
    **不进入任何阶段、不写任何文件**；
  - 若斜杠前缀未被平台送达，记录该平台行为，并确认**降级用法可用**（能力落差证据，不算通过也不算失败）。
- **配合方**：**用户**（对话观测）。

---

### V3 单阶段走通

- **步骤**：
  1. 以最小 Feature 走通一个阶段（建议 `discovery`）：`/sddu discovery <feature>`；
  2. 检查产物与状态是否落盘；
  3. 执行**三方对账**（见下）。
- **观测方式**：dsh **Web UI** 会话 + `.sddu/` 产物文件浏览 + 会话事件日志。
- **通过判据**：
  - 产物存在且非空（如 `discovery.md`）；
  - `state.json` 的 `phase` 与产物一致，`phaseHistory` 追加了对应条目；
  - 会话中出现**恰好一条** `[SDDU-STATE-SYNC]` 记录，字段完整；
  - 三方对账全部一致（见下）。
- **配合方**：**用户 + 维护者**。

#### V3 三方对账（`state.json` ⟷ 产物 ⟷ `[SDDU-STATE-SYNC]` 记录）

| # | 比对项 | 怎么比 | 通过判据 | 不一致怎么办 |
|:--:|--------|--------|---------|-------------|
| ① | **状态 vs 产物** | 读 `state.json.phase`，去 `.sddu/specs-tree-root/<feature>/` 看该阶段产物 | `phase` 对应的产物**存在且非空**（如 `planned` → `plan.md`） | 报告「阶段已推进但产物缺失/为空」，提示回退或补产，**暂停推进** |
| ② | **状态 vs 记录** | 读 `state.json.phaseHistory`，在会话（或事件日志）中找对应的 `[SDDU-STATE-SYNC]` | 每个 phase 推进都有对应 SYNC 记录；允许「日志有、state 无」 | 报告单向不一致并指出**缺失侧**；**禁止自动补齐任何一侧** |
| ③ | **产物 vs 记录** | 比对 SYNC 记录的 `artifact` 字段与磁盘实际产物 | 两者一致 | 报告差异并**暂停推进** |

> 对账铁律：一致性问题**报告而非静默覆盖**（EC-005）；
> `[SDDU-STATE-SYNC]` 记录**不是机器可校验的强证据**，只是一条可回放的推进证据。

### V4 门禁行为观测

- **步骤**：
  1. 制造一次**非法阶段跃迁**（如当前 `registered` 直接尝试进入 `build`）；
  2. 观测会话中是否出现结构化拒绝块；
  3. 同时翻阅 [`README.md`](./README.md) §8 与本文档，确认「已知降级」声明存在。
- **观测方式**：dsh **Web UI** 会话内容 + 会话事件日志。
- **通过判据（双判据，缺一不可）**：
  1. **观测到拒绝块**：会话中出现
     `[SDDU-GATE-DENY] {"feature":"…","from":"…","to":"…","missing":[…],"reason":"…","action":"none"}`，
     且**未写 `state.json`、未产出阶段产物**；
  2. **观测到降级声明**：文档与会话中均含「**已知降级**」声明段（FR-004b / 非硬强制）。
- **配合方**：**用户 + 维护者**。

> 说明：本 Feature 采用 **FR-004b（显式可观测的软引导）**；不采用 FR-004a 的代码层拒绝方案
> （需实现 dsh 插件，契约细节在快照中未覆盖，属 **v5.1.0+** 演进点，本 Feature 不实现）。
> 若模型未按协议输出拒绝块，即视为**降级边界被穿越** —— 这本身就是 V4 应记录下来的观测结果，
> 不得被文档掩盖。

---

### V5 升级跟随

- **步骤**：
  1. 在 dsh 版本更新后，按 [`upgrade-following.md`](./upgrade-following.md) 的**步骤 0~6** 执行；
  2. 重复 V1 → V2 → V3；
  3. 对每个破坏点填**破坏点记录模板**，记录修复动作与回归结果；
  4. 形成成本基线（人时 + 破坏点数）。
- **观测方式**：dsh **Web UI** + 产物文件 + 会话日志（同 V1~V3），外加破坏点记录表与成本基线表。
- **通过判据**：能**按清单定位破坏点**并完成回归 / 修复；成本基线表填写完整
  （含「无法观测」项，不得留空或记作「未变」）。
- **配合方**：**用户**。

## 3. 最小人工验证清单（NFR-005）

**最小步骤序列**（按顺序，全部在 Web UI + 文件浏览内完成，无需命令行）：

| 序 | 动作 | 预计耗时 |
|:--:|------|:--:|
| 1 | 安装 Skill 包（项目级 rank 100），确认落位自检清单输出 | ~3 min |
| 2 | **V1**：Web UI skill 列表确认 11 个条目 + 来源标识 | ~3 min |
| 3 | **V2**：输入 `/sddu` 与 `/sddu discovery <feature>`，再输入一个非法阶段标识 | ~5 min |
| 4 | **V3**：走通 `discovery` 阶段 + 执行三方对账 | ~10 min |
| 5 | **V4**：制造一次非法跃迁，观测拒绝块 + 确认降级声明 | ~5 min |
| 6 | 记录结论（区分「已通过项」与「未观测项」） | ~4 min |

- **时间预算上限**：**≤ 30 分钟**（单次完整 V1~V4；不含安装与刷新 dsh 契约）。
  V5 无固定预算（依赖 dsh 升级时机），但**单次升级跟随**的目标上限为 **≤ 2 小时**（含步骤 0~6 与修复回归）。
- **不依赖命令行**：全程不需要 CLI；仓库内 `jest` 仅用于**生成物静态结构**断言（可选、非前置）。

## 4. 缺口声明（EC-006）

1. **无 CLI → 无法自动化断言**：上述场景全部依赖人工观测，无法纳入 CI，也无法给出机器可校验的判定。
2. **本地 `jest` 的边界**：仅断言生成物的**静态结构**（目录 / 协议块 / 版本锚定 / 隔离规则），
   **不冒充实机验证**，不能替代 V1~V5。
3. **不将「未观测」等同于「通过」**：未实际观测的项在结论中必须标注
   「**待用户配合验证**」，与「已通过项」**分列记录**。
4. **开放张力（如实记录）**：若后续核实 dsh 存在 CLI（与 2026-08-14 快照口径相反），
   则可将部分场景（V1 的列表可见性、V3 的产物/状态一致性）转为脚本断言，
   届时本文档需同步修订，并在 `dsh-contract-manifest.json` 的 `command-registration` /
   `session-events` 依赖点上更新 `observableCheck` 与 `snapshotDate`。
